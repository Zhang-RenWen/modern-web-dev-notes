# 1-23-3 Node.js 記憶體控制 {#1-23-3}

::: info 新增（2026-11）
整理自 Notion「Node.js 了不起」子頁〈Node.js「記憶體（RAM）」控制〉，已套用原頁 AI 校正的現況。
:::

前端頁面常被重新整理，記憶體問題不容易被發現；伺服器程式一跑就是幾個月，任何一點洩漏都會累積到程序崩潰。

## V8 的堆積上限 {#1-23-3-1}

- V8 對 JavaScript 物件所在的**堆積（heap）**有上限。舊版 64 位元系統約 1.4GB；Node.js 12 起依系統可用記憶體動態決定，通常更大。
- 超過上限會出現 `JavaScript heap out of memory` 而退出，即使實體記憶體還有剩。
- 可以在啟動時調整（單位 MB）：

```bash
node --max-old-space-size=4096 app.js     # 老生代上限 4GB
node --max-semi-space-size=64 app.js      # 新生代 semi-space 大小
```

這是靜態設定，必須在程序啟動前決定。容器環境要和容器記憶體限制一起規劃，留空間給堆積以外的記憶體。

## 觀察記憶體使用 {#1-23-3-2}

```js
import process from 'node:process'

const toMB = (b) => (b / 1024 / 1024).toFixed(2) + ' MB'
setInterval(() => {
  const m = process.memoryUsage()
  console.log({
    rss: toMB(m.rss),               // 程序占用的實體記憶體總量（含堆積、堆疊、程式碼）
    heapTotal: toMB(m.heapTotal),   // V8 已向系統要的堆積
    heapUsed: toMB(m.heapUsed),     // 實際使用中的堆積
    external: toMB(m.external),     // V8 管理的 C++ 物件（例如 Buffer）
    arrayBuffers: toMB(m.arrayBuffers), // ArrayBuffer 與 Buffer 占用
  })
}, 1000)
```

## V8 的垃圾回收 {#1-23-3-3}

堆積是隨需求擴大的，不會一開始就要到上限。物件依存活時間分代管理：

| 區域 | 放什麼 | 回收演算法 |
| --- | --- | --- |
| 新生代 | 剛建立的物件 | **Scavenge**：空間分成 from／to 兩半，存活的複製到 to，再互換角色；活過幾次的物件晉升到老生代 |
| 老生代 | 存活較久的物件 | **Mark-Sweep** 標記並清除不再被引用的物件，再用 **Mark-Compact** 整理碎片 |

大多數物件很快就沒用，所以新生代回收頻繁且便宜；老生代回收成本高，要避免大量物件被長期留住。

## 常見的洩漏情境 {#1-23-3-4}

1. **無上限的快取**：用物件或 Map 當快取、memoize 函式結果，只增不減，最後全部堆在老生代。
   - 小量資料：限制筆數並淘汰最舊或最少使用的（LRU，見 [模擬面試 12 Q10](./interview-12.md#interview-12-10)）。
   - 大量資料或多程序共用：改用 Redis、Memcached。多個 Node.js 程序之間本來就無法共用記憶體，外部快取掛了程序也能繼續運作。
2. **一直變長的陣列**：生產者放資料的速度大於消費者處理的速度（佇列只進不出）。限制佇列長度、加上背壓或丟棄策略。
3. **重複綁定事件**：在每次請求的處理函式裡 `emitter.on(...)`，監聽器越掛越多。綁定移到外層只做一次，或用完 `off()`／`once()`。Node.js 超過 10 個監聽器會出現 `MaxListenersExceededWarning`，這通常就是警訊。
4. **計時器與閉包**：`setInterval` 沒清、閉包引用大物件。

## 找出洩漏 {#1-23-3-5}

過去常用的 `heapdump` 套件已經不需要了，現在用內建功能產生 heap snapshot：

```bash
node --heapsnapshot-signal=SIGUSR2 app.js
kill -USR2 <pid>             # 在目前目錄產生 .heapsnapshot
```

```js
import v8 from 'node:v8'
v8.writeHeapSnapshot()       // 程式內主動產生
```

或用 `node --inspect` 連上 Chrome DevTools。分析方式與前端相同：在 Memory 面板載入多個快照比較，依 Shallow／Retained Size 排序，從 Retainers 找出是誰在引用。

## 處理大型資料：Stream 與 Buffer {#1-23-3-6}

**Stream**：把大檔案切成小塊依序處理，記憶體用量固定。`fs.readFile` 一次讀進整個 1.5GB 檔案可能直接爆掉，改用串流：

```js
import { createReadStream, createWriteStream } from 'node:fs'
import { pipeline } from 'node:stream/promises'
import { createGzip } from 'node:zlib'

await pipeline(
  createReadStream('big.log'),
  createGzip(),                 // Transform stream：邊讀邊壓縮
  createWriteStream('big.log.gz'),
)
```

四種 Stream：Readable、Writable、Duplex（可讀可寫）、Transform（讀寫過程中轉換資料）。`pipeline` 會自動處理背壓與錯誤，比手動 `on('data')` 再 `write()` 安全。

**Buffer**：存在 V8 堆積之外（反映在 `external`、`arrayBuffers`），不受堆積上限限制。但仍然是實體記憶體，持續累積一樣會讓 `rss` 上升、被系統或容器砍掉。
