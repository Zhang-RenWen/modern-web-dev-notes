## Shell、Bash、Linux 指令在哪一層 {#1-16-7-1}

Shell、Bash、Linux 指令都在 **User Space**，跟你用 C++、Rust、Node.js 寫的程式在同一個權限層級，不是 Kernel。

```txt
User Space      Bash / Zsh、Linux 指令、C++ / Rust / Node.js 程式、Docker Engine
                （Shell 解讀命令；程式透過函式庫與 OS API 執行操作）
System Call     open / read / write / execve / fork
Kernel Space    程序管理、記憶體管理、檔案系統、網路協定堆疊、驅動程式
Hardware        CPU / RAM / SSD / 網卡
```

| 名稱 | 本質 | 例子 |
| --- | --- | --- |
| Shell | 命令直譯器的統稱 | Bash、Zsh、Fish |
| Bash | Shell 的一種實作 | 變數、迴圈、管線 |
| Linux 指令 | Shell 內建命令或外部程式 | `ls`、`cd`、`ps`、`grep` |
| Linux Kernel | 作業系統核心 | 程序、記憶體、驅動 |

## 執行 `ls -l` 時發生什麼 {#1-16-7-2}

1. Bash 解析指令，找到要執行的程式 `/usr/bin/ls`。
2. 透過 `fork()` 建立子程序，再用 `execve()` 載入 `ls`。
3. `ls` 透過 `getdents64`、`statx` 等系統呼叫向 Kernel 取得目錄與檔案資訊。
4. `ls` 格式化結果，透過 `write()` 輸出到終端機。

重點：**Shell 不直接控制硬體，而是透過作業系統介面請 Kernel 做事。**也不是每個指令都會啟動外部程式，例如 `cd` 是 Bash 內建命令，因為它要改變 Shell 自己的工作目錄，交給子程序改是沒有用的。

用 `strace ls` 可以實際看到這些系統呼叫。學會 C 或 Rust 之後，就能從「使用 Linux 指令」進一步「自己寫出類似的指令」，甚至研究 Shell 與 Kernel 的實作。

## Docker 在哪一層 {#1-16-7-3}

Docker Engine 在 User Space，但它利用 Kernel 的 **Namespaces**（隔離程序、網路、檔案系統的視圖）與 **Cgroups**（限制 CPU、記憶體）建立容器。Docker 沒有自己的 Kernel：在原生 Linux 上，所有容器共用主機的 Kernel；macOS、Windows 的 Docker Desktop 則多一層 Linux VM。

```bash
docker run -it ubuntu bash   # 容器裡有自己的 Bash、檔案系統視圖、程序視圖
uname -r                     # 但顯示的是主機的 Kernel 版本
```

它和 Shell、C++、Rust 不是同一類東西，通常不會打架，但會有資源或設定衝突：

| 衝突 | 原因 |
| --- | --- |
| Port 衝突 | 兩個服務都要綁主機的同一個 port |
| CPU 競爭、記憶體不足 | 容器共用主機的實體資源 |
| Volume 衝突 | 多個程序不當寫入同一份資料 |
| 權限 | 容器存取主機資源時受限 |

延伸：Container 和 VM 的差別在於 Container 不需要啟動自己的 Kernel（見 [1-7-5](./1-7-5.md)）。

## 為什麼同時跑很多指令不會互相破壞 {#1-16-7-4}

因為 Kernel 是所有程序的資源管理者，指令只能向 Kernel 提出請求，不能任意干涉其他程序。

| 機制 | 解決的問題 |
| --- | --- |
| 程序隔離 + 虛擬記憶體 | 每個程序有自己的虛擬位址空間，不能讀寫彼此的記憶體 |
| CPU 排程 | 多個程序分享 CPU 時間 |
| 檔案權限 | 限制誰能讀寫檔案 |
| 檔案鎖 | 協調同一檔案的並行存取（程式要主動使用） |
| Socket 綁定 | 管理位址與 port 的使用 |
| Mutex、Semaphore | 協調共享資源（程式要主動使用） |

但指令**真的會**衝突：

```bash
node server-a.js   # 監聽 3000
node server-b.js   # 也監聽 3000 → Error: listen EADDRINUSE

echo "AAA" > data.txt & echo "BBB" > data.txt   # 結果取決於誰先執行
```

Kernel 保證的是存取控制與資源隔離，不保證所有程序的操作沒有邏輯衝突。Docker 用 Network Namespace 讓兩個容器各自監聽內部的 3000 而不衝突，但若都映射到主機同一個 IP 與 port 仍然會衝突。

Linux 可以歸納成三個核心問題：**誰有權限？誰能使用資源？同時操作會不會出錯？**第三個問題就是學 C++／Rust 會遇到 Mutex、Atomic、Thread Safety、Memory Ordering 的原因。下一步適合研究程序、執行緒、CPU 核心三者的關係。

## 作業系統是用什麼寫的 {#1-16-7-5}

主要是 C、C++、Rust 與組合語言，C 長期是核心開發的主力，Rust 近年逐漸被引入。

| 作業系統 | Kernel 架構 | 主要語言 |
| --- | --- | --- |
| Linux | 模組化單體核心 | C、組合語言、Rust |
| Windows | 混合核心 | C、C++、組合語言、部分 Rust |
| macOS、iOS | XNU 混合核心 | C、C++、組合語言；系統框架另有 Objective-C、Swift |
| Android | Linux Kernel | C、組合語言、Rust；系統層另有 C++、Java、Kotlin |
| Redox OS | 微核心 | Rust |

作業系統不只有 Kernel：上面還有系統工具、Shell、函式庫（C、C++、Rust、Bash），再上面才是各語言寫的應用程式。

**C 適合寫作業系統的原因**：可以透過指標直接操作記憶體位址；執行環境需求低，沒有完整 OS 也能跑；容易和組合語言整合，處理開機、CPU 特權指令、中斷；能精確控制資料佈局與資源使用。

**Rust 能取代 C 嗎**：技術上可以實作核心（Ownership、Borrow Checker、型別系統、`no_std`），但 Linux 已累積數十年的 C 程式碼、驅動與工具鏈，而且核心開發免不了 `unsafe Rust`。

**雞生蛋的問題**：C 寫出作業系統，但 C 編譯器不是需要作業系統才能跑嗎？編譯器可以在另一台已有作業系統的電腦上執行，產生目標機器的程式碼，這叫**交叉編譯（Cross Compilation）**。開機流程是 `UEFI → Bootloader → Kernel → Init／Service Manager → 使用者程式`。

想徹底理解電腦如何運作的學習路線：**C → 組合語言基礎 → 計算機結構 → 作業系統 → Rust**，從「呼叫作業系統 API」一路理解到「作業系統本身怎麼實作這些 API」。
