# 1-24-1 從工程師到架構師 {#1-24-1}

::: info 新增（2026-11）
整理自 Notion「軟體業職涯」第一、二節，以及子頁〈現代後端框架的定位〉、〈未來不太可能「人均架構師」，但很可能「人均具備部分架構能力」〉。
:::

> **一句話**：不要把職涯護城河建立在「寫得比 AI 快」，而是建立在「知道該做什麼、為什麼這樣做、代價是什麼，以及出事後怎麼辦」。

## 工具人 vs 推動者 {#1-24-1-1}

一位工作一年多的工程師：React、Webpack、JS 底層都會，但升不上去。問他做過什麼——「依設計稿切畫面、串資料，功能都做完了」。有沒有拆過需求、主導元件設計、帶過分工？「沒有」。

- 寫程式是基本，**控場、拆解、協作、交付**才決定職級。
- 寫得快不等於做得穩；做得完不等於撐得住。
- **Junior 是執行者，Senior 是推動者。**

## 道、法、術、器 {#1-24-1-2}

| 層次 | 內容 | 特性 |
| --- | --- | --- |
| 器 | Vue、React、Next.js、Rspack… | 一波接一波，永遠追不完 |
| 術 | debounce、lazy load、code splitting | 解一時之急，救不了長期維護 |
| 法 | KISS、SOLID、開閉原則 | 讓你在框架更迭中不迷失 |
| 道 | 抽象思維、問題分解、邏輯建模 | PM 說「炸掉地球」，新手寫 `bombEarth()`，高手寫 `bombPlanet(planet)`，因為明天可能要炸火星 |

前端是「技術問題偏少、工程問題更明顯」的領域，價值在於**為日漸複雜的專案做複雜度管理**：大規模（多功能、多狀態、多畫面）、大團隊（協作模式與共識）、高效率（高流量下用合理成本提供好體驗）。

## Senior 能力模型 {#1-24-1-3}

1. **先判斷再寫**：需求的業務價值？上下游流量怎麼走？會不會高頻迭代？哪些事明確不做？
2. **技術邊界感**：後端介面、資料產出、測試標準，邊界清清楚楚。
3. **架構決策**：SPA／SSR／微前端看未來能否演化；要不要綁死第三方平台；效能要到什麼程度。Junior 解當下，Senior 解長期。
4. **工程決策**：冷啟動 5 秒降到 2 秒、第三方庫可替換而不炸業務、Safari／WebView／弱網降級、測試／灰度／回滾有劇本。

例：建立「提交 → 預覽 → 合併」三段門禁，E2E 測試波動率壓到 3% 以下，bundle 體積退步就自動阻擋合併。先具備這類關鍵經驗，重複造輪子才有意義。

**貢獻的四個層級**：個人（自己的程式寫好）→ 團隊（帶隊友寫好）→ 部門（統籌跨團隊協作、把關技術決策）→ 企業（影響公司技術方向）。被說「溝通能力不足」通常是卡在第一層往第二層。

**資深的判斷標準因公司而異**：
- 台灣公司偏重：能不能自己搞定需求並協作帶人（獨立完成中大型模組、有判斷力的 code review、估時與風險評估、推動小規模技術改善）。
- 國際公司偏重：能不能設計、抽象、推動整個系統並用英文溝通（解釋設計取捨、寫 design doc／ADR、非同步溝通、在領域內被視為專家）。

## 框架封裝了什麼，差距在哪裡 {#1-24-1-4}

現代後端框架已經封裝大量通用能力：路由、middleware、驗證與 DTO、ORM 與 migration、連線池、認證授權基礎、例外處理、日誌與追蹤整合、快取、佇列與排程、OpenAPI、CORS 與限流。所以後端拉開差距的不是「會不會把 API 寫出來」，而是**系統設計與工程決策**。

高含金量的能力：

| 類別 | 內容 |
| --- | --- |
| 身分與權限 | Access／Refresh Token、rotation、revoke、replay 偵測、MFA／Passkey、信任裝置、RBAC／ABAC、多裝置、多租戶 |
| 資料正確性 | Transaction、冪等、樂觀鎖／悲觀鎖、Outbox／Inbox、Saga 與補償、at-least-once 訊息語義 |
| 資料庫與效能 | Schema 設計、索引、EXPLAIN、N+1、連線池、快取策略、熱點、快取穿透與雪崩 |
| 可靠性 | Timeout、Retry、Circuit Breaker、Bulkhead、背壓、降級、災難復原 |
| 非同步系統 | Queue／Worker、重試策略、Dead-letter queue、順序、去重、失敗恢復 |
| 可觀測性 | 結構化日誌、Trace ID 與分散式追蹤、Metrics、SLI／SLO、告警、RCA |
| 長期治理 | API 版本與向後相容、Schema 演進、Contract testing、設定／密鑰／Feature Flag、部署與回滾 |

共同特色：**框架越難替你做決策、錯誤代價越高、越需要理解業務情境，含金量通常越高。**

**登入系統是很好的練習題**：做登入本身含金量普通，有價值的是設計完整的身分與存取系統（Login → MFA → Session → Token → Refresh → Rotation → Device Trust → Permission → Audit → Revocation），並能回答：Token 被偷怎麼辦？如何強制所有裝置登出？如何偵測 Refresh Token 被重放？Web 與 App 的 token 放哪？XSS／CSRF 怎麼處理？權限修改多久生效？管理員能否查看與撤銷 Session？稽核紀錄如何確保可信？（見 [1-19-4](./1-19-4.md)、[1-19-5](./1-19-5.md)）

## AI 時代：什麼會被商品化 {#1-24-1-5}

最容易被商品化的是 **UI + CRUD + API 膠水程式 + 樣板化的業務功能**，一般 CRUD 前端、簡單後台、Dashboard、表單受到的壓力最明顯。AI 也越來越會產生架構圖、Schema、API 設計、BFF／微服務／事件驅動方案、雲端與 Kubernetes 設定、常見效能解法，所以「知道某個架構 Pattern」本身的價值會下降。

不容易商品化的是：**需求定義 → Domain 建模 → 架構 → 資安 → 一致性 → 可靠性 → 效能 → 成本 → 法遵 → 維運**。這些沒有唯一正確答案，高度依賴組織、業務與風險情境。

> **System Design Knowledge ≠ Architecture Judgment**
>
> 前者可以透過書、文件、AI、Pattern 快速取得；後者來自「實際系統 → 決策 → 上線 → 出問題 → Debug → 修正 → 擴張 → 重構 → 再決策」。AI 能縮短架構師的知識學習時間，但很難壓縮經驗成熟時間。

未來不太可能「人均架構師」，但很可能「人均具備部分架構能力」：畫架構圖、列方案、寫樣板的門檻下降，但「對架構結果負責」的門檻沒有下降。職涯路徑可能從 Junior → Senior → Tech Lead → Architect，變成 AI-assisted Engineer → System Engineer → System Designer → Architect／Principal。

## 架構師的四個核心能力 {#1-24-1-6}

1. **系統拆解**：需求 → Domain → 邊界 → 服務 → API → 資料模型 → 基礎設施。
2. **Trade-off**：Monolith vs Microservices、REST vs 事件驅動、SQL vs NoSQL、要不要 Redis、要不要 Read Replica、要不要 Kafka、單區 vs 多區、強一致 vs 最終一致。答案取決於**流量 × 成本 × 團隊能力 × 維運能力 × 業務需求 × 未來成長 × 風險容忍度**。
3. **預測系統演化**：6 個月後呢？10 倍流量呢？團隊從 3 人變 30 人呢？產品方向改變呢？
4. **失敗經驗**：DB lock、記憶體洩漏、快取失效、部署失敗、回滾、網路分區、佇列積壓、併發與一致性問題。

思維的轉換：Engineer 問「怎麼做出來」→ Senior 問「怎麼做好」→ Architect 問「為什麼這樣做？還有哪些方案？代價是什麼？失敗會怎樣？三年後還撐得住嗎？」架構師的核心不是懂最多技術，而是**在限制條件下做高品質、可解釋的技術決策**。

成熟的架構決策同時考慮 **技術 × 成本 × 商業 × 法規 × 組織 × 風險**。例如 SaaS 多租戶還是單租戶，會影響基礎設施成本、客戶隔離、企業銷售、客製能力、法遵、維運成本、毛利與產品策略。因此架構師會產出 ADR、成本模型、風險清單、法遵對照、容量規劃與架構路線圖（見 [1-22-1](./1-22-1.md)）。

能力鏈：**需求分析 → Domain 拆解 → 資料建模 → 資料流 → API → 一致性 → 併發 → 快取 → 佇列 → 分散式系統 → 可觀測性 → 失敗處理 → 擴展 → 成本 → Trade-off**。最後要練成的是：看到需求能辨識問題；看到問題能列出方案；看到方案能說明代價；做完決策能承擔結果。

## 架構師與創業者 {#1-24-1-7}

兩者都在「資源有限 + 資訊不完整 + 未來不確定」下做決策：架構師管理系統（需求 → 約束 → 技術選項 → Trade-off → 風險 → 架構），創業者管理公司（市場 → 資源 → 商業模式 → Trade-off → 風險 → 組織）。所以 Architect → CTO／Founder 是合理的延伸，但不是自然等價，最大的缺口通常是**市場、銷售、通路、現金流、用人與授權**。

另一個分界：**Architecture ≠ Product，Product ≠ Business**。Demo 只有作品價值；有真實使用者才有產品價值；有人付費才有商業價值。所以做產品要 MVP-first，不要一開始就把 CQRS、串流、分散式架構全開。

質變發生在：「我會做功能」→「我會設計系統」→「我會做決策」→「我會配置資源」。

## 依賴塔：什麼知識最耐用 {#1-24-1-8}

晶片 → 作業系統 → 網路 → 雲端 → Runtime → 套件管理 → 框架 → 應用。越往上變化越快、越容易被替換；OS、網路、資料庫、資安、雲端、分散式系統這類底層知識最耐用（見 [1-24-3 技術有不同折舊率](./1-24-3.md#1-24-3-1)）。

**全端是起點，不是護城河**：「會前端加後端」已被 AI 與 BaaS 稀釋成基本要求。能把東西交付、上線、維運一條龍，或在全端之上再鑽一個高門檻領域（資料、資安、架構、產品），才是稀缺。

**靠近營收的位置更容易被看見價值**：金流、CRM、SEO 這類利潤中心的工程師，比內部行政系統更容易證明貢獻；能說出「哪家支付平台手續費低、穩定、使用者偏好」的人，比只會比較框架的人值錢。但反過來也成立：產業與組織決定你有沒有發揮空間，大公司分工細，賺不賺錢多半是上層決策。
