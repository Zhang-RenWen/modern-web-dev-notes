## 案例：3000 行原生 SQL → 換 ORM {#1-22-3-1}

有人因為 MySQL 換 PostgreSQL 重寫 3000 行 SQL，改用 SQLAlchemy 後自認「換 DB 像換手機殼」。回覆點出：**只是從 DB 耦合換成 ORM 耦合**（ORM 爆 CVE 要升級卻撞上舊套件的 Python 版本；ORM 交易回滾有 bug 又要整片重寫）。根因是**業務邏輯沒有和基礎設施解耦**，換 ORM 是頭痛醫頭。

## 套件使用原則 {#1-22-3-2}

- **核心自控、外圍套件化**：業務 / Domain Logic、關鍵狀態與資料流自己掌握；通用 UI、工具、基礎設施用成熟套件。
- 套件要包在明確介面後面，未來可替換。
- 警訊：大量 workaround、扭曲需求迎合套件、需要魔改 → 抽象模型已不適合。
- **套件是實作加速器，不是架構的方向盤。**

## 開源專案怎麼選 {#1-22-3-3}

把每個開源專案當成**你沒付錢、出事也不能找他背鍋的外包團隊**，評估的是團隊與治理，不是功能。

- 個人專案常 3–5 年就棄坑；企業支撐的 community 版通常較長命。底層技術越不穩（例：微信小程序），上層框架越容易棄坑——Taro UI 撐不住，作者乾脆改手寫 UI 元件。
- 集體治理易變成「老好人」：Raspberry Pi pi-gen 合併了一個近千行的 QCOW2 打包 PR，大量相容問題，作者被迫自行維護 fork，最後官方整段移除。
- 無預警 breaking change：Apollo Client 3.0 前五天由內部人員直推 master，改變 loading 時的 data 行為，且拒絕回滾或提供開關。
- 有強勢且持續做事的 BDFL 通常更穩（Linux、Python）；創始人離開易走偏（Rust、Node.js）。
- **辨識技巧**：issue 依留言數排序，看維護者在爭議 issue 裡的態度。
- **萬用解**：鎖版本，過一陣子再評估是否真的需要升級。

## 案例：MinIO 避免雲廠綁定 {#1-22-3-4}

IoT 廣告終端需要獨立權限上傳下載。直覺解是阿里雲 RAM + OSS SDK，技術上沒問題，但會把產品綁死在阿里雲；未來要上騰訊雲、華為雲或客戶自建機房就得重做。改用 **MinIO** 做中介，後端可接 OSS / S3 / 硬碟，終端只需一套 SDK。**從業務長期角度看技術選型。**

## 案例：Kafka vs RabbitMQ {#1-22-3-5}

- 線上廣告分發：內部多系統、百萬級 QPS → **Kafka**。
- 線下 IoT 廣告：量小，但要推到不可控的外部網路，要求權限與投遞確認 → **RabbitMQ**（ACL + ACK/NACK）。

**沒有標準答案，只有當下專案在乎什麼。**

## 案例：預留多對多 {#1-22-3-6}

終端與雲端虛擬物件一開始是 1:1；但了解行業後會知道：多螢幕同步播放（N:1）、政府與營運商共同管轄（1:N）遲早出現。**在不增加成本的前提下，把設計的解決範圍放大**，一開始就做成 M:N，之後只需加表不需重構。
