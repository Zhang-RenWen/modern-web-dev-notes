# 1-22-7 分散式系統基礎 {#1-22-7}

::: info 新增（2026-11）
整理自 Notion「系統設計與架構」七〈分散式系統基礎（MIT 6.824 Lecture 1 精華）〉。
:::

- **能用單機解決就不要做分散式。** 會走向分散式的四個理由：效能（平行化）、容錯、問題本身分散在不同地點（跨國轉帳）、安全隔離。
- 三個難處：併發的時序問題、**部分失效**（某些機器或網路壞、其他正常）、要真的拿到 1000 台的 1000 倍效能很難。
- **Scalability**：兩倍機器換兩倍吞吐是最划算的（買機器比請工程師改程式便宜）；但加 web server 只是把瓶頸**移到 DB**，之後就必須做設計工作。
- 規模把罕見故障變成日常：1000 台機器、每台一年壞一次 ≈ 每天壞三台，所以容錯必須內建在設計裡。
- **Availability**（特定故障下仍服務）vs **Recoverability**（停機等修好後能正確恢復，需要把狀態寫進非揮發儲存）；好的系統兩者兼具。兩大工具：非揮發儲存（checkpoint / log）與 **Replication**（核心風險是副本不同步）。
- **Consistency**：強一致（get 一定看到最近完成的 put）需要大量通訊，副本放越遠越貴（跨洲每次 10–30ms）；因此很多系統選擇弱一致換效能。
- **MapReduce**：工程師只寫 map / reduce，框架處理分散與容錯；shuffle 是最貴的網路傳輸。2004 年網路是瓶頸，所以把 map 排在存有資料的 GFS 機器上（**data locality**）；後來資料中心網路變快，就不再強求本地讀取。限制是只適合 map → shuffle → reduce 形狀，多階段要串多個 job，後繼系統改為完整 pipeline 與 streaming。
