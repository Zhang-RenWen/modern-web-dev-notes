# 8-3 ES 模組操作的實務考量

::: info 改寫（2026-11）
整理自《Practical Modern JavaScript》（2017）。原文對瀏覽器與 Node.js 支援度的擔憂已不存在（所有現代瀏覽器與 Node.js 都完整支援 ES Module），已改寫成「怎麼設計一個好模組」的檢查清單。
:::

模組系統讓我們不用再用 IIFE 包住程式碼來避免污染全域：

```js
// random.js：沒有 export 的東西，外部就碰不到
const calc = (n) => Math.floor(Math.random() * n)
export const range = (max = 1, min = 0) => calc(max + 1 - min) + min
```

但模組化不會自動帶來好設計。評估一個模組時問這幾件事：

| 面向 | 問題 |
| --- | --- |
| API | 對外介面是否小而清楚？使用者需要知道內部細節才能用嗎？ |
| 文件 | 每個匯出的函式都知道參數、回傳值、會丟什麼錯嗎？（TypeScript 型別本身就是文件） |
| 測試 | 能只透過公開介面測試嗎？要 mock 一堆東西才能測，代表依賴太多 |
| 擴充 | 加一個功能要改幾個模組？總是要同時改好幾個，代表切分的邊界不對 |
| 移除 | 能整個刪掉或換掉而不影響其他地方嗎？ |

幾個原則：

- **以複雜度而不是行數衡量**：幾千行的常數表很簡單；兩百行但互相糾纏的狀態邏輯才難維護。
- **依「一起改變的東西」切分**：同一個功能的元件、樣式、測試、API 呼叫放在一起（feature folder），比依檔案類型分資料夾容易維護。
- **避免循環依賴**：A 匯入 B、B 又匯入 A，初始化順序會出問題。可以用 ESLint 的 `import/no-cycle` 規則檢查。
- **控制模組的副作用**：匯入時就會執行的程式碼（註冊全域事件、修改原型）讓模組難以測試，也讓打包工具不敢 tree shake。在 `package.json` 用 `sideEffects` 標註。
- **不要建立萬用的 `utils.js`**：所有東西都往裡面丟，最後每個模組都依賴它。依用途拆成小模組。

打包與 tree shaking 見 [1-9-1](./1-9-1.md#1-9-1-3)、[1-9-2](./1-9-2.md)；大型專案的套件切分見 [1-9-3](./1-9-3.md)。
