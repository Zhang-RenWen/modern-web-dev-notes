# 1-10-3 金融圖表與 Three.js 開發原則 {#1-10-3}

::: info 新增（2026-11）
整理自 Notion「JavaScript」12，來自一個金融儀表板的 K 線圖與首頁 3D 主視覺（2026-10 兩次修正：效能 22 → 60 fps、視覺層次）。每條原則都對應一個真的發生過的問題。SVG／Canvas／WebGL 怎麼選見渲染技術與動畫工具地圖。

## 金融圖表 {#1-10-3-1}

- **K 線圖的 x 軸用交易日序號（類別軸）**，休市日就不會留空白。均線要用完整歷史算完再裁切。
- 十字線吸附到最近的資料點；tooltip 碰到邊界時翻到另一側；支援雙指和滾輪縮放；跟著游標更新的表格用 `table-layout: fixed` 防止抖動。
- 數值用動態的 T／B／M／K 縮寫，tooltip 再顯示完整金額。不要只靠 tooltip 補救，因為手機沒有 hover。
- **配色用語義 token**（primary、secondary、risk、volume）對應 CSS 變數，淺色深色各一組；不要強制每張圖第一條線用主色，風險序列一律用 risk 色，避免「風險」和「機會」兩條線同色。

## Three.js 主視覺踩過的坑 {#1-10-3-2}

| 問題 | 根因 | 修法 | 結果 |
| --- | --- | --- | --- |
| 畫面頓挫、不順 | 程式自己限速 30 fps；60 Hz 螢幕上每 2～3 次刷新才畫一次，間隔忽長忽短 | 每個動畫影格都畫；鏡頭緩動改用時間計算 | 閒置 22.3 → 60.0 fps，超過 25 ms 的影格 267 → 0 |
| 每幀多一份畫面成本 | 為了截圖匯出開了 `preserveDrawingBuffer`，但首頁不提供匯出 | 關掉 | — |
| 捲動時卡 | 捲動每一幀都 `setState`，整個區塊與大 SVG 重繪 | 捲動改寫 CSS 變數，並透過 ref 呼叫 `setProgress`；React 只在章節切換時重繪 | 捲動 JS 時間 1,285 → 453 ms，捲動 22.5 → 59.4 fps |
| 高解析度螢幕吃 GPU | DPR ≥ 1.5 還開 MSAA，填充成本數倍、效果有限 | 只在低 DPR 開 MSAA；pixel ratio 上限桌機 1.75、手機 1.25 | — |
| 動態解析度反而造成卡頓 | 單一長影格就觸發重設畫布大小，而重設本身會同步等待 GPU | 忽略超過 100 ms 的單一影格；連續 45 格明顯超時才降解析度，穩定約 4 秒才升回 | — |
| 試過但撤回 | 把透明面板設成 `visibility: hidden`，重新顯示時大陰影要重新點陣化約 200 ms | 撤回，維持透明度控制 | — |
| 改完使用者仍說卡 | Chrome 的「使用圖形加速」被關掉，3D 全由 CPU 畫 | 先查 `chrome://gpu` | 不是程式問題 |
| 畫面「炫但亂」 | 117 條路線同亮度、25 座城市都有雷達圈、底圖太暗、標題壓在線上 | 主次兩層、8 個焦點、提亮底圖、標題區漸層遮罩、移除跨邊界路線 | 50 條路線（7 主 43 次），一條清楚的主幹 |

## 要避免的作法 {#1-10-3-3}

**視覺設計**

- 所有元素同樣亮度、同樣顏色：眼睛找不到焦點，再多特效也只是雜訊。線、圈、粒子的數量不等於資訊量。
- 線條沒有起訖點、延伸到畫面外：看起來是雜訊，不是流向。標記之間的距離小於最大擴散半徑，圈會疊成一團。
- 文字直接壓在動態線條上，只靠 `text-shadow` 補救；只看一個螢幕尺寸就收工。
- 讓裝飾看起來像真資料：示意路線要在畫面與程式註解都註明不代表即時資料。

**效能**

- 自己限速 fps（跳幀、`setTimeout`）：在 60／120 Hz 螢幕上反而產生不均勻的間隔。用「每幀固定比例」做緩動：幀率一變，速度就跟著變。
- 沒有需要卻開 `preserveDrawingBuffer: true`；高 DPR 還開 MSAA，或 pixel ratio 不設上限。
- 每條線、每個點各自一個物件：draw call 會爆量。每幀 `new Vector3()`、`new Color()`、建立新陣列：GC 會造成週期性卡頓。
- 在一般裝置上做全螢幕後處理 bloom；一遇到單一長影格就重設解析度。

**React 整合**

- 捲動或動畫時每幀 `setState` 驅動 3D 或大型 SVG。
- 在 render 裡建立場景，或在 StrictMode 下重複初始化卻不清理；在 render 裡產生亂數，每次重繪路徑都會跳動。

**資源與相容性**

- 不釋放 geometry、material、texture、renderer，也不處理 `webglcontextlost`。
- 假設 WebGL 一定能用：瀏覽器可能有 WebGL 類別，但 GPU context 被停用。
- 離開畫面、切到別的分頁時仍在跑；忽略 `prefers-reduced-motion`。

## 推薦的作法 {#1-10-3-4}

**視覺層次**

- 分主次兩層：主要元素畫高亮線、光暈與流動粒子；次要元素只畫一股、透明度 0.2。只讓少數幾條線有粒子，方向感比滿屏光點更清楚。
- 焦點控制在 6～8 個，並用測試保證彼此距離大於擴散半徑。底圖要有足夠對比，讓動態元素有地理定位。
- 文字區加局部遮罩：用 `radial-gradient` 只壓文字所在角落，不要整片變暗。透明度、數量這類數值用截圖比對決定（例如背景線 0.14 太淡、0.2 剛好）。

**繪製與效能**

- 同材質的線合併成一組 `LineSegments`；重複的形狀用 `InstancedMesh`（所有雷達圈只用一個 instanced mesh）。
- 大量點用 `Points` 加自訂 `ShaderMaterial`，在 fragment shader 內算光暈。用帶狀光暈 mesh 加 `AdditiveBlending` 模擬 bloom，不需要全螢幕後處理；透明物件設 `depthWrite: false`。
- 動態 buffer 預先配置：`Float32BufferAttribute` 一次建立好，每幀只改數值並設 `needsUpdate = true`；位置每幀變動的物件設 `frustumCulled = false`。
- 粒子數依裝置設預算（桌機 64、手機 42），在初始化時分配，不在動畫幀裡重算。
- 用 `renderer.setAnimationLoop` 驅動，delta 上限 0.25 秒（從背景切回來不會跳）；緩動用 `1 - exp(-k × dt)`，任何幀率都一樣快。
- pixel ratio 設上限，再加動態解析度：持續變慢才降、穩定一段時間才升，並忽略單一突發長影格。

```js
// 與幀率無關的緩動：dt 是這一幀經過的秒數
const ease = 1 - Math.exp(-6 * dt)
camera.position.lerp(target, ease)
```

**生命週期與相容性**

- 先探測 `webgl2` context，拿不到就安靜退回 SVG 備援畫面。
- 用動態 `import()` 載入場景：three.js 只在需要的頁面載入，打包成獨立 chunk。
- `IntersectionObserver` 加 `visibilitychange`：離開畫面或分頁隱藏時停止動畫迴圈；`ResizeObserver` 處理尺寸變化。
- 尊重 `prefers-reduced-motion`：停止動畫，只畫靜態畫面。
- 處理 `webglcontextlost`：停止迴圈並切到備援畫面；元件卸載時釋放所有 geometry、material、texture、renderer，並強制釋放 context。

**和 React 的分工**

- 場景是命令式物件：React 只透過 ref 持有它，元件用 `memo` 加 `forwardRef`；捲動進度寫 CSS 變數並呼叫 `setProgress`，不經過 React state。
- 需要隨機的初始狀態（例如粒子相位）用 `useState` 的初始化函式建立一次。
- canvas 設 `aria-hidden`；重要文字用可以聚焦的 DOM 元素提供，鍵盤使用者也讀得到。

**資料、幾何與測試分離**

- 投影、路線等幾何放在不依賴 WebGL 的純模組，WebGL 場景與 SVG 備援共用同一份資料，並用單元測試檢查（路線在地圖範圍內、焦點彼此夠遠）。
- 場景用模擬的 renderer 測：取出 `setAnimationLoop` 註冊的函式，自己餵時間戳，斷言「每格都畫」、「持續變慢才降解析度」、「離開畫面會停」。

## 量測與驗收 {#1-10-3-5}

1. 先開 `chrome://gpu` 確認硬體加速。
2. 用有視窗的 Chrome、真實螢幕量測（headless 沒有 vsync，fps 不準）；先關掉殘留的瀏覽器程序。
3. 改動前用 `git stash` 在同一台機器量基準。
4. 看三個數字：場景 fps、超過 25 ms 的影格數、捲動時的 JS 時間。
5. 桌機與手機尺寸都拍改動前後截圖並排比較。

**合併前檢查清單**

- [ ] 畫面有明確的主次層次，焦點不超過 8 個且不重疊
- [ ] 沒有超出畫面、沒有起訖點的線；文字和動態圖形之間有遮罩或留白
- [ ] 沒有自己限速；緩動用時間計算
- [ ] 同材質已合併，重複形狀用 instancing，每幀不建立新物件
- [ ] pixel ratio 有上限；高 DPR 不開 MSAA
- [ ] 離開畫面、隱藏分頁、減少動態模式都會停止動畫
- [ ] 不支援 WebGL 或 context lost 時有備援；卸載時釋放資源
- [ ] 真實瀏覽器量過 fps，桌機與手機都截圖比對過

## 什麼時候不要用 Three.js {#1-10-3-6}

- 純 2D 的圖表、少量動態元素：SVG 或 Canvas 2D 就夠，也比較好做無障礙。
- 需要精確對齊文字、可點選、可被搜尋的內容：放在 DOM，不要放在 WebGL。
- 目標裝置常常沒有 GPU 或硬體加速被關：先確定備援畫面也好看，再決定要不要做 3D。

## 名詞剖析 {#1-10-3-7}

| 名詞 | 意思 |
| --- | --- |
| 類別軸 | x 軸只依序排資料點、不按真實時間間距，休市日就不佔位置 |
| DPR／pixel ratio | 一個 CSS 像素對應幾個實體像素；畫布要乘上它才清晰，但成本跟著平方成長 |
| MSAA | 多重取樣反鋸齒；高 DPR 時效果小、成本大 |
| draw call | CPU 要求 GPU 畫一批東西的一次指令；次數越多 CPU 越忙，要靠合併與 instancing 降低 |
| InstancedMesh | 同一個幾何形狀一次畫很多份，一個 draw call 完成 |
| geometry／material／texture | Three.js 的形狀資料／外觀著色方式／貼圖；都佔 GPU 記憶體，用完要 `dispose()` |
| ShaderMaterial | 自己寫 vertex 與 fragment shader 的材質 |
| Bloom／後處理 | 畫完整個畫面後再加一道全螢幕效果（例如光暈），成本高 |
| AdditiveBlending | 顏色相加的混色方式，重疊處會變亮，可模擬發光 |
| Frustum culling | 鏡頭看不到的物件不畫；位置每幀變動的物件邊界算不準時要關掉 |
| delta／dt | 這一幀距離上一幀的時間；用它算移動量，速度才不受幀率影響 |
| webglcontextlost | GPU 重置或資源不足時畫布與 GPU 的連線遺失，要能偵測並退回備援 |
| 動態解析度 | 依效能即時調整畫布解析度：卡就降、穩就升 |
