# 1-7-5 架構與效能: React {#1-7-5}

::: info 改寫（2026-11）
原內容整理自 2019 年前的書籍，以 class 元件的 `shouldComponentUpdate`、`PureComponent`、recompose 為主。已改用函式元件的 `memo`／`useMemo`／`useCallback` 與 React Compiler；事件池化已在 React 17 移除；刪掉 2018 年的瀏覽器跑分數據；Vue 3 的編譯期最佳化保留重點。
:::

> 一句話：**框架的效能問題，絕大多數是「不必要的重新渲染」和「一次做太多工作塞住主執行緒」**；先量測，再處理。

## React 的更新流程 {#1-7-5-1}

1. `setState` 把元件標記為需要更新，同一輪的多次更新合併成一次（批次）。
2. **Render 階段**：重新執行元件函式，產生新的虛擬 DOM，和舊的比對（diff）。這階段可以被中斷（Fiber）。
3. **Commit 階段**：把差異套用到真實 DOM，執行 `useLayoutEffect`，畫面更新後再執行 `useEffect`。

**預設行為：父元件重新渲染，所有子元件都會重新渲染**，不管 props 有沒有變。大部分情況這很快，不用處理；元件樹很大或有昂貴計算時才需要介入。

diff 的三個假設與 key 的規則見 [1-7-1](./1-7-1.md#1-7-1-5)。

## 減少不必要的重新渲染 {#1-7-5-2}

依成本由低到高：

| 做法 | 說明 |
| --- | --- |
| **把 state 往下放** | 只有某個子區塊用到的 state，就放在那個子元件裡，父元件不會因它重新渲染 |
| **把會變的部分當 `children` 傳進來** | `<Layout><ExpensiveTree /></Layout>`：Layout 自己的 state 改變時，`children` 是同一個元素，不會重新渲染 |
| **拆 Context** | 不同更新頻率的資料放在不同 Context，見 [1-7-3](./1-7-3.md#1-7-3-3) |
| `React.memo(Component)` | props 淺比較相同就跳過渲染（等同以前的 `PureComponent`） |
| `useMemo`／`useCallback` | 讓傳給 `memo` 子元件的物件、函式在依賴沒變時保持同一個參考 |
| React Compiler | 編譯時自動做上面兩件事，有用的專案可以把手寫的 memo 拿掉 |

**淺比較的陷阱**：`memo` 只比較第一層的參考。

```jsx
// 每次渲染都是新的物件和函式 → memo 失效
<Row style={{ color: 'red' }} onClick={() => select(id)} />

// 父元件直接修改陣列內容（mutate）→ 參考沒變 → memo 以為沒變，畫面不更新
items[0].done = true
setItems(items)            // 錯
setItems(items.with(0, { ...items[0], done: true })) // 對：產生新陣列
```

**長清單只改一項時**：清單元件把整個陣列傳給每一列，任一項變了，整個陣列是新的，所有列都會重新渲染。把每一列包成 `memo`，並且只傳該列自己的資料（`<Row user={user} />`），就只有改變的那一列重新渲染。上百列以上再考慮虛擬捲動（TanStack Virtual、react-window）。

用 React DevTools 的 Profiler 錄一段操作，看哪些元件渲染了、花了多久、為什麼渲染，再決定要不要處理。

## React 的效能設計 {#1-7-5-3}

- **事件委派**：所有事件在根容器統一監聽（React 17 以前在 `document`）。以前的「事件物件池化」在 React 17 移除，因為現代瀏覽器建立物件的成本已經很低。
- **批次更新**：同一輪的多次 `setState` 只渲染一次，React 18 起所有情境都批次。
- **Fiber**：React 16 把渲染工作拆成一個個小單位（fiber），可以暫停、讓出主執行緒、之後再繼續。這是 React 18 併發渲染（`useTransition`、`Suspense`）的基礎。以前的 Stack Reconciler 一旦開始遞迴就必須跑完，大型元件樹會讓輸入卡住。

## Vue 3 的編譯期最佳化 {#1-7-5-4}

Vue 有模板，編譯器在建置時就知道哪些部分永遠不會變，React 的 JSX 則要到執行時才知道。Vue 3 利用這點：

| 最佳化 | 效果 |
| --- | --- |
| 靜態提升 | 純靜態的節點只建立一次，之後渲染直接重用 |
| Patch flags | 動態節點標記「只有 class 會變」「只有文字會變」，diff 時只比對這些 |
| Block tree | 把動態節點收集成扁平陣列，更新時跳過整段靜態結構，不必逐層走訪 |
| 事件處理函式快取 | 內嵌的事件處理函式自動快取，不會造成子元件多餘的更新 |

所以 Vue 3 的更新成本主要和「動態節點數」成正比，而不是模板大小。React Compiler 則是用另一種方式（自動記憶化）縮小這個差距。
