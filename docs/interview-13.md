# 模擬面試 13：架構、系統設計與行為面試 {#interview-13}

::: info 新增（2026-11）
對應職缺：國泰前端工程師（大型專案架構、技術選型、外包 Code Review、共用元件、帶人、估時）、台達電（Code Review、mentor、跨團隊協作）。資深職缺的二面、主管面通常在這裡定生死。
:::

### Q1. 如果讓你從零規劃一個大型前端專案，你會怎麼做？ <Badge type="tip" text="高頻" /> {#interview-13-1}

::: details 解題思路
不要一開始就講框架。依「需求與限制 → 架構分層 → 專案結構 → 狀態與資料流 → 工程化 → 演進」講，每一步說明理由。
:::

::: details 標準答案與過程
1. **先問清楚**：使用者與規模、團隊人數與技能、要不要 SEO、多語系、瀏覽器範圍、上線時程、既有系統要不要整合。
2. **分層**：UI（框架）→ Application（use case、流程）→ Domain（規則、驗證，框架無關）→ Infrastructure（API client、儲存）。業務規則不綁 Vue／React，換框架或寫測試都容易。
3. **專案結構依業務切**（feature-based），不依技術種類切：

```txt
src/
  app/        初始化、router、providers
  features/   policy/ claim/ payment/（各自的元件、狀態、API）
  entities/   核心資料模型
  shared/     ui/ lib/ api/（真正跨功能共用）
```

4. **狀態分類**：伺服器狀態（Vue Query／TanStack Query）、全域客戶端狀態（Pinia／Zustand）、表單、URL、元件內部。
5. **API 層**：由 OpenAPI 產生型別與 client；資料進系統只做一次 normalize；統一錯誤處理與認證。
6. **工程化**：TypeScript strict、ESLint／Prettier、commit 規範、CI（lint、type-check、test、build、bundle 預算）、Storybook 元件庫。
7. **非功能需求**：效能預算、錯誤監控、權限、i18n、無障礙。
8. **文件與演進**：重要決策寫 ADR，記錄「在什麼指標下要調整架構」。

收尾一句：「架構的目標是讓 100 個人一起改這個專案時，改一個需求只動一個地方。」
:::

### Q2. 怎麼制定前端開發標準並讓團隊遵守？ <Badge type="tip" text="高頻" /> {#interview-13-2}

::: details 標準答案與過程
原則：**能自動化的就不要靠人記**。

| 類別 | 標準 | 落實方式 |
| --- | --- | --- |
| 格式 | Prettier | 存檔自動格式化、pre-commit（lint-staged） |
| 程式品質 | ESLint、TypeScript strict | CI 擋 |
| Commit | Conventional Commits | commitlint |
| 專案結構 | feature-based 目錄、命名規則 | 範本專案、CLI 產生器 |
| 元件 | 共用元件庫、設計 token | Storybook、禁止直接用第三方 UI（lint rule） |
| API | OpenAPI 產生型別 | CI 檢查 schema 變更 |
| 文件 | README、ADR、元件文件 | PR 範本檢查項目 |

推動方式：先找痛點（例如每次 review 都在吵格式），提案時說明好處與成本，先在一個專案試行，用數據（review 時間、bug 數）證明，再推廣。規範要有例外機制，並定期回顧淘汰沒用的規則。
:::

### Q3. 外包廠商交付的前端程式碼，你怎麼驗收？ <Badge type="tip" text="高頻" /> {#interview-13-3}

**考點**：國泰職缺明列「負責外包廠商前端原始碼的技術驗收與 Code Review」。

::: details 解題思路
驗收要「事前定標準、事中可檢查、事後可追蹤」，而且要能量化，避免變成主觀爭執。
:::

::: details 標準答案與過程
**事前（合約與規格階段）**

- 提供技術規範文件、範本專案、元件庫，寫進驗收條件。
- 定義可量化指標：lint／type-check 零錯誤、測試覆蓋率門檻、Lighthouse 分數、bundle 大小、無高風險弱點。

**事中**

- 要求小批次交付與 PR，不接受一次丟整包。
- CI 自動檢查：lint、type-check、測試、建置、依賴掃描、bundle 預算。

**驗收 Code Review 檢查清單**

1. 功能是否符合需求與邊界情況（錯誤狀態、空資料、權限不足）。
2. 架構：是否依專案結構分層、有沒有重複造輪子、業務邏輯是否塞在元件裡。
3. 安全：`v-html`／`innerHTML`、敏感資料存 localStorage、硬編碼密鑰、前端權限判斷是否有後端對應。
4. 效能：大列表、不必要的 watch、未清理的監聽與計時器。
5. 可維護性：命名、型別（大量 `any`）、註解與文件、測試。
6. 授權：引入的套件授權是否允許商用。

**事後**：問題分三級（必須修正／需討論／建議），追蹤到結案；累積成檢查清單給下一個廠商。
:::

**相關筆記**：[1-7-4 Code Review](./1-7-4.md#1-7-4-1)、[1-19-6 寫入 API 防護](./1-19-6.md)

### Q4. Vue、React、Angular 怎麼選？怎麼做技術選型？ <Badge type="tip" text="高頻" /> {#interview-13-4}

::: details 標準答案與過程
選型流程：**定義約束 → 列選項 → 依權重比較 → 做 PoC → 寫 ADR**。

評估面向：團隊現有技能與招募市場、專案規模與維護年限、生態（元件庫、SSR、行動端）、效能需求、學習成本、長期維護風險（社群與企業支持）。

| | Vue | React | Angular |
| --- | --- | --- | --- |
| 特性 | 漸進式、模板、官方生態完整 | 函式庫、JSX、生態最大 | 完整框架、DI、RxJS、強規範 |
| 適合 | 中小團隊快速開發、企業後台 | 需要 Next.js、React Native、大型生態 | 大型團隊、需要強一致的企業專案 |
| 風險 | 大型專案需自訂規範 | 選擇太多，團隊要自己決定架構 | 學習曲線陡 |

回答重點：「沒有最好的框架，只有在這個團隊與限制下最合適的。」並舉例說明你曾經的選型與理由，包括你放棄了什麼。
:::

### Q5. 你怎麼估時？怎麼評估技術風險？ <Badge type="tip" text="高頻" /> {#interview-13-5}

::: details 標準答案與過程
1. **拆解**：把需求拆到半天到兩天的任務（畫面、API 串接、狀態、驗證、測試、文件）。
2. **分類**：熟悉的用經驗值；不熟的先做 spike（限時技術調查）再估。
3. **加上常被忽略的工作**：測試、Code Review 往返、跨瀏覽器、與後端聯調、部署、修 bug。
4. **給範圍不給單點**：「3～5 天，主要風險是第三方 API 文件不完整」。
5. **風險清單**：依賴外部團隊、新技術、需求不明確、效能未知；每項寫對策與觸發條件。
6. **追蹤**：每天對照進度，發現延誤**提早說**並提出選項（砍範圍、延期、加人）。
:::

### Q6. 系統設計：設計一個即時股價看板 <Badge type="warning" text="進階" /> {#interview-13-6}

**題目**：顯示 500 檔股票即時報價與 K 線，每秒數百筆更新，要流暢不卡。

::: details 解題思路
依前端系統設計框架：需求 → 資料流 → 元件架構 → 效能 → 可靠性 → 取捨。
:::

::: details 標準答案與過程
**1. 釐清需求**：同時看幾檔？更新頻率？要不要歷史資料？延遲容忍度？裝置（桌機為主）？

**2. 資料流**

```txt
WebSocket（訂閱目前可見的股票）
  → 訊息解析（Web Worker）
  → 依 symbol 合併最新值（同一幀內多筆只留最後一筆）
  → requestAnimationFrame 批次更新 store
  → 只重繪有變化的列 / 圖表
```

**3. 關鍵設計**

- **只訂閱看得到的**：虛擬列表 + IntersectionObserver，捲動時調整訂閱清單。
- **節流畫面更新**：資料可以每秒 500 筆，畫面只需要每幀更新一次（約 60fps），用 rAF 合併。
- **渲染技術**：報價表用虛擬捲動 DOM；K 線、大量點位用 Canvas（TradingView Lightweight Charts）或 WebGL。
- **狀態**：最新報價放 `Map<symbol, Quote>`，用 `shallowRef`／外部 store 避免深層響應式代理；元件以 selector 只訂閱自己那一檔。
- **重連**：心跳偵測、指數退避重連、重連後依最後序號補資料或重新取快照。
- **頁面不可見時**：`visibilitychange` 時降低頻率或暫停。

**4. 可靠性與監控**：顯示連線狀態與資料時間戳、延遲監控、錯誤回報。

**5. 取捨**：SSE 足以處理單向推播且較簡單；需要下單等雙向操作時用 WebSocket。
:::

### Q7. 系統設計：設計一個有角色權限的企業後台 <Badge type="warning" text="進階" /> {#interview-13-7}

::: details 標準答案與過程
**1. 權限模型**：Role（職能）→ Permission（動作，如 `policy.approve`）→ Scope（資料範圍：自己、部門、全部）→ Condition（金額上限、狀態）。前端只負責顯示，後端每支 API 都要檢查。

**2. 登入流程**：OIDC + PKCE 或 BFF + session cookie；登入後取得使用者資訊與權限清單。

**3. 前端三層控制**

| 層級 | 做法 |
| --- | --- |
| 路由 | 動態註冊可用路由；守衛檢查 `meta.perm` |
| 選單 | 依權限過濾選單樹（子節點有權限就保留父節點） |
| 按鈕／欄位 | `can('policy.approve')` 函式或 `v-permission` 指令 |

**4. 資料**：列表依 scope 由後端過濾；敏感欄位由後端遮罩。

**5. 稽核**：所有寫入操作記錄誰、何時、改了什麼；高風險操作 Step-up 驗證、雙人覆核（Maker-Checker）。

**6. 效能與體驗**：權限清單快取並在變更時失效；無權限頁面與 403 處理一致。
:::

### Q8. 你怎麼帶新人或指導其他工程師？ <Badge type="tip" text="高頻" /> {#interview-13-8}

::: details 標準答案與過程
1. **降低上手成本**：專案 README、環境一鍵啟動、架構圖、範本與範例 PR。
2. **安排漸進任務**：從小 bug、文件、測試開始，再到完整功能；每個任務說清楚驗收條件。
3. **Code Review 當教學**：解釋「為什麼」而不只是「改成這樣」；用提問引導（「如果這個 API 失敗會怎樣？」）。
4. **結對與分享**：遇到通用問題整理成文件或內部分享，讓知識留在團隊。
5. **給回饋**：定期一對一，具體指出做得好與可改進的地方。

回答時用 STAR 舉一個實例，並講出可衡量的結果（新人多久可以獨立交付、review 往返次數下降）。
:::

### Q9. 說一個你處理過的線上事故 <Badge type="tip" text="高頻" /> {#interview-13-9}

::: details 解題思路
用 **STAR + 根因 + 預防** 結構，重點是展現你的排查方法與學到的教訓，不是事故有多慘。
:::

::: details 標準答案與過程
回答範本：

```txt
S（情境）：什麼系統、影響多少使用者、什麼時候發生
T（任務）：你的角色與目標（先止血、再找根因）
A（行動）：
  1. 怎麼發現（告警、客訴、監控）
  2. 先做了什麼止血（rollback、關 feature flag、擴容）
  3. 怎麼定位（log、traceId、重現步驟、二分法比對版本）
  4. 根因是什麼（技術層面 + 流程層面：為什麼測試沒抓到）
R（結果）：多久恢復、影響範圍
預防：加了什麼測試、告警、CI 檢查、流程調整；寫進 postmortem
```

準備 2～3 個不同類型的故事（效能、資料錯誤、部署失誤），每個 2 分鐘內講完，並能接受追問細節。
:::

### Q10. 和 PM、設計師或後端意見不同時，你怎麼處理？ <Badge type="tip" text="基礎" /> {#interview-13-10}

::: details 標準答案與過程
1. **先理解對方的目標**：問「這個需求要解決什麼問題？」，常常爭的是做法，目標其實一致。
2. **把意見轉成可比較的選項**：列出方案 A／B 的成本、風險、時程、使用者影響，用資料而不是立場說話（Prototype、量測數據、使用者回饋）。
3. **提出替代方案**：「這個效果做完要兩週，用 X 方式一天可以達到八成效果」。
4. **決策後一致執行**：誰有決定權就由誰決定；記錄決策與理由（會議紀錄或 ADR），之後回顧。
5. **需求變更走流程**：評估影響並讓相關人確認，而不是默默加班吞下。
:::

**相關筆記**：[1-22-1 對不同人說話](./1-22-1.md#1-22-1-6)

### Q11. 面試最後，你可以反問什麼？ <Badge type="tip" text="基礎" /> {#interview-13-11}

::: details 標準答案與過程
反問是你評估公司的機會，也展現你在乎什麼：

**團隊與工作**
- 這個職缺目前最急著解決的問題是什麼？入職後 3 個月的期待是什麼？
- 團隊編制？前端與後端、設計、QA 怎麼分工？
- 外包和內部團隊的比例與合作模式？

**工程實務**
- 一個需求從提出到上線的流程？有 Code Review、CI/CD、自動化測試嗎？
- 基礎設施怎麼管理？（有沒有 IaC、環境怎麼同步、部署是自動還人工）
- 技術債怎麼處理？有沒有時間做重構或技術改善？

**成長**
- 資深工程師在這裡的晉升路徑與評估方式？
- 團隊怎麼做技術分享與學習？

避免只問薪資福利（交給 HR 階段），也避免問網路上查得到的資訊。
:::
