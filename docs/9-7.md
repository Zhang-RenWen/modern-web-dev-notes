# 9-7 非同步程式流程

::: info 改寫（2026-11）
整理自《Practical Modern JavaScript》（2017）。原文在回呼、事件、Promise、產生器、async 之間反覆比較；現在的結論很明確：**預設用 async/await**，其他方式各有特定用途。
:::

| 方式 | 現在什麼時候用 |
| --- | --- |
| **async/await** | 預設。一次性的非同步工作、多步驟流程 |
| Promise 組合（`Promise.all`、`allSettled`、`race`、`any`） | 並行多個工作，搭配 `await` 使用 |
| 回呼函式 | 舊 API、效能極度敏感的熱路徑；新程式碼用 `util.promisify` 或自己包成 Promise |
| 事件（`EventTarget`、`EventEmitter`） | **會發生很多次**的事：使用者操作、WebSocket 訊息、進度通知 |
| 迭代器、產生器 | 描述序列（可能無限長），由使用端決定要拿多少 |
| 非同步迭代器 `for await` | 一筆一筆陸續到來的資料：串流、分頁 API、事件流 |
| Observable（RxJS） | 複雜的事件組合：防抖、取消前一個請求、合併多個來源 |

幾個判斷原則：

- **一次性結果用 Promise／async，多次事件用事件或非同步迭代器**。用事件處理一次性結果（例如註冊 `success` 和 `error` 兩個監聽）會讓程式一半在處理監聽的註冊與移除。
- 回呼本身沒有錯，問題是巢狀與錯誤處理分散；三個以上相依的步驟就改成 async/await。
- Promise 比回呼多一點成本（每個 `then` 都建立新物件），對一般應用可以忽略。
- 用產生器實作無限序列比手寫迭代器短很多（見 [4-3](./4-3.md#4-3-3)）。
- 深層巢狀的 Promise 鏈（`then` 裡面又 `then`）是 async/await 最能改善可讀性的地方。
