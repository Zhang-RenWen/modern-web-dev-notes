::: info 新增（2026-11）

> **主線一句話**：框架負責 UI，核心能力保持框架無關；資料有唯一權威來源，轉換最少、修改集中、依賴方向清楚。

## 去框架化 7 原則 {#1-6-11-1}

1. 一個資料來源只建立一個權威儲存點（Single Source of Truth，先回答「這份資料誰擁有？」）。
2. 資料流採**最少必要節點**，不是最短：每多一層都要有明確存在理由（例如隔離 Backend Schema）。
3. API 資料進系統後，只做一次 normalization / mapping。
4. Source Data 與 Derived Data 分離：`statusLabel`、`canEdit` 這類可算出來的值不要變成第二份來源。
5. Read 可以廣，Write 必須集中：UI → Action / Use Case → Store，不讓元件到處直接改 store。
6. Domain Rule（金額門檻、狀態轉換、角色權限）與 Use Case 不依賴 Vue / React。
7. UI interaction（Modal、Tab、Loading、動畫、lifecycle）留在框架層，不為去框架而硬抽。

```txt
UI Framework      Rendering / Lifecycle / UI State
      ↓
Application       Use Case / Action / Workflow
      ↓
Domain            Rules / Validation / Model（framework-free）
      ↓
Infrastructure    API / Storage / Cache / I/O

Transport Model → Normalize → Domain/Store Model → Derived View Data → UI
```

## 專案結構：依業務邊界切，不依技術種類切 {#1-6-11-2}

`components/ hooks/ services/ utils/` 只適合小專案與 Demo；中大型專案用 feature-based：

```txt
src/
  app/        初始化、router、providers
  routes/     路由頁面（入口）
  features/   auth/ user/ order/ dashboard/（各自管理元件、狀態、API）
  entities/   核心資料模型
  shared/     真正跨模組共用：ui/ lib/ api/ hooks/
```

Kubernetes 屬於基礎設施，不是前端 src 結構的一部分；前端是 build 成靜態檔再部署到 Nginx / CDN / Container。

## 狀態先分類，再選工具（Redux 不是預設） {#1-6-11-3}

| 狀態類型 | 常見工具 |
| --- | --- |
| Server State / API 快取 | TanStack Query、SWR、RTK Query |
| 小型全域狀態 | Pinia、Zustand、Context + Reducer |
| 複雜企業級狀態 | Redux Toolkit |
| 表單狀態 | React Hook Form、VeeValidate |
| URL 狀態 | Router search params |
| Dialog 開關等 | Local state |

MVC / MVP / MVVM / VIPER 只當概念圖用：真正要回答的是「誰負責畫面、狀態、資料、流程、業務邏輯」。現代對應大致是 View → Component/Page，ViewModel → Composable/Hook/Store selector，Interactor → Use Case/Domain Service，Coordinator → Router/App Shell。

**面試可用的一句話**：我會先依業務切 features，再把真正跨模組的東西放 shared；狀態先區分 server / client / form / URL，再選工具。

## 能力分級 {#1-6-11-4}

- 中階會**修**問題；資深能**定位、解釋、預防**；Tech Lead / Architect 從架構上**降低問題發生率**。
- 架構分級：初階「做出來」→ 中階「不重複」（Hook/Composable、Service）→ 資深「100 人一起開發會怎樣」（分層、狀態設計、資料流、feature 結構、效能、改一個需求只動一個 Service）→ Lead「前端平台」（Monorepo、Design System、Storybook、CI/CD、Testing）。

## 產品設計觀 {#1-6-11-5}

- 上游決定下游：**Data Model → 資訊架構 IA → User Flow → Component / Product Pattern → Layout → Visual**。上游錯了，CSS 再漂亮也救不了。
- Layout 是排列方式，不是產品設計本身；版型名稱不用背，記用途：F 型給文章與資訊密集頁、Z 型給 Landing、Card 給商品與功能模組、Split 給對比、Masonry 給作品集、固定導覽給長頁與文件站。
- 大型產品主要在組合成熟 Pattern：Dashboard（KPI、Chart、Filter、Table、Alert）、CRM（List、Detail、Timeline）、電商（List、Detail、Cart、Checkout）。
- 用 design token 維持一致：spacing 4/8/12/16/24/32、radius、font-size、button-height；按鈕檢查高度、padding、icon 間距、點擊範圍與 default/hover/active/disabled/loading 五種狀態。
