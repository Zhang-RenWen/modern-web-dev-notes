# 1-6-3 快取政策 {#1-6-3}

::: info 改寫（2026-11）
原內容整理自 2019 年前的書籍（引用《HTTP 權威指南》），已依 RFC 9111 與現在的瀏覽器行為改寫。逐步搭 Koa 專案、套件原始碼逐行解說已刪，改成一個最小範例。修正的過時說法：「F5 會跳過強快取」、用 `<meta>` 控制快取、「大廠不用 ETag」、`must-revalidate` 會強制每次驗證。
:::

> 一句話：**能不發請求就不發（強快取），非發不可就只問「變了沒」（協商快取），內容一變就換網址（檔名 hash）。**

## 快取在哪幾層 {#1-6-3-1}

一個請求依序經過這幾層，任一層命中就不往下走：

| 層 | 誰控制 | 說明 |
| --- | --- | --- |
| bfcache（往返快取） | 瀏覽器 | 上一頁／下一頁時直接還原整個頁面（含 JS 狀態），連 HTTP 快取都不查 |
| Service Worker（Cache Storage） | 你的 JS | 攔截 `fetch` 自己決定回快取或打網路，離線應用靠它 |
| HTTP 快取（memory／disk cache） | 回應標頭 | DevTools 顯示 `(memory cache)` 或 `(disk cache)`；放記憶體還是磁碟由瀏覽器決定，標頭管不到 |
| CDN／Proxy（共享快取） | 回應標頭（`s-maxage`、`private`） | 多個使用者共用；個資回應要標 `private` 或 `no-store` |
| 伺服器 | 後端 | 資料庫快取、Redis 等，不屬於 HTTP 快取 |

::: warning 共用 CDN 的好處已經沒了
Chrome 86（2020）起 HTTP 快取依「頂層網站」分區：A 網站載過的 `cdn.example.com/jquery.js`，B 網站還是要重新下載。以前「用公共 CDN 的函式庫，使用者早就快取過」的理由不再成立，自己打包反而少一次 DNS 和連線。
:::

## 強快取與協商快取 {#1-6-3-2}

| | 強快取（freshness） | 協商快取（validation） |
| --- | --- | --- |
| 標頭 | `Cache-Control: max-age=N`（HTTP/1.0 的 `Expires` 會被 `max-age` 覆蓋） | `ETag` ↔ `If-None-Match`、`Last-Modified` ↔ `If-Modified-Since` |
| 有沒有請求 | 沒有，直接用本地這份 | 有，但沒變時伺服器只回 `304`，不帶 body |
| DevTools | `200 (from disk cache)` | `304 Not Modified` |
| 適合 | 檔名帶 hash、不會變的資源 | HTML、API 這類會變的內容 |

判斷順序：先看快取還新不新鮮；過期了才帶驗證標頭去問。兩種驗證標頭同時存在時，伺服器以 `If-None-Match` 為準（`Last-Modified` 只精確到秒，同一秒內改兩次會判斷錯）。

**沒設 `Cache-Control` 不等於不快取**：只要有 `Last-Modified`，瀏覽器會用「啟發式快取」，自己估一段有效期（常見是距離上次修改時間的 10%）。一年沒改的檔案可能被快取一個多月，這是「明明部署了，使用者還看到舊版」的常見原因，所以每個回應都該明確寫 `Cache-Control`。

## Cache-Control 常用指令 {#1-6-3-3}

| 指令 | 意思 | 常見誤解 |
| --- | --- | --- |
| `max-age=N` | N 秒內新鮮，不發請求 | `max-age=0` 是「立刻過期，每次都要驗證」，不是不快取 |
| `no-cache` | 可以存，但**每次使用前都要驗證** | 名字誤導，它不是「不快取」 |
| `no-store` | 完全不存（含磁碟） | 個資、金額這類敏感回應用它 |
| `must-revalidate` | **過期後**一定要驗證，伺服器連不上就回 504，不能拿舊的頂 | 新鮮期內照樣直接用快取，不會每次驗證 |
| `private`／`public` | 只能存在使用者瀏覽器／CDN 也能存 | 帶 `Authorization` 的回應預設不給共享快取存 |
| `s-maxage=N` | 只給 CDN／Proxy 用的有效期 | 瀏覽器忽略它 |
| `immutable` | 新鮮期內連重新整理都不驗證 | 只在檔名帶 hash 的資源上用 |
| `stale-while-revalidate=N` | 過期後 N 秒內先回舊的，背景再更新 | CDN 普遍支援，瀏覽器支援度依版本確認 |

## 實務設定 {#1-6-3-4}

| 資源 | 設定 | 原因 |
| --- | --- | --- |
| `index.html`（SPA 入口） | `no-cache` + `ETag` | 每次確認拿到最新入口，入口才會引用新版 JS |
| 檔名帶 hash 的 JS／CSS／圖片 | `max-age=31536000, immutable` | 內容一改檔名就變，舊檔名可以快取一年 |
| 不帶 hash 的圖片、字型 | `max-age=86400` + `ETag` | 折衷：一天內不問，過期再驗證 |
| 一般 API | `no-cache` + `ETag`，或 `max-age=短秒數` | 依資料多久會變決定 |
| 個資、交易 API | `private, no-store` | 不能留在磁碟或共享快取 |
| CDN 上的頁面 | `s-maxage=60, stale-while-revalidate=300` | CDN 多快取一段時間，使用者不用等回源 |

- 版本號用**檔名 hash**（Vite、webpack 預設就有），不要用 `?v=1.8.9`：有些 Proxy 不快取帶查詢字串的網址，而且手動改版號容易忘。
- `<meta http-equiv="Cache-Control">` **沒有作用**，瀏覽器的 HTTP 快取只看回應標頭。
- 部署新版時，舊版 `index.html` 可能還在引用已刪掉的 chunk，使用者切頁會 `ChunkLoadError`。保留前一版的資源一段時間，或捕捉錯誤後提示重新整理。

## 重新整理與瀏覽器操作 {#1-6-3-5}

| 操作 | 行為 |
| --- | --- |
| 點連結、網址列按 Enter、開新分頁 | 照標頭走：新鮮就用快取，過期就驗證 |
| 上一頁／下一頁 | 優先用 bfcache；沒有就用 HTTP 快取，**連過期的也可能直接用** |
| 一般重新整理（F5、⌘R） | 主文件一定驗證。子資源：Chrome 照常用快取（2017 年起），Firefox 會送驗證請求；標 `immutable` 的不驗證 |
| 強制重新整理（Ctrl+Shift+R、⌘⇧R、Ctrl+F5） | 跳過快取，所有資源重新下載 |
| DevTools 勾「Disable cache」 | 開著 DevTools 時等同每次強制重新整理，只影響自己 |

## ETag 怎麼產生 {#1-6-3-6}

ETag 只要「內容不同就不同」，產生方式由伺服器決定：

- Node 的 `etag` 套件（Express、Koa 使用）：字串或 Buffer 用 `"長度16進位-SHA1前27字"`；檔案用 `W/"大小-修改時間"`（`W/` 是弱 ETag，代表語意相同、位元組不一定相同）。
- Nginx：`"修改時間-大小"`，兩者都用 16 進位。

多台伺服器的坑：如果 ETag 用修改時間計算，而各台部署時間不同，同一份檔案在不同機器 ETag 不一樣，負載平衡切到別台就驗證失敗、重新下載整份。解法是 ETag 改用內容雜湊、部署時統一檔案時間，或讓靜態資源走檔名 hash 加 `immutable`，根本不需要驗證。早期 Apache 預設把 inode 算進 ETag，才有「大型網站關掉 ETag」的說法，現在已不適用。

## 最小驗證範例（Node.js） {#1-6-3-7}

不需要框架，用 `node:http` 就能看到 `304`。存檔成 `server.mjs`，執行 `node server.mjs`，打開 DevTools 的 Network 重新整理兩次。

```js
import http from 'node:http'
import { createHash } from 'node:crypto'
import { readFile } from 'node:fs/promises'

http.createServer(async (req, res) => {
  const body = await readFile('./index.html')
  const etag = `"${createHash('sha1').update(body).digest('base64url').slice(0, 27)}"`

  res.setHeader('Cache-Control', 'no-cache') // 可以存，但每次都要驗證
  res.setHeader('ETag', etag)

  // If-None-Match 可能是逗號分隔的多個值，也可能帶 W/ 前綴
  const tags = (req.headers['if-none-match'] ?? '').split(',').map((t) => t.trim().replace(/^W\//, ''))
  if (tags.includes(etag) || tags.includes('*')) {
    res.statusCode = 304 // 沒變：不送 body
    return res.end()
  }
  res.setHeader('Content-Type', 'text/html; charset=utf-8')
  res.end(body)
}).listen(3000, () => console.log('http://localhost:3000'))
```

第一次是 `200`，之後都是 `304`；改一下 `index.html` 再重新整理，又會回到 `200`。把 `no-cache` 換成 `max-age=60`，60 秒內重新整理子資源會看到 `(memory cache)`。

## 面試題 {#1-6-3-8}

**怎麼讓瀏覽器不要快取某個資源？**
敏感資料用 `Cache-Control: no-store`。如果只是要「每次拿最新」，用 `no-cache` 加 `ETag` 更好：沒變時只回 304，省流量。靜態資源則用檔名 hash，讓新版本換網址。`<meta>` 標籤和 `Pragma: no-cache` 都不是正解。

**`no-cache`、`max-age=0`、`must-revalidate` 差在哪？**
`no-cache`：每次使用前都驗證。`max-age=0`：立刻過期，所以每次也會驗證，但規格允許在連不上伺服器時用過期的。`must-revalidate`：只管「過期之後」，過期就一定要驗證、不准用舊的；新鮮期內照樣直接用。三者常一起出現：`max-age=0, must-revalidate` ≈ `no-cache`。

**`Cache-Control: max-age=60, must-revalidate` 的效果？**
60 秒內直接用快取，不發請求；超過 60 秒一定要向伺服器驗證，伺服器連不上就回錯誤，不會拿舊的頂。

**強快取和協商快取同時設定，誰先？**
先看強快取：還新鮮就不發請求，根本輪不到 ETag。過期了才帶 `If-None-Match`／`If-Modified-Since` 去問。

**為什麼 ETag 比 Last-Modified 可靠？**
`Last-Modified` 只精確到秒，而且只看時間：內容沒變但檔案被重新產生，時間變了就會白白重新下載。ETag 依內容計算，兩個問題都沒有。
