## Code Review {#1-7-4-1}

- **目的**：在出大包前攔截問題、互相學習、讓知識流通（緊急時能互相 cover）。忙到要犧牲時可以犧牲，平時就把它做好。

1. **別只抓 bug 和 coding style**（避免「腳踏車棚效應」）：style 交給統一標準與工具；人力放在商業邏輯是否真的解決問題、架構是否埋維護地雷、安全（SQL Injection、XSS）、測試是否真的覆蓋。
2. **Review 不是審判**：用「有沒有考慮過 ○○？為什麼沒採用？」；請、謝謝常掛嘴邊。
3. **建議分三級**：Merge Blocker（不改不能 merge）／To Discuss（疑似重大，必須討論）／Minor（改不改都可）。每則留言都要回覆，不改也要說明原因。
4. **讓 PR 作者自己 merge**：反映團隊 ownership 文化（視專案性質）。
5. **不要開大 PR**：拆小，尊重 reviewer 的時間。

- 不是主管也能做：在不破壞的前提下自己先採用，讓好做法擴散。

## Scrum {#1-7-4-2}

- **角色**：PO 彙整每次迭代的真實需求、對轉化率負責而不是對長官負責；Scrum Master 讓團隊維持在 Scrum 狀態；Developer 負責執行。
- 新團隊先用實體便利貼磨合細節，熟了再上線上工具；核心是把可驗證的單位變小、快速迭代。
