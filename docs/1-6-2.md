# 1-6-2 效能最佳化 {#1-6-2}

::: info 改寫（2026-11）
原內容整理自 2019 年前的書籍，已精簡並更新：WebP 不需要再用 JS 偵測支援度（改用 `<picture>`）；雪碧圖在 HTTP/2 之後已不必要；`requestAnimationFrame` 不需要 polyfill；事件委派改用 `closest()`；補上 INP 相關的長任務切割。

## 面試怎麼回答「做過哪些效能最佳化」 {#1-6-2-1}

不要背清單，用一個真實案例講完整的四步：

1. **量測**：用什麼指標發現問題（例如 LCP 3.8 秒、某頁 INP 400ms），在哪些裝置、多少比例的使用者。
2. **找原因**：用 Lighthouse、DevTools Performance、Bundle 分析找到瓶頸（例如首頁圖片 2MB、首屏載入了只有 10% 使用者會點開的影片模組）。
3. **改法與取捨**：做了什麼、為什麼選這個做法、有什麼副作用。
4. **結果**：用數字證明，最好是 A/B 分組（例如 5% 流量對照），以及有沒有出現預料外的狀況、怎麼處理。

先講到策略名稱就好，讓面試官挑有興趣的點追問。指標定義見 [1-6-1](./1-6-1.md)，載入流程的完整最佳化清單見 [1-6-4 網頁效能入門](./1-6-4.md)。

## 常見的專案層級做法 {#1-6-2-2}

| 方向 | 現在的做法 |
| --- | --- |
| 圖片格式 | 用 `<picture>` 讓瀏覽器自己挑：`<source type="image/avif">` → `<source type="image/webp">` → `<img>` 備援。不需要再用 JS 偵測 WebP 支援度 |
| 圖片尺寸 | `srcset` + `sizes` 依螢幕給不同大小；一定要寫 `width`／`height`（或 `aspect-ratio`）避免版面跳動（CLS） |
| 延遲載入 | 畫面外的圖片、iframe 加 `loading="lazy"`；**首屏最大的那張圖不要 lazy**，反而要加 `fetchpriority="high"` 改善 LCP |
| 隨選載入 | 用 `import()` 動態載入：路由層級切分、點了才需要的模組（彈窗、編輯器、圖表）等使用者互動或進入畫面時再載 |
| 預先載入 | `preconnect`（提早連線第三方網域）、`preload`（本頁一定會用到的字型或 LCP 圖片）、`prefetch`（下一頁可能用到的資源） |
| 打包瘦身 | Tree shaking（要用 ES Module 寫法）、檢查是否把整個 lodash、moment 打包進來（換成 lodash-es 按需引入、`Intl`／day.js） |
| 快取 | 檔名帶 hash + 長期快取，見 [1-6-3](./1-6-3.md) |
| 圖示 | 雪碧圖（多張小圖拼一張）是 HTTP/1.1 時代為了減少請求數；HTTP/2 之後改用 SVG 圖示或 icon font，按需引入 |

## 動畫與渲染效能 {#1-6-2-3}

- 動畫只動 `transform` 和 `opacity`，它們在合成層處理，不會觸發重新排版和繪製。
- `will-change: transform` 只加在真的要動的元素上，加太多會吃大量 GPU 記憶體。
- JS 動畫用 `requestAnimationFrame`，它會對齊螢幕更新頻率、背景分頁自動暫停（現在所有瀏覽器都支援，不用 polyfill）。
- 長列表用虛擬捲動，或 CSS `content-visibility: auto` 讓畫面外的區塊延後渲染。

**版面抖動（layout thrashing）**：讀取 `clientHeight`、`offsetTop`、`getBoundingClientRect()` 這類值時，如果前面剛改過樣式，瀏覽器必須立刻重新排版才能給正確的值。讀寫交錯就會連續排版好幾次。

```js
// 不好：讀、寫、讀、寫…每次讀都觸發一次排版
for (const el of els) el.style.height = el.clientHeight * 2 + 'px'

// 好：先全部讀，再全部寫，只排版一次
const heights = els.map((el) => el.clientHeight)
els.forEach((el, i) => { el.style.height = heights[i] * 2 + 'px' })
```

寫入的部分也可以放進 `requestAnimationFrame`，在下一次畫面更新前統一執行。觸發排版的屬性清單與渲染管線見 [1-5-3](./1-5-3.md)。

## 互動效能（INP）：不要讓主執行緒塞住 {#1-6-2-4}

點擊後畫面要等到目前執行中的 JS 跑完才能更新。超過 50ms 的長任務就會讓使用者感覺卡。

```js
async function processAll(items) {
  for (const [i, item] of items.entries()) {
    process(item)
    // 每處理一批就讓出主執行緒，讓瀏覽器先處理點擊和畫面更新
    if (i % 50 === 0) await (globalThis.scheduler?.yield?.() ?? new Promise((r) => setTimeout(r)))
  }
}
```

- `scheduler.yield()` 是 Chrome 129 起的 API，讓出後會優先回到原本的工作；其他瀏覽器用 `setTimeout` 退而求其次。
- 計算量大的工作（解析大檔、影像處理）搬到 Web Worker。

## 事件委派 {#1-6-2-5}

1,000 個 `<li>` 不要各綁一個監聽，綁在父元素上，再判斷點到誰：

```js
list.addEventListener('click', (e) => {
  const li = e.target.closest('li') // 點到 li 裡面的 <span> 也找得到
  if (!li || !list.contains(li)) return
  console.log(li.dataset.id)
})
```

好處是監聽器只有一個、之後新增的 `<li>` 不用再綁。`closest` 比只檢查 `e.target.nodeName` 可靠。

## 防抖與節流 {#1-6-2-6}

兩者都不減少事件觸發次數，而是減少**處理函式的執行次數**：

| | 防抖（debounce） | 節流（throttle） |
| --- | --- | --- |
| 行為 | 停止觸發一段時間後才執行一次 | 固定間隔最多執行一次 |
| 適合 | 搜尋框輸入完才查詢、視窗調整完才重算版面 | 捲動時更新進度、拖曳、無限捲動檢查 |

```js
function debounce(fn, wait) {
  let timer
  return function (...args) {
    clearTimeout(timer)
    timer = setTimeout(() => fn.apply(this, args), wait)
  }
}

function throttle(fn, wait) {
  let last = 0
  return function (...args) {
    const now = Date.now()
    if (now - last >= wait) {
      last = now
      fn.apply(this, args)
    }
  }
}
```

進階需求：`leading`／`trailing`（第一次或最後一次要不要執行）、`cancel()` 取消、`maxWait`（防抖最久等多久）。lodash 的 `debounce`／`throttle` 都有。只是要知道「元素是否進入畫面」時，用 `IntersectionObserver` 取代捲動事件加節流。
