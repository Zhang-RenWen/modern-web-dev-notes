# 1-11-4 WebSocket {#1-11-4}

::: info 改寫（2026-11）
原內容整理自《High Performance Browser Networking》（Ilya Grigorik，2013）第 17 章。已濃縮協定細節（分框、遮罩、擴充），刪掉從未標準化的「多工擴充」；補上實務上真正會遇到的事：心跳、重連、背壓、身分驗證、負載平衡與 Socket.IO 的定位。
:::

> 一句話：**先用一個 HTTP 請求「升級」，之後這條 TCP 連線就變成雙向的訊息通道**，雙方隨時都能送文字或二進位資料。

## API {#1-11-4-1}

```js
const ws = new WebSocket('wss://example.com/chat', ['chat.v1']) // 第二個參數是子協定，可省略
ws.binaryType = 'arraybuffer' // 二進位訊息要 ArrayBuffer 還是 Blob（預設）

ws.onopen = () => ws.send(JSON.stringify({ type: 'join', room: 'a' }))
ws.onmessage = (e) => {
  if (typeof e.data === 'string') handle(JSON.parse(e.data))
  else handleBinary(new Uint8Array(e.data))
}
ws.onclose = (e) => console.log('closed', e.code, e.wasClean)
ws.onerror = () => {} // 只表示出錯，細節看不到；後面一定接著 close

ws.close(1000, 'bye')
```

- 一律用 `wss://`（TLS）：除了安全，也比較不會被中間的代理伺服器擋掉或改壞。
- `send` 不會等對方收到才回傳，資料先進瀏覽器的緩衝區。送大量資料時要看 `ws.bufferedAmount`，太大就先停，避免記憶體爆掉（背壓）。Chromium 的新 API `WebSocketStream` 用 Streams 內建了背壓。
- **子協定**：用戶端列出支援的格式，伺服器選一個回傳（`ws.protocol`），用來做版本協商，例如 `chat.v1`、`graphql-transport-ws`。

## 協定重點 {#1-11-4-2}

**交握**：

```text
GET /chat HTTP/1.1
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13
Origin: https://app.example.com

HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=
```

`Sec-WebSocket-Accept` 是把 Key 加上固定字串後算 SHA-1，證明伺服器真的懂 WebSocket，不是隨便回應的 HTTP 伺服器。之後連線上跑的就不再是 HTTP。

**分框（frame）**：每則訊息切成一個或多個 frame，每個 frame 只有 2～14 位元組的標頭（含類型：文字、二進位、ping、pong、close）。用戶端送出的 frame 一定要經過遮罩（mask），防止惡意網頁利用 WebSocket 污染中間代理伺服器的快取。

**壓縮**：`permessage-deflate` 擴充可以壓縮每則訊息，瀏覽器會自動協商；高頻的小訊息壓縮效益不大，反而耗 CPU。

## 實務上要自己處理的事 {#1-11-4-3}

| 問題 | 做法 |
| --- | --- |
| 斷線 | 斷線後**指數退避重連**（1s、2s、4s…，加上隨機抖動），避免伺服器重啟時所有用戶端同時湧入 |
| 連線看起來還在但其實斷了 | **心跳**：定期送 ping（或自訂的 `{type:'ping'}`），太久沒回應就主動關閉重連；也能避免代理伺服器因閒置切斷連線 |
| 重連後漏掉訊息 | 訊息帶序號，重連時告訴伺服器「最後收到第幾號」，由伺服器補送 |
| 身分驗證 | 瀏覽器的 `WebSocket` 不能自訂標頭。常見做法：同網域靠 Cookie；或先用 `fetch` 拿一次性短效 token，放在網址或連線後的第一則訊息。伺服器要檢查 `Origin`，防止跨站 WebSocket 劫持 |
| 訊息格式 | 自己定義：`{ type, id, payload }`，`type` 決定怎麼處理，`id` 用來對應請求與回應 |
| 背景分頁、手機休眠 | 連線可能被暫停或切斷，回到前景時檢查狀態、必要時重連 |

[Socket.IO](https://socket.io/) 把上面這些都做好了（重連、心跳、房間、確認回覆、連不上時退回長輪詢），但它是**自己的協定**，伺服器也要用 Socket.IO，不能直接接一般的 WebSocket 伺服器。

## 部署與效能 {#1-11-4-4}

- **負載平衡與擴充**：每條連線固定在一台伺服器上。多台伺服器時，要廣播的訊息得透過 Redis Pub/Sub 這類訊息中介傳給其他台；負載平衡器要支援 WebSocket 升級，閒置逾時要設得比心跳間隔長。
- **沒有內建的請求／回應對應**：所有訊息都在同一條通道上，大訊息會擋住後面的小訊息（隊頭阻塞），必要時自己把大檔案切塊，或大檔案改走 HTTP 下載。
- **不經過 HTTP 快取**：能用一般 HTTP 快取的資料（設定、靜態清單）不要放在 WebSocket 裡傳。
- **HTTP/2、HTTP/3 下的 WebSocket**（RFC 8441、9220）可以和其他請求共用連線，但需要伺服器支援，目前多數部署仍是獨立的 HTTP/1.1 升級連線。
- 只需要伺服器單向推送時，[SSE](./1-11-3.md) 更簡單；需要不保證順序、低延遲的傳輸，可以評估 WebTransport。
