## CommonJS 與 ES Modules {#1-23-2-1}

ES5 本身沒有模組系統；Node.js 一開始用的是社群規範 **CommonJS**。ES2015 之後才有標準的 **ES Modules（ESM）**。

```js
// CommonJS
const fs = require('fs')
module.exports = { hello: 'world' }

// ES Modules
import fs from 'node:fs'
export const hello = 'world'
```

Node.js 怎麼判斷一個檔案是哪一種：

| 條件 | 視為 |
| --- | --- |
| 副檔名 `.mjs` | ESM |
| 副檔名 `.cjs` | CommonJS |
| `.js` 且最近的 `package.json` 有 `"type": "module"` | ESM |
| `.js` 且 `"type": "commonjs"` 或沒寫 | 預設 CommonJS（新版 Node.js 若偵測到 `import`／`export` 等 ESM 語法，會改用 ESM 執行） |

ESM 在 Node.js 12 實驗、14 起穩定。新專案建議直接用 ESM，並使用目前的 Active LTS 版本。

## 瀏覽器只認 ES Module {#1-23-2-5}

需要判斷「這個檔案是哪一種模組」的是 Node.js，因為它兩種都支援。**瀏覽器根本不支援 CommonJS**，所以沒有這個問題。

瀏覽器看的是 `script` 標籤怎麼寫：

```html
<script src="a.js"></script>                <!-- 傳統 script -->
<script type="module" src="b.js"></script>  <!-- ES Module -->
```

- 有 `type="module"`：用 ES Module 規則解析，可以用 `import` / `export`。
- 沒有：當作傳統 script，寫 `import` 會直接報語法錯誤。
- 把 CommonJS 程式碼丟進瀏覽器會得到 `require is not defined`，因為瀏覽器沒有 `require` 和 `module.exports`。
- 副檔名對瀏覽器沒有意義，`.mjs` 和 `.js` 都一樣；它只看 `type` 屬性，以及伺服器回傳的 MIME type 是不是 JavaScript。

**那為什麼前端專案可以寫 `require`？** 因為 Webpack、Vite、esbuild 這些打包工具在建置時已經把它轉掉了，瀏覽器收到的是打包後的結果。

## 兩者是誰的標準 {#1-23-2-6}

- **ES Module 是語言標準**：由 TC39 訂在 ECMAScript 規格裡，定義 `import` / `export` 的語法與語意。至於瀏覽器怎麼載入模組（`script type="module"`、模組解析），則由 WHATWG 的 HTML 標準規定。
- **CommonJS 是社群慣例**：2009 年左右由社群提出，因為當時 JavaScript 沒有模組系統，後來被 Node.js 採用而普及。它不是 ECMAScript 標準，也不是瀏覽器標準，實務上是 Node.js 生態系的事實標準。

所以不是「瀏覽器用 ESM、Node.js 用 CommonJS」的二分法：ESM 是 JavaScript 語言本身的標準，瀏覽器和 Node.js 都是實作它的環境。

::: tip 面試回答
ESM 是 ECMAScript 的官方標準，瀏覽器透過 `type="module"` 辨識。CommonJS 是 Node.js 生態的社群規範，瀏覽器不支援，要靠打包工具轉換。Node.js 兩者都支援，依副檔名與 `package.json` 的 `type` 判斷。
:::

## ESM 的注意事項 {#1-23-2-2}

1. ESM 裡沒有 `__dirname`、`__filename`：

```js
import { dirname } from 'node:path'
import { fileURLToPath } from 'node:url'

const __filename = fileURLToPath(import.meta.url)
const __dirname = dirname(__filename)
// Node.js 20.11+ 可以直接用 import.meta.dirname / import.meta.filename
```

2. 相對路徑匯入要寫完整副檔名：`import { x } from './utils.js'`（TypeScript 編譯前也寫 `.js`）。
3. **互相載入**：ESM 可以直接 `import` CommonJS；Node.js 22.12+ 與 20.19+ 起，CommonJS 預設也能 `require()` 同步的 ESM（模組內不能有頂層 await）。
4. ESM 支援頂層 await，CommonJS 不支援。

## NestJS 改用 ESM {#1-23-2-3}

NestJS 預設輸出 CommonJS，而且很穩定；除非要整合只提供 ESM 的套件或和前端工具鏈一致，否則不必改。要改的話：

1. `tsconfig.json`：`"module"` 與 `"moduleResolution"` 設成 `"NodeNext"`（或 `"node16"`），`target` 至少 ES2020。
2. `package.json` 加 `"type": "module"`。
3. 所有相對匯入補上 `.js` 副檔名；`main.ts` 可以用頂層 await 啟動。
4. 開發時用支援 ESM 的執行器（例如 `tsx`）。

## AMD、UMD、IIFE 還有人用嗎 {#1-23-2-4}

| 格式 | 狀態 |
| --- | --- |
| **ESM** | 標準，瀏覽器與 Node.js 原生支援，打包工具能靜態分析與 Tree Shaking |
| **CommonJS** | Node.js 傳統格式，大量 npm 套件仍在用 |
| **UMD** | 同時相容 CommonJS、AMD、全域變數，舊時代發布函式庫用，逐漸減少 |
| **IIFE** | 不算模組系統，用於直接用 `script` 標籤嵌入的簡單腳本 |
| **AMD**（RequireJS 的 `define()`） | 已淘汰：語法繁瑣、瀏覽器不原生支援、無法靜態分析。只會出現在 2010 年代初期的舊專案或老 jQuery 外掛，看到就代表需要升級 |
