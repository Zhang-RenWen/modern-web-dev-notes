## 五條底層原則 {#1-19-3-1}

1. **後端才是法官，前端只是 UX**：任何前端遮罩、禁用按鈕、防 F12 都只是防呆，不是防禦。
2. **假設 token 一定會被偷**：所以要短效、可撤銷、可輪替、可審計。
3. **不要自己發明密碼學**：亂數、雜湊、簽章一律用平台 API。
4. **能看 ≠ 能拿**：原文只在必要瞬間、最少地方出現，且可追蹤、可失效。
5. **最弱的環節常常是人**：社交工程、單一維護者、疲勞的審查者。

## XZ Utils 後門（CVE-2024-3094）— 供應鏈攻擊 {#1-19-3-2}

- **經過**：攻擊者「Jia Tan」花約 2.5 年，先用多個分身帳號施壓疲憊的單人維護者 Lasse Collin，再以熱心貢獻者身分接手維護權，把 payload 藏在「沒人會讀」的測試用二進位檔，透過 build script 在建置時注入 liblzma。
- **技術手法**：利用 IFUNC resolver 提早執行程式碼 + 動態連結器 audit hook，在 GOT 被填入真正位址後、設為唯讀前的窗口，把 OpenSSH 的 RSA 驗證函式換成自己的；只對持有攻擊者私鑰的連線放行，並清除 log。
- **怎麼被發現**：Microsoft 工程師 Andres Freund 測 Postgres 時發現 SSH 登入慢約 0.5 秒 + Valgrind 報錯，一路追到 xz。混淆做太多反而造成效能異常。
- **可帶走的教訓**：
  - 依賴鏈的安全 = 最弱依賴的安全；被嚴格審查的專案（OpenSSH）可以從不被審查的依賴（xz）被攻破。
  - Release tarball ≠ Git 原始碼；**可重現建置（reproducible build）** 與 SBOM 才能比對差異。
  - 測試二進位檔、build script、自動產生的檔案都是盲區。
  - 維護權移交、安全聯絡窗口變更，是高風險事件，應被監控。
  - 效能異常也是資安訊號，不要直接當 bug 丟回給上游。
  - 開源讓這件事「能被發現並公開檢討」；閉源不見得更安全。
- 來源影片：[Veritasium - The Internet Was Weeks Away From Disaster](https://www.youtube.com/watch?v=aoag03mSuXQ)

## 自架伺服器資安翻車（他人經驗） {#1-19-3-3}

- 問題：主機 IP 暴露、Cloudflare 只做轉址（源站仍可被直連）、SSH 用密碼登入、無防火牆、無 fail2ban。
- 補強：Cloudflare Tunnel（源站不開對外 port）、SSH 只允許金鑰 + 關閉密碼登入與 root 登入、防火牆預設拒絕、fail2ban 擋暴力嘗試。
- 補充：改 SSH port 只能減少掃描噪音，不算安全措施；真正有效的是金鑰登入 + 防火牆白名單。

## 591 租屋網防 DevTools（disable-devtool） {#1-19-3-4}

- 591 開 DevTools 會自動跳回上一頁，用的是開源專案 disable-devtool，跑 userscript 即可繞過。
- 教訓：**Client 端反爬 / 反逆向只能擋新手**。真正的防爬要在伺服器端：認證、速率限制、Bot 偵測（如 Cloudflare）、TLS 指紋（JA3/JA4）等。
- 中國 Web/APK 常見混淆（CSS class hash、JS 魔改、token 怪異編碼）同理：增加成本，不能取代後端驗證。

## 照片 EXIF 洩漏位置 {#1-19-3-5}

- 手機照片可能含 GPS 座標，精準到門牌。
- **會出事**：Email 附件、AirDrop、雲端分享、通訊軟體「原檔傳送」、拍賣/租屋社團的原檔。
- **通常不會**：IG、Threads、FB、LINE 一般上傳會清除位置資訊。
- 關閉：iPhone 設定 → 隱私權與安全性 → 定位服務 → 相機 → 永不；Android 相機設定 → 關閉位置資訊。舊照片可在 iPhone 相片的「調整」移除位置。
- 工程面延伸：自家系統收使用者上傳圖片時，應在伺服器端剝除 EXIF。

## 家用網路被殭屍網路 DDoS（2026-10 脆友親身經驗） {#1-19-3-6}

- **症狀**：家裡網路突然超慢；過濾路由器紀錄，發現大量中國 IP 直接打家裡的公網 IP。
- 來源：https://www.threads.com/share/D_r2dNffT/

### 處置流程（照實際順序）

| #   | 做了什麼                                         | 結果                                | 為什麼                                                                                                                                |
| --- | ------------------------------------------------ | ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | 攔截網址                                         | 無效                                | 對方直接打 IP，封包裡沒有網址可以比對                                                                                                 |
| 2   | 路由器 Geo-IP 封鎖中國網段                       | 區網恢復；對外仍慢，路由器 CPU 100% | 封包在路由器就丟掉，不用再 NAT 轉送、內網 Server 也不用回應；但每個進來的封包都要比對大量網段，CPU 被吃滿，攻擊流量也照樣佔用對外頻寬 |
| 3   | Domain 的 DNS 搬到 Cloudflare                    | 等約 1 小時生效後又被打             | 沒在 DNS 層擋中國查詢，殭屍網路重新解析 domain 就又拿到 IP                                                                            |
| 4   | 封鎖中國區的 DNS 查詢                            | 新的查詢拿不到 IP                   | 但已曝光的 IP 還是會被打                                                                                                              |
| 5   | 中華電信重撥換浮動 IP + Cloudflare DDNS 更新記錄 | 終於甩開                            | 攻擊者手上的 IP 失效，新 IP 又查不到                                                                                                  |

### 原理解析

- **攻擊者盯的是 domain，不是 IP**：殭屍網路會定期重新解析，記錄指到哪就打到哪。所以「藏 IP」和「換 IP」要一起做，而且**先藏再換**；先換卻沒藏，新 IP 很快又曝光（步驟 3 就是這樣）。
- **在哪一層擋，決定誰付成本**：
  - 自家路由器擋：流量已經到你家線路上，頻寬照樣被吃，家用路由器 CPU 也扛不住大量規則比對。
  - 上游擋（Cloudflare 等）：流量在對方的邊緣節點就被吸收，你的線路與設備不受影響。
  - 原則：**DDoS 要在流量抵達自己之前擋；自己的設備只能處理「已經進門」的流量。**
- **為什麼連區網都變慢**：每個打進來的連線，路由器都要查轉發規則、記錄連線狀態（conntrack）、NAT 轉給內網 Server，Server 回應再轉一次；量一大，連線表與 CPU 塞滿，內網流量也被拖累。Geo-IP 在入口直接丟包，省掉了這整段。
- **網址攔截 vs IP 攔截**：網址只存在於 HTTP 的 Host 或 TLS 的 SNI 裡；直接打 IP、或非 HTTP 的封包沒有網址可比對。
- **浮動 IP + DDNS**：浮動 IP 是家用網路免費的「換門牌」；DDNS 讓 domain 自動跟著新 IP 走，不用手動改記錄。

### 下次可以直接這樣做（更穩）

- Cloudflare 記錄開 **Proxy（橘色雲）**：DNS 回傳的是 Cloudflare 的 IP，源站 IP 不會出現在查詢結果，比按地區擋 DNS 查詢更可靠。
- ⚠️ 按地區擋 DNS 查詢可被繞過：權威 DNS 看到的是遞迴解析器的位置，殭屍網路改用海外公共 DNS 或 VPS 就能查到。
- 用 WAF 國家規則擋中國（作用在經過 Proxy 的 HTTP 流量）。
- 源站只允許 Cloudflare IP 段連入，或改用 Cloudflare Tunnel 完全不開對外 port（見上方〈自架伺服器資安翻車〉）。
- 換 IP 後，新 IP 不要出現在任何沒 Proxy 的記錄（MX、子網域、舊 A 記錄）；DNS 歷史查詢網站會保留舊記錄。
- 不需要的 port forwarding 直接關掉；路由器不要長期扛大量 Geo-IP 規則。

### 可帶走的教訓

- 先看紀錄再動手：知道是誰、打哪裡，才知道該在哪一層擋。
- 每做一步都問：**攻擊者下一步怎麼重新找到我？**
- 處置順序本身就是設計：**藏（Proxy / 擋查詢）→ 擋（上游 WAF）→ 換（新 IP）**。

## 資安職涯方向 {#1-19-3-7}

- 「資安紅海」主要指低門檻職位：只看 SIEM 報表的 SOC 初階、腳本式滲透、只有入門證照。
- 相對缺人的方向：**雲端資安**（IAM、零信任、K8s）、**資安架構**、**高階紅隊**、**GRC 合規**（ISO 27001 等）、**AI 資安**（prompt injection、資料投毒）。
- 驅動力是法規與攻擊面擴大（AI、IoT、雲端），且事故當下的風險取捨需要人負責。
- 軟體開發背景轉資安的優勢：懂系統怎麼被做出來，就更懂哪裡會出問題；[1-19-4](./1-19-4.md) 到 [1-19-6](./1-19-6.md) 都是開發者轉安全最直接的切入點。
