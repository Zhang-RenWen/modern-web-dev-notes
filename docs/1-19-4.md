## 隨機數：Unique ≠ Random ≠ Unpredictable {#1-19-4-1}

| 類型 | 本質 | 用途 |
| --- | --- | --- |
| **PRNG** | Seed + 確定性演算法，知道狀態就能重播 | 遊戲、模擬、動畫（如 `Math.random()`） |
| **CSPRNG** | OS 收集熵後播種的密碼學安全生成器 | Token、Key、Nonce、OAuth state、CSRF token |
| **TRNG** | 物理噪音 | OS / 硬體的熵來源，應用程式通常不直接碰 |

- 安全 API：瀏覽器 `crypto.getRandomValues()`、Node `crypto.randomBytes()`、Java `SecureRandom`、Go `crypto/rand`。
- **禁止**用 `userId + timestamp` 之類自己湊 seed 或 token：攻擊者能大幅縮小搜尋空間。
- Entropy 看的是「攻擊者面對多少不確定性」，不是字串長度。安全 token 至少 128-bit entropy。
- UUID：v4 若由 CSPRNG 產生勉強可用，但 v1/v7 含時間戳，**不能當安全 token**；需要不可猜就直接用 CSPRNG。
- 先問安全性質再選工具：要唯一？不可預測？保密？不可重複（nonce）？

## JWT 與 Token 儲存 {#1-19-4-2}

- JWT = `header.payload.signature`。Payload 只是 Base64URL 編碼，**任何人都看得到**，不要放敏感資料。
- Signature 是「防竄改」不是「加密」；由 **server** 簽發，client 不持有簽章金鑰。
- JWT 能證明「是我簽的、沒被改、沒過期」，**不能**防止被偷、XSS、CSRF、權限設計錯誤。
- 驗證必做：固定允許的 `alg`（拒絕 `none` 與演算法混用）、檢查 `exp` / `iss` / `aud`。
- 儲存策略：
  - localStorage / sessionStorage：JS 可讀，怕 XSS；**不放 refresh token**。
  - HttpOnly + Secure + SameSite Cookie：JS 讀不到，但會自動附帶，需搭配 CSRF 防護。
  - **推薦**：Access token 放 memory、短效；Refresh token 放 HttpOnly Cookie + rotation。
  - 高安全需求（金融、醫療）：**BFF pattern**，瀏覽器只拿 session cookie，真正 token 留在後端。
- 「JWT 完全無狀態」在成熟系統常不成立：要強制登出、撤銷、多裝置管理，仍需 server 端 session/refresh token 表。
