## 選擇比努力重要 {#1-24-2-1}

最怕的不是累，而是**錢少、又累、又無法累積技術**。入職前先評估產業與公司的開發流程：有沒有 Code Review、測試、CI/CD？技術決策由誰做？做的東西能不能說得出來？

## 雷職缺：一個人扛整間公司 {#1-24-2-2}

例：職缺要求前端（Vue 2／3、TypeScript）＋後端（Node.js／Express）＋實體與雲端主機架設＋PostgreSQL／MySQL＋AWS EC2／ELB／API Gateway／CloudFront，再加上「靈活的創業家精神」「能獨立完成 MVP 系統開發與建置」。

訊號：**職責範圍等於整個技術團隊**、用「創業精神」包裝無限責任。就算月薪很高，一個人也很難做好。

## 救火案、多層外包怎麼判斷 {#1-24-2-3}

危險訊號：

- 前一任已離職或被換掉，而且沒有完整交接。
- 需求已經延誤，但上線日期不動。
- 只告訴你技術棧，不肯說目前完成度與問題。
- 要你「馬上到位」「進去就能做」。
- 業主、主承商、轉包商之間權責不清。
- 要你負責把問題修好，卻沒有權限改架構或重新估時。
- 要你同時扛前端、需求分析、測試、部署與跨部門溝通。

每多一層轉包，問題就多一層：需求被轉述而失真、真正的決策者離你很遠、每層都抽成、出事時互相推責、合約責任與實際管理關係不一致。最後系統救回來，功勞屬於承包公司；專案延誤或出錯，現場工程師最容易被究責。

**真正傷職涯的是：承擔大量責任，卻拿不到決策權、可展示的成果和能力成長。**這類案子常常只累積維修經驗（修既有 bug、配合臨時需求、跨廠商溝通、趕不合理時程），履歷上只能寫「維護某銀行專案」，卻說不清楚系統內容；也容易把你的市場定位鎖回「派遣人力」。救火案還會吃掉最重要的資源：下班後的時間與精神。

如果還是要接，先談清楚：
- 薪資要有風險溢價。
- 職責邊界寫清楚，不替既有技術債背無限責任。
- 資訊不足時，上線時程不能由你承諾。
- 最好能取得整理架構、做技術決策或帶人的權限。

## 台灣商用客製化系統的開發生態 {#1-24-2-4}

**定義**：以承接客製化商業系統專案為主的公司，通常深耕特定領域（醫療、金融、ERP、HR、POS、公文、資安、網管），做 ERP 的不會去接銀行交易，反之亦然。對領域商業邏輯的了解有時比甲方窗口還深；大多依過去經驗開發、依客戶需要微調，或因應新法規開發新功能，很少處理非預期的技術問題。

**職務結構**：

```txt
PG（programmer）→ SD（system designer）→ SA（system analyst）→ PM（project manager）→ 業務
```

- SA 常跟甲方承辦與關鍵人員接觸，整理需求寫成規格書；SD（有時就是 PG lead）寫技術規格（這段常被跳過）；PG 依規格實作，規格資訊不足時只能自己推敲。
- 案子的主導者通常是 PM，PM 有時也兼業務；就算不是，業務常常是講話最大聲的人，視獎金分配制度而定。
- 小團隊或小型專案常是 PM 直接對 PG 的「一條龍」模式。
- 過去多半到客戶端駐點開發，現在比較有機會遠端，但仍常要跑客戶那邊。

**薪資與發展**：大致是軟體相關工作中的低標，年薪成長幅度有限，除非轉向業務或管理；而管理職通常也需要業務能力。這個生態的重點是**如期交付驗收**：要嘛搞定系統，要嘛搞定甲方承辦。

**生存建議**：跟對主管、加入健康的團隊很重要。PM 一開始沒把範疇定好、讓甲方有錯誤預期，後面技術團隊再強也難救。專案無法結案通常不是技術問題，而是人和政治問題（見 [1-24-4 需求訪談與範疇控制](./1-24-4.md)）。

## 職涯經驗法則 {#1-24-2-5}

- **頭銜帶不走，經驗帶得走**：老闆不加薪時，至少爭取更多職責與能累積經驗的機會。
- **每年更新一次履歷**：這是寫給自己的年終總結；一年下來沒東西可寫，就是該改變的訊號。
- **估時要留緩衝**：3 人日的工作估 5 人日，不熟的部分另加調查時間。熬夜提早做完，主管只會認為這就是你的正常速度。
- **新知識學到夠完成任務就好**：除非有興趣或確定長期會用到。
- **技術棧比你想的短命**：可以熱愛技術，但不要愛上某個技術。
- **用查 bug 的態度看販賣焦慮的內容**：追到原始數據，通常邏輯漏洞一堆。
- **法律紅線**：商用前先看開源授權（GPL 的傳染性）；爬蟲不要打爆對方網站；和公司有糾紛走勞動調解或仲裁，不要刪資料庫。
- **不要一直證明自己懂很多，要累積看得見的完成品**：持續運作的服務、公開 Demo、架構 case study，比任何自我描述都有說服力。

## 開源貢獻路徑 {#1-24-2-6}

**文件、型別定義 → 小 bug → 小功能**。先在 issue 留言認領、一個 PR 只做一件事、AI 產生的內容自己驗證過再送。累積 2～3 個被合併的 PR 就能寫進履歷。挑專案的方法見 [1-17-4](./1-17-4.md#1-17-4-6)，評估開源專案的治理見 [1-22-3](./1-22-3.md#1-22-3-3)。
