# 1-12-1 資安實作建議 {#1-12-1}

::: info 改寫（2026-11）

> 一句話：**前端的檢查都只是體驗，真正的防線在後端**；前端要做的是不洩漏、不執行不該執行的東西、不讓自己變成攻擊的跳板。

## 前後端分離的驗證流程 {#1-12-1-1}

1. 使用者登入，後端驗證後發給憑證（Session Cookie 或 token）。
2. 之後每個請求帶上憑證，**後端每次都要驗證身分與權限**（401：還沒登入或憑證失效；403：登入了但沒有權限）。
3. 前端依回應渲染畫面；遇到 401 導向登入頁。

前端的路由守衛、隱藏按鈕只是讓使用者不會走錯路，有心人直接呼叫 API 就繞過了。憑證存哪裡、怎麼防 XSS 與 CSRF 見 [1-12-3](./1-12-3.md#1-12-3-2) 與 [1-12-4](./1-12-4.md)。

## 基本守則 {#1-12-1-2}

| 守則 | 原因 |
| --- | --- |
| 全站 HTTPS，加上 HSTS | 防止中間人竊聽或竄改；HSTS 讓瀏覽器以後只走 HTTPS |
| **敏感資料不放在網址** | 網址會留在伺服器 log、瀏覽器歷史、`Referer` 標頭、分析工具裡。token、密碼、身分證號放在請求 body 或標頭 |
| 登入、驗證碼這類端點要限流 | 防暴力破解：同帳號、同 IP 短時間內失敗太多次就延遲或鎖定，搭配 CAPTCHA |
| 錯誤訊息不透露細節 | 登入失敗統一說「帳號或密碼錯誤」；不回傳堆疊、SQL 錯誤；移除 `X-Powered-By` 這類洩漏框架版本的標頭 |
| 輸出時跳脫，不要信任任何輸入 | 防 XSS：框架預設會跳脫，危險的是 `innerHTML`、`v-html`、`dangerouslySetInnerHTML`，非用不可時先用 DOMPurify 清理 |
| 設定安全標頭 | CSP、`X-Content-Type-Options`、`frame-ancestors` 等，見 [1-12-2](./1-12-2.md) |
| 前端不放任何密鑰 | 打包進 JS 的東西所有人都看得到；第三方 API 金鑰要經過自己的後端代理 |

Node.js 後端可以用 [helmet](https://helmetjs.github.io/) 一次設定好常見的安全標頭：`app.use(helmet())`。

## 依賴套件的安全 {#1-12-1-3}

現代專案大部分程式碼來自第三方套件，套件出問題，你的網站就出問題。

- **提交 lockfile**，CI 用 `npm ci`／`pnpm install --frozen-lockfile`，確保裝到的版本和測試過的一致。
- **自動升級**：Dependabot 或 Renovate 自動開 PR 升級，搭配測試；`npm audit`／`pnpm audit` 列出已知漏洞，`npm audit fix` 在相容範圍內升級。
- **供應鏈攻擊**：曾有熱門套件的維護者帳號被盜、植入惡意版本。降低風險的做法：新版本發佈後等幾天再升級（Renovate 的 `minimumReleaseAge`）、停用不必要的安裝腳本（`ignore-scripts`）、少引入只有幾行功能的小套件、檢查套件的發佈來源（npm provenance）。
- **第三方腳本**（分析、客服、廣告）在你的網頁上擁有和你一樣的權限。只載入必要的，用 CSP 限制來源，固定版本的 CDN 檔案加上 SRI（`integrity` 屬性）。
