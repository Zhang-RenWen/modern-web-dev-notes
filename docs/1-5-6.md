# 1-5-6 同源政策與 CORS {#1-5-6}

::: info 新增（2026-11）
整理自 Notion「同源政策與跨來源資源共用 Same-Origin Policy / CORS」。規範在 WHATWG Fetch Standard。
:::

**同源政策 Same-Origin Policy** 是瀏覽器最基本的安全模型：A 網站的 JS 不能隨便讀 B 網站的資料。**CORS（Cross-Origin Resource Sharing）**是在這個限制上開的合法門：由**伺服器**用回應標頭告訴瀏覽器「哪些來源可以讀我」。

::: tip 最常被誤會的一點
**CORS 是瀏覽器在執行的，不是伺服器在擋**。簡單請求其實已經送到伺服器、伺服器也回應了，只是瀏覽器發現回應沒帶允許的標頭，**不讓 JS 讀取**。所以 Postman、curl、後端呼叫後端都不會遇到 CORS 錯誤。
:::

## 什麼叫同源 {#1-5-6-1}

**Origin = 協定（scheme）+ 主機（host）+ 埠（port）**，三個都一樣才算同源。以 `https://app.example.com` 為基準：

| 網址 | 同源嗎 | 原因 |
| --- | --- | --- |
| `https://app.example.com/users` | ✅ | 只有路徑不同 |
| `http://app.example.com` | ❌ | 協定不同 |
| `https://api.example.com` | ❌ | 主機不同（子網域也算不同） |
| `https://app.example.com:8443` | ❌ | Port 不同（https 預設 443） |
| `http://localhost:5173` → `http://localhost:3000` | ❌ | 本機開發最常撞到：前後端 Port 不同 |

**同源（Origin）≠ 同站（Site）**：Site 只看協定 + 可註冊網域（eTLD+1），`app.example.com` 和 `api.example.com` 是**同站但不同源**。CORS 看 Origin，Cookie 的 SameSite 看 Site。

## 同源政策限制什麼、不限制什麼 {#1-5-6-2}

| 被限制（跨源時） | 不被限制 |
| --- | --- |
| JS 用 `fetch`／`XMLHttpRequest` **讀取**回應 | `<img>`、`<script>`、`<link>`、`<video>`、`<iframe>` 載入跨源資源 |
| JS 存取跨源 iframe 的 DOM | `<form>` 送出到跨源網址 |
| 讀取跨源的 localStorage、IndexedDB、Cookie | 跳轉、開新視窗 |
| `<canvas>` 畫了跨源圖片後讀像素 |  |

右欄「可以送出但讀不到結果」正是 **CSRF 攻擊**能存在的原因，所以 CORS 不能取代 CSRF 防護。

## 兩種跨源請求 {#1-5-6-3}

### 簡單請求（Simple Request）

同時符合以下條件，直接送出，瀏覽器看回應決定給不給讀：

- Method 是 `GET`、`HEAD`、`POST`。
- 只帶瀏覽器允許的標頭（`Accept`、`Accept-Language`、`Content-Language`、`Content-Type` 等）。
- `Content-Type` 只能是 `application/x-www-form-urlencoded`、`multipart/form-data`、`text/plain`。

### 預檢請求（Preflight）

不符合上面任一條件（例如 `PUT`／`DELETE`、`Content-Type: application/json`、帶 `Authorization` 標頭），瀏覽器會**先自動送一個 OPTIONS** 問伺服器，通過才送正式請求：

```txt
瀏覽器 ── OPTIONS /api/users ─────────────────────▶ 伺服器
         Origin: https://app.example.com
         Access-Control-Request-Method: PUT
         Access-Control-Request-Headers: content-type, authorization

瀏覽器 ◀──────────────────────────── 204 No Content ──
         Access-Control-Allow-Origin: https://app.example.com
         Access-Control-Allow-Methods: GET, POST, PUT, DELETE
         Access-Control-Allow-Headers: content-type, authorization
         Access-Control-Max-Age: 600

瀏覽器 ── PUT /api/users（正式請求）──────────────▶ 伺服器
```

前端呼叫 JSON API 幾乎都會觸發預檢，所以 DevTools Network 常看到每個 API 前面多一個 OPTIONS。

## 伺服器要回的標頭 {#1-5-6-4}

| 標頭 | 作用 |
| --- | --- |
| `Access-Control-Allow-Origin` | 允許的來源：單一 Origin 或 `*`（不能列多個；要多個就由伺服器依請求動態回，並加 `Vary: Origin`） |
| `Access-Control-Allow-Methods` | 預檢用：允許的 Method |
| `Access-Control-Allow-Headers` | 預檢用：允許的自訂標頭 |
| `Access-Control-Allow-Credentials: true` | 允許帶 Cookie／認證資訊 |
| `Access-Control-Max-Age` | 預檢結果可快取幾秒，減少 OPTIONS 次數（瀏覽器各有上限） |
| `Access-Control-Expose-Headers` | 讓 JS 讀得到額外的回應標頭（預設只能讀少數幾個，如 `Content-Type`） |

## 帶 Cookie 的跨源請求 {#1-5-6-5}

跨源請求**預設不帶 Cookie**，要兩邊都設定：

```js
// 前端
fetch('https://api.example.com/me', { credentials: 'include' })
// axios
axios.get('https://api.example.com/me', { withCredentials: true })
```

伺服器必須回 `Access-Control-Allow-Credentials: true`，而且 `Access-Control-Allow-Origin` **不能是 `*`**，要寫明確的 Origin。Cookie 本身還要符合 SameSite 規則（見 JWT 登入一頁）。

## 常見錯誤與解法 {#1-5-6-6}

| Console 錯誤大意 | 原因 | 解法 |
| --- | --- | --- |
| No 'Access-Control-Allow-Origin' header | 伺服器沒回 CORS 標頭 | 後端加上允許的 Origin |
| Response to preflight request doesn't pass | OPTIONS 沒處理、回了 401／404／302 | 讓 OPTIONS 不經過登入驗證並回 2xx |
| Request header field authorization is not allowed | 自訂標頭沒列在 Allow-Headers | 加到 `Access-Control-Allow-Headers` |
| wildcard '\*' cannot be used when credentials mode is 'include' | 帶 Cookie 又用 `*` | 改成明確的 Origin |
| Redirect is not allowed for a preflight request | 預檢被轉址（如 http → https、少了結尾 `/`） | 直接打最終網址 |

## 解決 CORS 的幾種方式 {#1-5-6-7}

| 做法 | 說明 | 適合 |
| --- | --- | --- |
| 後端設定 CORS 標頭 | Express `cors` 套件、Spring `@CrossOrigin`／`CorsConfiguration`、Nginx `add_header`、API Gateway 的 CORS 設定 | 正式做法 |
| 開發代理 | Vite `server.proxy`、webpack devServer proxy：瀏覽器打同源的 `/api`，由 dev server 轉發 | 本機開發 |
| 同網域反向代理 | 正式環境用 Nginx／ALB／CloudFront 把 `/api/*` 轉給後端，前後端同源，根本沒有跨源 | 最乾淨，也省掉預檢 |
| JSONP | 利用 `<script>` 不受限制，只能 GET | 舊做法，不建議 |

代理能「解決」CORS，正好證明 CORS 只存在於瀏覽器：伺服器對伺服器沒有這層限制。

## 實戰筆記 {#1-5-6-8}

- SPA 優先打同源的 `/api/*`，由 CDN 或代理轉給後端，就完全不需要 CORS，同時也簡化 Cookie、CSP、callback、WAF 的設定。Cookie 的 Domain 限制在實際的 host，不要隨手設成 `.example.com`。
- WebSocket 不受 CORS 保護，後端要自己做 Origin allowlist。proxy 改了 Host、但 Origin 沒變時，Spring 的同源檢查會回 403，要設精確的 `allowedOrigins`（不要用 `*`）。用 curl 測試時沒帶 Origin 會得到假的成功。
- 反向代理、CORS、WebSocket 的 Origin 檢查、HTTPS 是四件不同的事，也都不能代替授權。不要用「允許所有 Origin」來掩蓋根因。

## 面試常見問法 {#1-5-6-9}

- **什麼是同源？** → scheme + host + port 都相同。
- **CORS 錯誤時，請求有送到伺服器嗎？** → 簡單請求有，只是 JS 讀不到；需要預檢的請求，預檢失敗就不會送正式請求。
- **什麼情況會觸發預檢？** → 非 GET／HEAD／POST、自訂標頭、JSON Content-Type。
- **CORS 能防 CSRF 嗎？** → 不能；CSRF 用表單送出，不需要讀回應。
