## 為什麼 DB 最重要 {#1-22-4-1}

前端、API、框架、服務切分都能重構；**Schema + production 歷史資料最難改**。好的後端要能回答：資料 5–10 年後還能不能被理解、修改、追蹤與遷移。

## 建模原則 {#1-22-4-2}

- 流程：**現實世界 → Entity → Relationship → Constraint → Lifecycle → Schema**；訂單不只 User→Order→Product，還有 Payment、Refund、Shipment、Status History。
- **核心資料保持穩定，變動資料向外拆**：
  - `member`：id、name、email、phone、status、時間戳
  - `member_profile`：生日、地址、職業、頭像
  - `member_setting`：語系、時區、通知、行銷同意
  - `member_verification`：email/phone 驗證時間、KYC 等級
  - 行為資料：`login_history`、`orders`、`activity_log`、`event_log`
- 分類規則：高穩定高頻強一致 → 核心表；可選低頻易增加 → 擴充表；一對多多值 → 獨立表；歷史與行為 → history / audit / event log。
- **先想查詢模式再設計 Index / Partition / Cache**；資料邊界清楚之後才決定 Service、API、要不要 BFF 或微服務。

## 歷史與資料保護 {#1-22-4-3}

- **Audit Log**：誰、何時、哪筆、從什麼值改成什麼值。可協助還原，但 **Audit Log ≠ Backup**（同庫損毀會一起消失）。
- **Soft Delete**：`deleted_at`，防誤刪、保關聯、利稽核。
- **Backup**：每日完整 + 增量 + 異地；重要系統加 Point-in-Time Recovery。
- **Ledger / Event**：重要數字不只存結果（`balance = 10000`），也存事件（+5000、-1000…）；Event Sourcing 複雜度高，不必全面使用。
- **Temporal Data**：`effective_from / effective_to / changed_by / reason`——要能回答「以前長什麼樣、為什麼變、能不能還原」。
- 最低配：核心表 + created/updated_at + soft delete + audit log + backup。

## 案例：壽險地址 Legacy Data {#1-22-4-4}

早期只要「能印信封」，地址塞成一個字串（台北市 / 臺北市 / 台北巿 混用）；二三十年後要做 MDM、去重、地理風險分析才全部爆出來。正確現代化方式：**原始資料保留**，另建 Parser / Normalizer 產生 `raw_address` + `normalized_city / district / road / number`。金融保險的鐵律：**歷史事實不能因為今天的模型比較漂亮而消失。**

## 效能診斷順序 {#1-22-4-5}

> **Query → Index → Schema → Transaction → Architecture → Hardware**（不要反過來）

- Query：Slow Query、Full Scan、N+1、`SELECT *`、大 OFFSET、一次讀太多。
- Index：是否命中、Composite 順序、選擇性、無效索引造成寫入放大；用 EXPLAIN。
- Transaction：範圍過大、交易中等外部 API、Lock 競爭、Connection Pool 設定。
- DB 常常不是 CPU Bound，而是 **Memory + Storage I/O**：Working Set 能否放進 RAM、IOPS、Disk Latency、log flush、checkpoint、sort spill。
- **PostgreSQL 參數比 SQL 更決定上限**：
  - Query Planner 會估算命中量，量少時寧可 Seq Scan，別跟 planner 耍小聰明。
  - `shared_buffers` 建議約系統記憶體 25%，要和 OS page cache 取平衡。
  - 分區表需要開很多檔，受 OS 檔案上限影響；PG 11 起有 `enable_partition_pruning`。
  - pgbench（tpcb-like、20 連線）：預設 6,400 TPS → 手調 15 個基礎參數 8,300 TPS（約 +30%）→ 全參數 + OS 自動調參 22,000 TPS，延遲標準差也更穩。⚠️ 第三組是雲廠商（華為雲）產品，數字僅供量級參考。
  - 入門從 [postgresqlco.nf](https://postgresqlco.nf/) 基礎 15 個參數開始。

## 擴展路線與 Sharding {#1-22-4-6}

```txt
Schema → Index → SQL tuning → Cache → Scale Up → Read Replica
→ Partition 大表 / 拆冷熱 → 按業務邊界拆 → 最後才 Sharding
```

- **關聯式 DB 也能 scale**：Facebook social graph、YouTube 影片 metadata 都在分散式 MySQL（YouTube 開源 Vitess）。「只有 NoSQL 能擴展」是錯誤觀念。
- Vertical Partition = 按欄位拆；Horizontal Partition = 按列拆；Partition 通常同一 DB 內，Sharding 跨節點。
- **Read Replica 要注意 Replication Lag**：商品列表、文章、報表可讀 replica；剛付款查狀態、剛改資料立即讀、登入權限判斷要謹慎或讀 primary。
- Logical Shard ≠ Physical DB：多個邏輯分片可先放同一台，長大再搬。
- **Shard Key 選錯後面很難救**，它本質是「資料歸屬設計」：

| Shard Key | 適合 | 風險 |
| --- | --- | --- |
| user_id | 使用者型產品 | 大戶變熱點 |
| tenant_id | B2B SaaS | 大租戶變 hot tenant |
| order_id | 訂單 | 查某 user 全部訂單要跨 shard |
| region | 全球多區 | 地區流量不均 |
| created_at（Range） | Log、交易、K 線 | 最新區間全部打在同一片 |
| hash(id) | 平均分布 | 範圍查詢不便、加 shard 要 rebalance |

- 真正難點：Cross-shard Join / Transaction、全域唯一、Rebalancing、Hot Shard、Routing Layer、Migration、備份還原、監控到單一 shard。
- 面試版：Sharding 是依 shard key 把資料切到多節點，每片只存一部分；Replica 是複製全部資料分擔讀取。通常先做 index、tuning、cache、replica、partition，單庫容量、寫入量、租戶隔離或地理分布真的出現才 sharding。

## SQL 學習定位 {#1-22-4-7}

語法門檻不高（數天 CRUD/JOIN、數週 CTE/Window Function）；值得累積的是 **Schema、Index、Execution Plan、Transaction / Lock / Isolation / Deadlock、Partition / Replication**，架構層能力要靠 production 經驗與故障案例。ORM、雲、AI 降低實作成本，但不會替你決定一致性要多高、哪裡要 transaction、什麼規模才值得 sharding。

## 正規化 vs ETL {#1-22-4-8}

- **正規化 = 表怎麼設計**（客戶資料只存一次，訂單只存 customer_id）。
- **ETL = 不同系統的資料怎麼搬運與整理**（`customer_name / name / cust_name` 統一成同一欄）。ETL 過程可能做正規化，但兩者不等同。
- 資料庫設計三層：**Schema Design → Transaction Design（Ledger、異動紀錄）→ Data Pipeline（ETL、報表）**。金融業最痛的往往是第三層：20 年前的格式 + 10 套系統 + 欄位命名不一致。

## MongoDB 速查 {#1-22-4-9}

- 舊語法淘汰：`insert / update / remove` → `insertOne/Many`、`updateOne/Many`、`deleteOne/Many`。
- `find(filter, projection)`、`.sort({ price: -1 }).limit(10)`、`createIndex / getIndexes / dropIndex`。
- 真正該學的是：什麼要嵌入、什麼要 reference、文件會不會無限成長、查詢模式需要什麼 index、Aggregation、Transaction、Replica Set、Sharding。

## Vector DB {#1-22-4-10}

- 解決「什麼東西跟這個很像」；SQL 解決「哪一筆精確符合、和其他資料有什麼結構關係」。兩者不是同一類問題，**Vector DB 吃掉的是搜尋 / 檢索層，不會取代 OLTP 核心交易庫**。
- 趨勢是 SQL 把向量吃進去：**PostgreSQL + pgvector** 同時有 Transaction、JOIN、JSON、向量搜尋，中小系統不必另養一套。
- 選型：MVP → pgvector；已用 Mongo → Atlas Vector Search；本機 Demo → Chroma / FAISS；大規模低延遲 → Qdrant / Weaviate / Milvus / Pinecone；關鍵字 + 語意 → Hybrid Search。
- 陷阱：chunk 太碎或太大、embedding 模型選錯、**沒有 metadata filter 導致權限外洩**、只靠向量漏掉精確關鍵字、沒附來源、刪資料沒刪 vector。
- 學習順序：Relational → Index / Transaction / Query Plan → Distributed DB → Vector / ANN → Hybrid Search → RAG。下一步值得深入：**B-tree index vs HNSW 差在哪**。
