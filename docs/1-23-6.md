# 1-23-6 JavaScript 的能力邊界 {#1-23-6}

::: info 新增（2026-11）
整理自一次問答：前端程式能操控系統與瀏覽器到什麼程度？瀏覽器支援度變化快，表格為 2026-11 的概況，實際以 [caniuse](https://caniuse.com/) 與 MDN 為準。
:::

**語言本身不決定權限，權限由它跑在哪個宿主（runtime）與作業系統決定**（見 [1-21 Rust 與 C++ 比較](./1-21.md#1-21-9)）。JS 能做到什麼，取決於宿主提供哪些 API。由淺到深分四層：

```txt
第 1 層  網頁 JS          瀏覽器沙箱：能力多，但每件事都要使用者授權
第 2 層  瀏覽器擴充套件    可讀改所有網頁，Native Messaging 通往本機程式
第 3 層  作業系統上的 JS   Node.js／Deno／Bun／Electron：權限 = 執行它的使用者帳號
第 4 層  更底層           嵌入式可以；作業系統核心實務上做不到
```

## 第 1 層：網頁裡的 JS {#1-23-6-1}

能力比多數人想像的多，但大多要 **HTTPS（secure context）**、**使用者手勢觸發**（點擊後才能呼叫）、**權限詢問**。

### 硬體與裝置 {#1-23-6-2}

| API | 能做什麼 | 支援概況 |
| --- | --- | --- |
| `getUserMedia` / `getDisplayMedia` | 相機、麥克風、螢幕錄影 | 主流瀏覽器 |
| Geolocation、Device Orientation | 定位、陀螺儀、加速度計 | 主流瀏覽器（iOS 動作感測要另外請求權限） |
| Gamepad | 遊戲手把 | 主流瀏覽器 |
| Web MIDI | 電子琴、MIDI 控制器 | Chromium、Firefox |
| Web Bluetooth | BLE 裝置（心率帶、IoT） | Chromium |
| WebUSB | 直接和 USB 裝置交換資料 | Chromium |
| Web Serial | 序列埠，例如 Arduino、ESP32 | Chromium（桌面為主） |
| WebHID | 特殊鍵盤、遊戲周邊、條碼槍 | Chromium（桌面） |
| Web NFC | 讀寫 NFC 標籤 | Android 版 Chrome |

```js
// 用 Web Serial 讀 Arduino 從序列埠送來的資料（必須在點擊事件裡呼叫）
button.addEventListener('click', async () => {
  const port = await navigator.serial.requestPort()   // 跳出裝置選擇視窗
  await port.open({ baudRate: 9600 })
  const reader = port.readable.pipeThrough(new TextDecoderStream()).getReader()
  for (;;) {
    const { value, done } = await reader.read()
    if (done) break
    console.log(value)                                // 例如溫度感測器的讀數
  }
})
```

### 檔案、運算與網路 {#1-23-6-3}

| 類別 | 能做到 | 支援概況 |
| --- | --- | --- |
| 本機檔案 | 使用者授權後讀寫檔案與整個資料夾（File System Access API：`showOpenFilePicker`、`showDirectoryPicker`） | Chromium（桌面） |
| 私有檔案系統 | 每個網站一塊高效能的私有儲存（OPFS），可跑 SQLite | 主流瀏覽器 |
| 接近原生的運算 | WebAssembly 執行 C／C++／Rust 編譯的程式 | 主流瀏覽器 |
| GPU 運算 | WebGPU：圖形與通用運算（compute shader） | Chromium、Safari 26、Firefox（Windows 起） |
| 多執行緒 | Web Worker；共享記憶體 `SharedArrayBuffer` 需要跨來源隔離（COOP + COEP 標頭） | 主流瀏覽器 |
| 網路 | fetch、WebSocket、WebRTC 點對點連線與資料通道、WebTransport | WebTransport 支援度較晚，其餘主流 |
| 背景與安裝 | Service Worker 離線運作、推播通知、安裝成 PWA；Background Sync | 推播含 iOS 16.4+ 已安裝的 PWA；Background Sync 僅 Chromium |

這些組合起來的實際案例：瀏覽器裡跑 Python（Pyodide）、SQLite、完整的 Linux 虛擬機（v86、WebVM）、影片剪輯、本機 LLM 推論（WebLLM，透過 WebGPU）。

### 沙箱的牆：做不到的事 {#1-23-6-4}

- 不能讀寫任意檔案，只能碰使用者主動選擇的檔案與資料夾。
- 不能執行本機程式，不能呼叫系統 API。
- 不能開原生 TCP／UDP socket。Chrome 的 Direct Sockets API 只開放給特殊安裝形式的 Isolated Web Apps，一般網頁不行。
- 不能讀其他網站的資料（同源政策、CORS，見 [模擬面試 9 Q4](./interview-9.md#interview-9-4)），不能碰其他分頁或其他程式。
- 不能在頁面外側錄鍵盤滑鼠，不能改系統設定。
- 不能跳過權限詢問；儲存空間可能被瀏覽器回收，除非申請 `navigator.storage.persist()`。

### 真正的極端：漏洞 {#1-23-6-5}

在規格之內，網頁 JS 不會超出上面的牆；超出的情況只剩漏洞：

- **旁路攻擊**：2018 年的 Spectre 讓網頁 JS 能透過高精度計時推測讀取同一程序內的記憶體。瀏覽器的對策是 **Site Isolation**（不同網站放不同程序）、降低 `performance.now()` 精度，並要求跨來源隔離才能使用 `SharedArrayBuffer`。
- **沙箱逃逸**：要從網頁拿到作業系統控制權，通常要串兩個漏洞：先讓渲染程序執行任意程式碼（例如 V8 的漏洞），再利用另一個漏洞逃出沙箱。這是瀏覽器漏洞獎金最高的一類，所以保持瀏覽器更新是最基本的防線。
- **指紋追蹤**：不需要權限，也能從 Canvas、字型、螢幕、硬體資訊組合出近乎唯一的識別碼，這是隱私層面的灰色地帶。

## 第 2 層：瀏覽器擴充套件 {#1-23-6-6}

擴充套件的權限遠大於網頁：

- 取得 host permissions 後可以讀取、修改使用者造訪的所有網頁內容。
- 攔截與改寫網路請求（Manifest V3 的 `declarativeNetRequest`）、管理分頁、讀寫 cookie、截取分頁畫面。
- **Native Messaging**：和本機安裝的程式透過標準輸入輸出溝通，等於從瀏覽器架一座通往作業系統的橋，例如密碼管理器的桌面程式、憑證元件。

這也是惡意擴充套件危險的原因：安裝時授予的權限要仔細看。開發範例見 [1-6-12 Chrome Extension 案例](./1-6-12.md#1-6-12-10)。

## 第 3 層：JS 直接跑在作業系統上 {#1-23-6-7}

離開瀏覽器後，JS 就是一般的系統程式語言，**權限等於執行它的那個使用者帳號**；用 `sudo` 執行就是 root。

| 宿主 | 能做到 |
| --- | --- |
| Node.js、Deno、Bun | 讀寫任意檔案、`child_process` 執行任何指令、原生 TCP／UDP（`node:net`、`node:dgram`）、C++ 原生模組；用 FFI 直接呼叫 C 函式庫（Deno `Deno.dlopen`、Bun `bun:ffi`、Node 的 koffi 套件） |
| Electron、Tauri | 完整的桌面 App（VS Code、Slack、Discord 都是 Electron）。Tauri 前端用網頁技術、後端用 Rust，體積較小 |
| React Native、Capacitor | 手機 App，透過原生模組呼叫 iOS／Android API |
| macOS JXA | 用 JS 自動化操控其他 App（Finder、Mail、Safari） |

```js
// Node.js：網頁 JS 做不到、在這裡都可以
import { readFile } from 'node:fs/promises'
import { execFile } from 'node:child_process'
import net from 'node:net'

console.log(await readFile('/etc/hosts', 'utf8'))          // 讀系統檔案
execFile('ls', ['-la', '/'], (err, out) => console.log(out)) // 執行指令
net.connect(22, 'localhost').on('data', (b) => console.log(b.toString())) // 原生 TCP
```

權限控管的方向剛好和瀏覽器相反：**預設全開，要自己限制**。

- **Deno** 預設全關，要明確開啟：`deno run --allow-read=./data --allow-net=api.example.com main.ts`。
- **Node.js** 的權限模型（Node.js 22.13+、23.5+ 起為穩定功能）：`node --permission --allow-fs-read=./data app.js`。
- 作業系統本身的保護仍然有效：macOS 的螢幕錄影、輔助使用、相機等權限，Electron App 一樣要使用者在系統設定裡授權；沒有管理員權限就改不了系統檔案。

## 第 4 層：更底層 {#1-23-6-8}

- **嵌入式可以**：Espruino、Moddable XS、JerryScript 這類精簡引擎能在 ESP32 等 MCU 上跑 JS，直接控制 GPIO、感測器、Wi-Fi（見 [1-16-6 ESP32](./1-16-6.md)）。
- **作業系統核心實務上做不到**：JS 需要 runtime 與垃圾回收，核心層要的是可預測的記憶體配置與執行時間，還要能處理中斷與硬體暫存器。曾有把 V8 直接開機的實驗性核心（runtime.js），但都停在實驗階段。驅動與核心仍是 C、Rust、組合語言的領域（見 [1-16-7 作業系統是用什麼寫的](./1-16-7.md#1-16-7-5)）。

## 其他程式語言也一樣嗎 {#1-23-6-10}

**一半一樣，一半不一樣**。要分成兩個面向看：

**1. 權限的上限：所有語言都一樣，由宿主與作業系統決定**

- Python、Java、Go、C++ 寫的一般程式，和 Node.js 一樣跑在 User Space，權限就是執行它的帳號權限；沒有管理員權限，誰都改不了系統檔案或核心。
- 換宿主就換邊界：任何語言編成 WebAssembly 放進瀏覽器，就和網頁 JS 關在同一個沙箱，C++ 也開不了原生 socket；Java 以前的瀏覽器 Applet、Android App、iOS App 一樣受沙箱與權限系統限制。
- 唯一的差別是：**瀏覽器原生只執行 JavaScript**（加上 WebAssembly），其他語言要進瀏覽器都得編成 Wasm 或轉成 JS。

**2. 能往下走多深：各語言不一樣，取決於需不需要 runtime**

| 語言 | 需要的執行環境 | 最底層能做到 |
| --- | --- | --- |
| C、C++、Rust、Zig | 可以不需要（`no_std`、freestanding） | 開機程式、作業系統核心、驅動、無作業系統的 MCU |
| Go | 自己的 runtime + GC | 系統工具、網路服務；TinyGo 可跑在 MCU；寫核心不實際 |
| Java、C#、Kotlin | JVM／.NET runtime | 伺服器、Android；寫核心不實際 |
| Python、JavaScript、Ruby | 直譯器／JIT + GC | 一般程式；精簡版（MicroPython、Espruino）可跑在 MCU；寫核心不實際 |

不需要 runtime 和 GC 的語言才能寫作業系統本身，因為核心要自己管理記憶體、處理中斷、直接操作硬體暫存器，而且執行時間必須可預測（見 [1-16-7](./1-16-7.md#1-16-7-5)、[1-21 C++ 深入](./1-21.md#1-21-8)）。

**3. 安全預設也不一樣**：同樣在 User Space，C／C++ 允許直接操作記憶體位址（出錯就是未定義行為），Rust 要先通過編譯器的所有權檢查，Java、Python、JS 則完全不讓你碰記憶體位址。這是「控制自由度」的差別，不是「權限」的差別。

## 一句話 {#1-23-6-9}

網頁 JS 的邊界是瀏覽器沙箱：能做的事很多，但每一件都經過使用者授權，越界只剩漏洞。離開瀏覽器後，JS 和 Python 一樣是一般的系統程式語言，權限由作業系統決定；真正碰不到的只有核心層。
