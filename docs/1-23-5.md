## 開發時自動重啟 {#1-23-5-1}

- Node.js 18.11 起內建 `node --watch app.js`，檔案變更就自動重啟，多數情況不用再裝工具。
- `nodemon` 仍然常見：支援設定檔 `nodemon.json`、`--watch`／`--ignore` 指定監看範圍、`-L` 輪詢模式（在 Windows 掛載到 Docker 容器的目錄收不到檔案事件時有用）。
- TypeScript 用 `tsx watch src/main.ts`。

## 日誌除錯：debug 模組 {#1-23-5-2}

程式碼裡到處 `console.log`，上線前還要記得刪。`debug` 套件讓日誌依命名空間開關，預設不輸出，用環境變數開啟：

```js
import createDebug from 'debug'
const debug = createDebug('app:http')

debug('%s %s', req.method, req.url)
```

```bash
DEBUG=app:* node app.js     # 只在需要時開啟，並顯示兩次輸出的時間間隔
```

Express 等許多套件內部也用它（`DEBUG=express:*`）。正式環境的結構化日誌則用 pino、winston，並送到集中式日誌系統。

## 中斷點除錯：--inspect {#1-23-5-3}

Node.js 內建 Inspector，不需要再安裝舊的 `node-inspector` 套件。

```bash
node --inspect app.js            # 預設 127.0.0.1:9229
node --inspect-brk app.js        # 第一行就暫停，方便除錯啟動流程
node --inspect=0.0.0.0:9229 app.js  # 容器內除錯時讓外部連入（只在開發環境，不要對外開放）
```

- **Chrome**：網址列輸入 `chrome://inspect`，在 Configure 加入位址，點 inspect 開啟和前端一樣的 DevTools（中斷點、變數、呼叫堆疊、Memory、Profiler）。
- **VS Code**：可以直接用 JavaScript Debug Terminal；連到容器或遠端時在 `launch.json` 用 attach：

```json
{
  "type": "node",
  "request": "attach",
  "name": "Attach to container",
  "address": "localhost",
  "port": 9229,
  "localRoot": "${workspaceFolder}",
  "remoteRoot": "/app"
}
```

VS Code 的好處是發現問題可以直接改程式碼，不用在瀏覽器和編輯器之間切換。

## 測試的層級與價值 {#1-23-5-4}

| 層級 | 測什麼 | 通常由誰寫 |
| --- | --- | --- |
| 單元測試 | 一個函式、一個類別 | 開發者 |
| 整合測試 | 多個模組組合後是否正常（含資料庫、API） | 開發者或測試人員 |
| 系統測試／E2E | 整個系統是否符合需求 | 測試人員或自動化 E2E |

單元測試的價值：
1. **防止迴歸**：每修一個 bug 就補一個測試，同樣的 bug 不會再回來；重構時確認行為沒變。
2. **逼你寫出低耦合的程式**：可測試的程式不一定好，但難以測試的程式通常耦合太高（例如一個函式同時打 API 又改 DOM）。
3. **可信度**：成熟的開源專案都有測試，這是程式碼的「合格證」。

撰寫原則：一個測試案例只驗證一件事；同時測正常情況與例外情況；測試檔和原始碼放在一起（`foo.ts` 旁邊放 `foo.test.ts`），改程式時比較不會忘記改測試，建置時再排除測試檔即可。

## 測試工具 {#1-23-5-5}

- **斷言**：內建 `node:assert`（`strictEqual`、`deepStrictEqual`、`throws`、`rejects`…）。
- **測試執行器**：Node.js 20 起內建穩定的 `node:test`（`node --test`），小型專案不需要額外框架；前端或 Vite 專案用 Vitest；Jest 仍很普遍；舊專案常見 Mocha、AVA。
- **HTTP 測試**：supertest 直接對 app 發請求；或用 `fetch` 搭配 MSW 模擬外部 API。

```js
import { test } from 'node:test'
import assert from 'node:assert/strict'
import { factorial } from './math.js'

test('factorial', async (t) => {
  await t.test('0! = 1', () => assert.equal(factorial(0), 1))
  await t.test('3! = 6', () => assert.equal(factorial(3), 6))
  await t.test('負數回傳 NaN', () => assert.ok(Number.isNaN(factorial(-1))))
})
```

## TDD 與 BDD {#1-23-5-6}

- **TDD（測試驅動開發）**：先定介面、先寫測試，再實作到測試通過。強調邏輯正確性，bug 少；但高耦合的複雜邏輯寫測試很花時間。常見語法 `suite` / `test`。
- **BDD（行為驅動開發）**：從功能與預期行為出發描述，比較像黑箱測試。常見語法 `describe` / `it`，讀起來像規格。

兩者不必嚴格區分，衡量測試好壞看的是指標：
- **通過率**：必須 100%，有一個失敗就是不通過。
- **覆蓋率**：用 c8／istanbul（nyc）或測試框架內建的 coverage 產生報告，標出沒被執行到的程式碼。覆蓋率上不去，常常代表程式本身耦合太高。
