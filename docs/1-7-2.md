## 心智模型 {#1-7-2-1}

- **四個區域**：Working Directory → (`add`) → Staging / Index → (`commit`) → Local Repo → (`push`) → Remote。`fetch` 只抓不合併；`pull` = fetch + merge（團隊常用 `pull --rebase` 保持線性歷史）。
- **快照而非差異**：SVN/CVS 存版本間的 delta、還原要一路重播 patch；Git 每次 commit 存整個專案快照，沒變的檔案只放指標，所以切版本、開分支都快。
- **四種物件**：Blob（檔案內容，同內容只存一份）、Tree（目錄與檔名 → blob/tree）、Commit（指向一棵 tree + parent + 作者訊息）、Tag（指向 commit）。Branch 只是貼在 commit 上會移動的標籤；HEAD 指向目前分支。
- **`git add` 才是重工**：套用 .gitignore / .gitattributes（CRLF、LFS）→ 算 hash → 寫 blob → 更新 index。所以 commit 幾乎瞬間完成。觀察用：`git ls-files --stage`、`git cat-file -p <sha>`。

## 現代實務指令 {#1-7-2-2}

```txt
git status / add / commit / log / diff
git switch <branch>       # 取代 checkout 切分支
git switch -c feature/x   # 建立並切換
git restore <file>        # 丟掉工作區修改
git restore --staged <f>  # 取消暫存、保留修改
git fetch / pull --rebase / push -u origin <branch>
git stash / stash pop / stash apply
git rebase / cherry-pick / revert
git reflog                # 誤刪 branch、reset 錯時的救命指令
git bisect                # 二分法找出引入 bug 的 commit
git tag v1.0.0 && git push origin v1.0.0
```

**規則**：`reset --hard` 會丟資料，不懂別用；團隊共用分支不要 rebase；撤銷已推送的 commit 用 `revert`；`blame` 用來追脈絡不是抓戰犯。

## 分支策略 {#1-7-2-3}

- **Git Flow**（main / develop / feature / release / hotfix）：適合 App 發版、套裝軟體、需維護多版本的企業系統。
- **現代 SaaS 常見**：短生命 feature branch + PR + CI + main 隨時可部署。Git Flow 要懂，但不必照抄。

## 合併衝突 {#1-7-2-4}

1. `git status` 找出 `both modified` 的檔案
2. 處理 `<<<<<<< HEAD … ======= … >>>>>>> branch` 區塊（保留一邊或手動整合；VS Code 有 Accept 按鈕）
3. `git add <file>` 標記已解決 → merge 用 `git commit`、rebase 用 `git rebase --continue`
4. 想放棄：`git merge --abort` / `git rebase --abort`

- 預防：合併前先拉最新、commit 小而清楚、模組切乾淨避免多人改同一塊。

## Conventional Commit {#1-7-2-5}

格式：`<type>(scope): <description>`，破壞性變更用 `feat(api)!:` 或 footer `BREAKING CHANGE:`。

| type | 用途 | 例 |
| --- | --- | --- |
| feat | 新功能 | feat(auth): add login with OTP |
| fix | 修 bug | fix(order): prevent duplicate checkout |
| docs | README、API 文件、描述行為的註解 | docs: update installation guide |
| style | 格式、空白、分號，不影響邏輯 | style: format with prettier |
| refactor | 重構（不加功能也不修 bug），含為改善架構的搬檔 | refactor: move auth module to services |
| perf | 效能 | perf: cache user lookup |
| test | 測試（含搬測試檔） | test(payment): add refund cases |
| chore | 雜項維護：依賴、env、純可讀性註解、暫時註解掉程式、單純搬檔 | chore(deps): upgrade nanoid to 5.0.9 / chore(env): add API_KEY |
| build / ci | 建置系統 / CI 設定 | ci: add GitHub Actions workflow |
| revert | 回復先前 commit | revert: revert login page redesign |

## 面試問 Git 問得「高級」 {#1-7-2-6}

不問會不會 commit，而問情境：分支策略怎麼設計、遇過什麼問題？hotfix 怎麼操作？已 merge 的 bug 怎麼 rollback？feature 與 main 長期分歧怎麼處理？最棘手的衝突經驗？

## `git add` 背後做了什麼 {#1-7-2-7}

::: info 新增（2026-11）
本節以下整理自 Notion「Git 進入web開發網站」子頁〈from AI〉、〈commit msg〉、〈合併衝突〉。
:::

1. **展開路徑並套用忽略規則**：讀 `.gitignore`、全域 ignore（`core.excludesFile`），把你輸入的路徑展開成檔案清單；`-A` 還會找出已刪除的檔案，準備在 index 標記刪除。
2. **套用 `.gitattributes` 的 clean filter**：例如 CRLF 轉 LF、Git LFS 把大檔換成指標檔，得到「規範化」後的內容。
3. **計算雜湊、寫入 blob**：對內容算 SHA-1（新版可用 SHA-256）。`.git/objects/` 已有同樣雜湊就直接重用（去重複），沒有才用 zlib 壓縮寫入。
4. **更新 index**（`.git/index`）：每個路徑記錄 blob 雜湊、檔案模式（100644／100755／120000）與檔案的 stat 資訊（mtime、inode，用來快速判斷檔案有沒有改）。
5. **互動與衝突**：`git add -p` 會把 diff 切成 hunk 讓你挑；在合併衝突中 `git add <file>` 代表「我解完了」，把檔案從 unmerged 狀態移回正常 index。
6. **hooks**：`pre-commit` 不會在 add 時觸發；Git LFS 之類的工具是透過 filter 在這個階段接管檔案。

快的原因：未變的檔案重用舊 blob、用 stat 快取避免重算雜湊、物件分散在 256 個子目錄。`git commit` 只是把 index 組成 tree 物件、加上 parent 與作者資訊寫成 commit 物件，所以幾乎瞬間完成。

```bash
git ls-files --stage        # index 條目與 blob 雜湊
git cat-file -p <blobSHA>   # blob 內容
git cat-file -p <treeSHA>   # tree 結構
```

## Commit type 怎麼選：常見情境 {#1-7-2-8}

| 情境 | type | 例 |
| --- | --- | --- |
| 升級套件修弱點 | chore(deps) | `chore(deps): upgrade nanoid to 5.0.9 to fix security vulnerability` |
| 新增／修改／刪除環境變數 | chore(env) | `chore(env): add API_KEY` / `update DB_HOST to new server address` / `remove unused SENTRY_DSN` |
| 區分開發與正式環境設定 | chore(env) | `chore(env): separate development and production env files` |
| README、API 文件、描述函式行為的註解 | docs | `docs: fix incorrect parameter description in API docs` |
| 純為可讀性的註解、刪過時註解 | chore | `chore: remove outdated comments in main.js` |
| 暫時註解掉程式碼 | chore | `chore: temporarily comment out debug logs` |
| 單純搬檔 | chore | `chore: move utils.js to helpers directory` |
| 為了改善架構而搬檔 | refactor | `refactor: move auth module to services directory` |
| 搬測試檔 | test | `test: move unit tests to __tests__ folder` |
| 搬移造成功能改變 | feat | `feat: separate authentication logic into its own module` |

判斷原則：說明「行為」或給人閱讀的文件用 `docs`；不影響功能的開發雜務用 `chore`；拿不準時，程式碼內的註解變更多半歸 `chore`。

## 合併衝突補充 {#1-7-2-9}

- 會發生在 `git merge`、`git pull`（內含 merge）、`git rebase`、`git cherry-pick`。
- 圖形工具：VS Code（衝突區塊上的 Accept Current／Incoming／Both）、GitKraken、SourceTree；或 `git mergetool` 開啟設定好的工具（meld、kdiff3）。
- 合併前先拉最新、commit 小而清楚、模組切分好避免多人改同一塊、用 PR 流程，都能減少衝突。
