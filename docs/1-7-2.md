# 1-7-2 單向數據流架構 React 解析 {#1-7-2}

::: info 改寫（2026-11）
原內容整理自 2019 年前的書籍，以 React 16 的 class 元件為主。已改用函式元件與 Hooks，並更新三個已經改變的行為：React 18 起 `setState` 在任何地方都會自動批次更新；React 17 起事件綁在根容器而不是 `document`；React 17 移除了合成事件的物件重用（`e.persist()` 不再需要）。
:::

## JSX 與條件渲染 {#1-7-2-1}

JSX 會被編譯成函式呼叫（React 17 起是 `jsx('div', props)`，舊版是 `React.createElement`），所以大括號裡只能放**運算式**，不能直接寫 `if`／`for`。

```jsx
function List({ isLoading, error, items }) {
  // 狀態多的時候，在 return 前用 if 提早處理，比巢狀三元運算子好讀
  if (isLoading) return <Spinner />
  if (error) return <ErrorMessage error={error} />
  if (items.length === 0) return <p>清單是空的</p>
  return <ul>{items.map((item) => <li key={item.id}>{item.name}</li>)}</ul>
}
```

常見陷阱：`{count && <Badge />}` 在 `count` 是 `0` 時會把 `0` 印到畫面上，要寫 `{count > 0 && <Badge />}`。

## setState 是同步還是非同步 {#1-7-2-2}

正確說法是：**React 會把同一輪事件裡的多次更新合併（batch），統一重新渲染一次**，所以呼叫完 `setState` 立刻讀，拿到的還是舊值。

```jsx
function Counter() {
  const [count, setCount] = useState(0)
  const handleClick = () => {
    setCount(count + 1)
    setCount(count + 1) // 兩次都讀到同一個 count，結果只 +1
    setCount((c) => c + 1) // 依前一個值計算要用函式寫法
  }
}
```

| | React 17 以前 | React 18 起 |
| --- | --- | --- |
| React 事件處理函式內 | 批次 | 批次 |
| `setTimeout`、Promise、原生 `addEventListener` 內 | **不批次，同步更新** | 也批次（automatic batching） |

舊書說「React 控制之外的 setState 是同步的」只適用 React 17 以前。現在需要「更新完立刻讀 DOM」時用 `flushSync(() => setState(…))`，或把讀 DOM 的程式放進 `useLayoutEffect`。

## 合成事件 {#1-7-2-3}

React 不在每個元素上綁原生事件，而是在**根容器**（`createRoot` 的那個節點）統一監聽，再依元件樹模擬冒泡（React 16 是綁在 `document`）。事件物件是包裝過的 `SyntheticEvent`，原生事件在 `e.nativeEvent`。

- **非同步讀事件物件**：React 16 的事件物件會被重用，非同步讀取會變 `null`，要 `e.persist()`；React 17 起取消重用，可以直接讀。
- **和原生監聽混用時的停止冒泡**：React 的 `e.stopPropagation()` 只能停止 React 樹裡的冒泡。如果你在 `document` 或 `window` 上自己綁了原生監聽，React 17 起事件在根容器就停住、不會到 `document`；但要擋住**根容器以下**的原生監聽仍然做不到，因為它們在 React 處理之前就執行了。

## 清單的 key 與 diff {#1-7-2-4}

React 比對同一層子節點時，用 `key` 判斷「這是不是同一個元素」，再決定移動、新增或刪除。

React 的移動策略很簡單：由左到右走新清單，如果某個節點在舊清單的位置比「目前已處理過的最大位置」還前面，就移動它。所以把**最後一個移到最前面**時，React 會移動其他所有節點，而不是只移動那一個。Vue 3 用「最長遞增子序列」找出最少的移動次數，這種情況只移動一個。

`key` 的原則：

- 用資料本身穩定的 ID；不要用 `Math.random()`（每次渲染都重建）。
- 用陣列索引當 key，在中間插入或刪除時，元件的內部狀態（輸入框內容、展開狀態）會錯位。
- 只有純文字、沒有狀態、也不會重新排序的清單，用索引無妨。

## 元件設計原則 {#1-7-2-5}

**單一職責：拆的是「會因為不同原因而改」的部分**

```jsx
// 取資料和顯示混在一起：換 API 或改顯示方式都要動同一個元件
// 拆開：資料邏輯放進自訂 Hook，元件只負責畫面
function useWeather(city) {
  const [data, setData] = useState(null)
  useEffect(() => {
    let ignore = false
    fetchWeather(city).then((d) => { if (!ignore) setData(d) })
    return () => { ignore = true } // 避免 city 變了之後，舊請求的結果蓋掉新的
  }, [city])
  return data
}
function WeatherInfo({ temperature, wind }) {
  return <p>{temperature}°C，風速 {wind} km/h</p>
}
```

不需要把每個元件都拆到最小，拆過頭只是增加跳來跳去的成本。實務上資料請求多半交給 TanStack Query、SWR 這類函式庫，它們處理了快取、重試、競態。

**封裝：子元件只透過 props 溝通，不碰父元件的內部狀態**

```jsx
// 不好：把整個 setState 或父元件實例傳下去，子元件得知道父元件 state 的結構
<Controls parent={this} />
// 好：只傳語意明確的 callback
<Controls onIncrement={() => setCount((c) => c + 1)} onDecrement={() => setCount((c) => c - 1)} />
```

**組合優先於繼承**：用 `children` 或具名的 props 插槽組合版面；共用邏輯用自訂 Hook。HOC、render props 是 Hooks 出現前的做法，舊程式碼裡還會看到。

**盡量純**：同樣的 props 渲染出同樣的畫面。依賴全域變數（例如直接讀 `window.config.siteName`）的元件，改成由 props 傳入，測試時就不用改全域變數。副作用集中在 `useEffect`、事件處理函式或資料層。

**可測試**：用 Testing Library 從使用者角度測（找到按鈕、點擊、檢查畫面文字），不要測元件內部的 state。如果測一個元件要先搭一堆假的父元件，代表它和父元件耦合太深。

**命名**：元件名稱說清楚「它是什麼」（`UserAvatar`、`OrderSummary`），不要 `Comp1`、`NewList2`；事件 props 用 `onXxx`，處理函式用 `handleXxx`。
