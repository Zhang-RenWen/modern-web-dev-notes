### Q1. 從輸入網址到畫面出現，中間發生什麼？ <Badge type="tip" text="高頻" /> {#21-9-1}

::: details 解題思路
分「網路段」和「渲染段」，每段講 3～5 步，最後點出可以優化的地方，讓答案和效能、快取串起來。
:::

::: details 標準答案與過程
**網路段**

1. 解析 URL，檢查各層快取（Service Worker、HTTP Cache）；命中就不發請求。
2. DNS 解析取得 IP（瀏覽器 → OS → 遞迴解析器 → Root → TLD → 權威 DNS）。
3. 建立連線：HTTP/1.1、HTTP/2 走 TCP 三向交握 + TLS 握手；HTTP/3 走 QUIC（UDP 上整合 TLS 1.3）。
4. 送出 HTTP 請求，經過 CDN、負載平衡、反向代理到應用伺服器，收到回應。

**渲染段**

5. 解析 HTML 建 DOM；遇到 CSS 建 CSSOM（會阻塞渲染）；遇到同步 script 會暫停解析（`defer`／`async`／`type="module"` 不會）。
6. DOM + CSSOM → Render Tree → Layout → Paint → Composite。
7. JS 執行可能再修改 DOM，觸發重新 Layout／Paint。

**可優化點**：DNS 預解析（`dns-prefetch`）、`preconnect`、CDN、HTTP/2+、快取、減少阻塞資源、關鍵 CSS、SSR／SSG。
:::

### Q2. 常見 HTTP 狀態碼？401 和 403、502 和 504 差在哪？ <Badge type="tip" text="基礎" /> {#21-9-2}

::: details 標準答案與過程
- **401 Unauthorized**：還沒證明你是誰（沒帶 token、token 過期）→ 前端導向登入或用 refresh token 換新。
- **403 Forbidden**：知道你是誰，但沒有權限 → 顯示無權限頁，不要重新登入。
- **502 Bad Gateway**：閘道收到上游的壞回應（上游掛了、回應格式錯）。
- **503 Service Unavailable**：服務過載或維護中。
- **504 Gateway Timeout**：閘道等上游等到逾時（上游太慢）。

其他常考：200、201（已建立）、204（無內容）、301／302（導向）、304（快取有效）、400（請求格式錯）、404、409（衝突，例如版本不符）、422（驗證失敗）、429（請求太多，看 `Retry-After`）、500。
:::

**相關筆記**：[1-18-18 HTTP 必背對照](./1-18-18.md#1-18-18-2)

### Q3. HTTP/1.1、HTTP/2、HTTP/3 差在哪？ <Badge type="tip" text="高頻" /> {#21-9-3}

::: details 標準答案與過程
| | HTTP/1.1 | HTTP/2 | HTTP/3 |
| --- | --- | --- | --- |
| 傳輸層 | TCP | TCP | QUIC（UDP） |
| 格式 | 文字 | 二進位分幀 | 二進位分幀 |
| 多工 | 無，一條連線一次一個請求（瀏覽器開 6 條並行） | 一條連線多個串流 | 一條連線多個串流 |
| 隊頭阻塞 | HTTP 層與 TCP 層都有 | HTTP 層解決，TCP 層掉包仍會卡住全部串流 | 串流獨立，掉包只影響該串流 |
| 標頭壓縮 | 無 | HPACK | QPACK |
| 建立連線 | TCP + TLS 多次往返 | 同左 | 通常 1-RTT，可 0-RTT |
| 網路切換 | 斷線重連 | 斷線重連 | 連線遷移（Wi-Fi 換 4G 不斷） |

對前端的影響：HTTP/2 之後，「合併檔案、雪碧圖、網域分片」這些 HTTP/1.1 時代的技巧不再必要，甚至有反效果（快取粒度變粗）。
:::

**相關筆記**：[1-18-12 HTTP-1.x](./1-18-12.md)、[1-18-13 HTTP-2.0](./1-18-13.md)、[1-18-1 TCP／UDP／QUIC](./1-18-1.md#1-18-1-2)

### Q4. CORS 是什麼？什麼時候會有 preflight？怎麼解決？ <Badge type="tip" text="高頻" /> {#21-9-4}

::: details 標準答案與過程
**同源政策**：協定、網域、port 三者相同才是同源。瀏覽器預設不讓 JS 讀取跨源請求的回應。CORS 是**伺服器**用回應標頭告訴瀏覽器「允許哪些來源讀取」。

**簡單請求**：方法為 GET／HEAD／POST，且只用安全標頭、Content-Type 限 `application/x-www-form-urlencoded`、`multipart/form-data`、`text/plain`。直接發送，伺服器回 `Access-Control-Allow-Origin`。

**Preflight**：其他情況（PUT、DELETE、`Content-Type: application/json`、自訂標頭如 `Authorization`）會先發 `OPTIONS`：

```txt
OPTIONS /api/orders
Origin: https://app.example.com
Access-Control-Request-Method: PUT
Access-Control-Request-Headers: authorization, content-type

204 No Content
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Methods: GET, POST, PUT
Access-Control-Allow-Headers: authorization, content-type
Access-Control-Max-Age: 600
```

要帶 cookie：前端 `credentials: 'include'`，後端 `Access-Control-Allow-Credentials: true`，且 `Allow-Origin` **不能是 `*`**。

解法：後端設定 CORS（白名單，不要反射任意 Origin）；開發環境用 Vite／Webpack dev server proxy；正式環境用同網域反向代理或 BFF，根本避開跨源。

觀念：CORS 是瀏覽器保護使用者的機制，**不是伺服器的防護**，Postman、curl 不受限制；它也不能防 CSRF。
:::

**相關筆記**：[21-10 Q2 CSRF](./21-10.md#21-10-2)

### Q5. Cookie、Session、JWT 差在哪？Token 應該存哪？ <Badge type="tip" text="高頻" /> {#21-9-5}

::: details 標準答案與過程
- **Cookie** 是瀏覽器端的傳輸容器，會自動附在同網域請求上。
- **Session** 是伺服器端的狀態，Session ID 通常放在 Cookie 裡。好撤銷，但要共享儲存（Redis）才能水平擴展。
- **JWT** 是自帶資訊並簽章的 token，伺服器不用查表就能驗證。**只是 Base64URL 編碼，不是加密**，不放敏感資料；簽發後難以即時撤銷。

存放位置比較：

| 位置 | XSS 能偷 | CSRF 風險 | 建議 |
| --- | --- | --- | --- |
| localStorage | 能 | 無 | 不放 refresh token |
| 記憶體（變數） | 較難（重新整理就消失） | 無 | 放短效 access token |
| HttpOnly + Secure + SameSite Cookie | 不能讀 | 有，需防護 | 放 refresh token 或 session |

推薦組合：access token 短效放記憶體；refresh token 放 HttpOnly Cookie 並做 rotation。高安全需求（金融）用 **BFF**：瀏覽器只拿 session cookie，token 留在伺服器。
:::

**相關筆記**：[1-19-4 隨機數與 Token 儲存](./1-19-4.md#1-19-4-2)、[1-19-2 JWT 登入](./1-19-2.md)

### Q6. OAuth 2.0、OIDC、SSO、PKCE 是什麼關係？畫出登入流程 <Badge type="tip" text="高頻" /> {#21-9-6}

::: details 解題思路
先釐清名詞：OAuth 2.0 是**授權**，OIDC 是在 OAuth 上加**身分**，SSO 是使用情境，PKCE 是保護授權碼的機制。再畫 Authorization Code + PKCE。
:::

::: details 標準答案與過程
- **OAuth 2.0**：讓 App 取得存取資源的 access token（授權），本身不定義「使用者是誰」。
- **OIDC**：在 OAuth 2.0 上加 ID Token（JWT）與 UserInfo，提供身分驗證。
- **SSO**：一次登入，多個系統共用登入狀態，通常以 OIDC 或 SAML 實作（Keycloak、Azure AD、Okta）。
- **PKCE**：SPA、手機 App 無法安全保存 client secret，用一次性的 code_verifier 防止授權碼被攔截後冒用。

```txt
1. 前端產生 code_verifier（隨機），code_challenge = BASE64URL(SHA256(verifier))
2. 導向 IdP：/authorize?response_type=code&client_id=..&redirect_uri=..
                &scope=openid profile&state=..&code_challenge=..&code_challenge_method=S256
3. 使用者在 IdP 登入、同意
4. IdP 導回 redirect_uri?code=..&state=..   （前端檢查 state 防 CSRF）
5. 前端（或 BFF）POST /token：code + code_verifier
6. IdP 驗證 SHA256(verifier) == challenge → 回 access_token、id_token、refresh_token
7. 呼叫 API 帶 Authorization: Bearer <access_token>
```

不要再用 Implicit Flow（token 放在 URL fragment）和 Password Grant。
:::

**相關筆記**：[1-22-6 認證與身份](./1-22-6.md#1-22-6-4)、[1-19-5 登入、MFA 與信任裝置](./1-19-5.md#1-19-5-1)

### Q7. RESTful API 怎麼設計？什麼是冪等？ <Badge type="tip" text="高頻" /> {#21-9-7}

::: details 標準答案與過程
原則：

1. URI 用名詞、複數表示資源：`GET /orders/123`，不要 `GET /getOrder?id=123`。
2. Method 表示動作：GET 讀、POST 建立、PUT 整筆替換、PATCH 局部更新、DELETE 刪除。
3. 階層表達關係：`GET /orders/123/items`。
4. 分頁、排序、篩選用 query：`?page=2&size=20&sort=-createdAt&status=paid`；大資料用 cursor 分頁。
5. 版本：`/v1/orders`。
6. 統一錯誤格式：`{ code, message, details, traceId }`。

**冪等（Idempotent）**：同一請求執行一次或多次，伺服器狀態結果相同。GET、PUT、DELETE 是冪等的；POST 不是。

為什麼重要：網路逾時後前端或閘道會重送。付款、下單這類 POST 要加 **Idempotency-Key**：

```js
const key = crypto.randomUUID()             // 同一次操作重送時沿用同一把 key
await fetch('/api/payments', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json', 'Idempotency-Key': key },
  body: JSON.stringify({ orderId, amount }),
})
```

後端記錄 key 與結果，重複的 key 直接回傳第一次的結果，不重複扣款。
:::

### Q8. 什麼是 BFF？什麼時候需要？ <Badge type="tip" text="高頻" /> {#21-9-8}

**考點**：國泰 DDT 必要條件「有後端 API 串接與 BFF 架構經驗」。

::: details 標準答案與過程
BFF（Backend For Frontend）是專門服務某一個前端的後端層，由前端團隊擁有。

做的事：
1. **聚合**：一個頁面要呼叫 5 個微服務，BFF 並行呼叫後合併成一個回應，減少往返。
2. **裁剪與轉換**：只回傳畫面需要的欄位，轉成前端好用的 DTO。
3. **隔離變動**：後端服務改版時，只改 BFF 的轉換邏輯。
4. **安全**：token 留在 BFF，瀏覽器只拿 session cookie；密鑰不外流。
5. **前端專屬邏輯**：快取、格式化、權限判斷後的選單組裝。

和 API Gateway 的差別：Gateway 是所有流量的入口（路由、限流、TLS、認證），BFF 是「某個前端需要什麼形狀的資料」。兩者可以並存：`Client → Gateway → BFF → 微服務`。

何時不需要：只有一個前端、後端只有一個服務且回應已經貼合畫面時，BFF 只是多一層部署與延遲。

常見實作：Node.js（Fastify、NestJS）、Next.js Route Handlers；GraphQL 也是一種 BFF 形式。
:::

**相關筆記**：[1-22-6 BFF](./1-22-6.md#1-22-6-3)

### Q9. 即時資料要用輪詢、SSE 還是 WebSocket？ <Badge type="tip" text="高頻" /> {#21-9-9}

::: details 標準答案與過程
| 方式 | 方向 | 特性 | 適合 |
| --- | --- | --- | --- |
| 短輪詢 | 客戶端拉 | 最簡單，浪費請求 | 低頻狀態檢查 |
| 長輪詢 | 客戶端拉 | 伺服器有資料才回 | 舊環境相容 |
| **SSE** | 伺服器 → 客戶端 | 基於 HTTP、自動重連、文字格式 | 通知、進度、AI 串流回應、行情單向推播 |
| **WebSocket** | 雙向 | 全雙工、低延遲、要自己處理重連與心跳 | 聊天、協作編輯、遊戲、交易下單 |

WebSocket 實務要處理：斷線重連（指數退避）、心跳偵測、重連後補資料（帶最後序號）、訊息順序與去重、背壓（訊息太多時節流畫面更新，例如用 `requestAnimationFrame` 合併）、認證（連線時帶 token，過期要重新驗證）。
:::

### Q10. API 請求怎麼處理錯誤、重試、取消與競態？ <Badge type="warning" text="進階" /> {#21-9-10}

::: details 標準答案與過程
用一層統一的 HTTP client 處理：

1. **攔截器**：自動帶 token；401 時用 refresh token 換新，並把同時失敗的請求排隊、換完一起重送（避免同時打好幾次 refresh）。
2. **錯誤分類**：網路錯誤、逾時、4xx（使用者可修正，顯示訊息）、5xx（顯示稍後再試並回報）。
3. **重試**：只重試冪等請求或帶 Idempotency-Key 的請求；用指數退避加隨機抖動；429 依 `Retry-After`。
4. **取消**：`AbortController`，元件卸載或參數改變時取消。
5. **競態**：搜尋框快速輸入時，舊請求比新請求晚回來會覆蓋結果。用取消、或比對請求序號只採用最新的。

```js
let latest = 0
async function search(q) {
  const id = ++latest
  const data = await api.get('/search', { params: { q } })
  if (id !== latest) return        // 已經有更新的請求，丟掉這個結果
  results.value = data
}
```
:::
