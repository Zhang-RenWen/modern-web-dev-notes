# 1-6-1 效能監控和錯誤收集與回報 {#1-6-1}

::: info 改寫（2026-11）
原內容整理自 2019 年前的書籍，已依現在的標準改寫：FMP、TTI 已被 Lighthouse 淘汰，改用 Core Web Vitals（LCP、INP、CLS；INP 在 2024 年取代 FID）；`performance.timing` 已廢除，改用 `PerformanceObserver`；回報時機從 `unload` 改成 `visibilitychange`；刪掉 FMP 自製演算法與劫持 `console.error` 的做法。
:::

> 一句話：**效能看真實使用者的 Core Web Vitals，錯誤要能收齊（同步、非同步、資源、框架）並還原到原始碼，回報不能拖慢頁面。**

## 該看哪些指標 {#1-6-1-1}

| 指標 | 量什麼 | 「良好」門檻（第 75 百分位） |
| --- | --- | --- |
| **LCP**（Largest Contentful Paint） | 畫面上最大的圖片或文字區塊畫出來的時間：使用者覺得「主要內容出來了」 | ≤ 2.5 秒 |
| **INP**（Interaction to Next Paint） | 整個停留期間，點擊、按鍵到畫面有反應的延遲（取接近最差的一次） | ≤ 200 毫秒 |
| **CLS**（Cumulative Layout Shift） | 版面無預警跳動的程度 | ≤ 0.1 |
| FCP（First Contentful Paint） | 第一個內容出現 | ≤ 1.8 秒 |
| TTFB（Time to First Byte） | 伺服器回應速度 | ≤ 0.8 秒 |

前三個是 Google 的 **Core Web Vitals**，會影響搜尋排名。以前常講的 FMP（第一次有意義繪製）定義太主觀，TTI 對真實使用者不穩定，都已經不用；「關鍵內容何時出現」交給 LCP，或自己用 Element Timing 標記。

另外兩個事件常被混淆：`DOMContentLoaded` 是 HTML 解析完、同步腳本執行完；`load` 是圖片、樣式等所有資源都載完。

## 怎麼量 {#1-6-1-2}

| 方式 | 說明 |
| --- | --- |
| **實驗室資料**（Lighthouse、DevTools Performance） | 固定網路與裝置，適合開發時找問題，但不代表真實使用者 |
| **真實使用者資料（RUM）** | 在使用者瀏覽器裡量，再回報；Chrome 使用者體驗報告（CrUX）、Search Console 也有 |

最簡單的 RUM 是用 Google 的 [`web-vitals`](https://github.com/GoogleChrome/web-vitals) 套件，它處理了很多邊界情況（背景分頁、bfcache 還原、iframe）：

```js
import { onLCP, onINP, onCLS } from 'web-vitals'

const report = (metric) => navigator.sendBeacon('/rum', JSON.stringify(metric))
onLCP(report)
onINP(report)
onCLS(report)
```

想自己量時，用 `PerformanceObserver`（`performance.timing` 已廢除）：

```js
// 導覽各階段時間
const [nav] = performance.getEntriesByType('navigation')
console.log({ ttfb: nav.responseStart, domReady: nav.domContentLoadedEventEnd, load: nav.loadEventEnd })

// 長任務：主執行緒被占用超過 50ms 的工作，是 INP 差的主因
new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) console.log('long task', entry.duration)
}).observe({ type: 'long-animation-frame', buffered: true }) // Chrome 123+；更舊的 Chromium 用 'longtask'

// 自訂指標：例如「第一排商品圖出現」
performance.mark('first-row-rendered')
performance.measure('first-row', { end: 'first-row-rendered' }) // 從頁面開始算到這個標記
```

## 錯誤要從哪裡收 {#1-6-1-3}

| 錯誤來源 | 怎麼接 | 注意 |
| --- | --- | --- |
| 同步執行的錯誤 | `window.addEventListener('error', …)` | 也可以用 `window.onerror`，但只能設一個 |
| 沒被處理的 Promise rejection | `window.addEventListener('unhandledrejection', …)` | `await` 沒包 `try/catch` 的錯誤會到這裡 |
| 圖片、腳本、樣式載入失敗 | `window.addEventListener('error', handler, true)` | **要在捕獲階段監聽**，資源錯誤不會冒泡 |
| 跨網域腳本的錯誤 | `<script crossorigin="anonymous">` + CDN 回 `Access-Control-Allow-Origin` | 沒設定只會拿到 `Script error.`，沒有訊息和行號 |
| React 元件 | Error Boundary（`componentDidCatch`） | 事件處理函式和非同步程式碼的錯誤接不到 |
| Vue 元件 | `app.config.errorHandler` | |
| CSP 違規、瀏覽器介入（例如擋掉廣告） | Reporting API：`Reporting-Endpoints` 標頭 | 由瀏覽器直接回報，不用寫 JS |

```js
window.addEventListener('error', (e) => {
  if (e.target !== window) {
    report({ type: 'resource', url: e.target.src || e.target.href }) // 資源載入失敗
  } else {
    report({ type: 'js', message: e.message, stack: e.error?.stack })
  }
}, true)

window.addEventListener('unhandledrejection', (e) => {
  report({ type: 'promise', reason: String(e.reason), stack: e.reason?.stack })
})
```

`try/catch` 只接得到**同一個呼叫堆疊**裡的錯誤：包在 `setTimeout` callback 外面的 `try` 接不到裡面丟出的錯，所以全域監聽是必要的。

**還原到原始碼**：線上程式碼經過壓縮，行號沒有意義。建置時產生 source map，**上傳到錯誤監控服務而不要公開部署**，由服務端把堆疊還原成原始檔案與行號。Sentry 這類服務已經包好上面所有收集、還原、去重、告警。

## 回報：不能拖慢頁面 {#1-6-1-4}

- **用 `navigator.sendBeacon()` 或 `fetch(url, { keepalive: true })`**：頁面關閉時請求也會送出，不會阻擋換頁。
- **在 `visibilitychange`（變成 `hidden`）時送出累積的資料**，不要用 `unload`／`beforeunload`：手機切到背景、直接關分頁時它們常常不觸發，而且 `unload` 會讓頁面進不了 bfcache。
- **批次與取樣**：先累積再一次送；流量大時依比例取樣；同一個錯誤短時間內重複發生只送一次。
- **回報網域**：用獨立網域可以避免帶上主站的 Cookie，也不會被主站的連線數限制卡住；但要處理 CORS，`sendBeacon` 送 `text/plain` 就不會觸發預檢。

## 偵測當機與卡死 {#1-6-1-5}

主執行緒卡死時，頁面上的 JS 什麼都做不了，所以要靠頁面外的觀察者：

- **Service Worker 心跳**：頁面每幾秒傳訊息給 Service Worker，太久沒收到就判定卡死並回報。
- **下次載入時補報**：載入時在 `sessionStorage` 寫「進行中」，正常離開（`pagehide`）時改成「已離開」；下次載入發現還是「進行中」，代表上次異常結束。
- 長任務、`long-animation-frame` 的資料可以找出「哪段程式碼讓頁面卡住」。

<script setup>
import { ref, onMounted, onUnmounted } from 'vue'
const log = ref('')
function onError(event) {
  log.value += `${event.type}: ${event.message}\n`
  console.log(event)
}
// Thrown from a timer so it reaches window.onerror instead of Vue's handler.
function generateScriptError() {
  setTimeout(() => new Function('const s;'))
}
onMounted(() => window.addEventListener('error', onError))
onUnmounted(() => window.removeEventListener('error', onError))
</script>
