# 1-12-4 JWT 登入 {#1-12-4}

::: info 改寫（2026-11）

> 一句話：**問題從來不是「用 JWT 還是 Cookie」，而是「憑證放在哪裡、怕 XSS 還是怕 CSRF」**；兩種攻擊的防法不一樣，要一起處理。

## JWT 是什麼 {#1-12-4-1}

`header.payload.signature` 三段用 `.` 串起來，前兩段是 Base64URL 編碼的 JSON（**誰都能解開來看**），第三段是伺服器用密鑰對前兩段算出的簽章。伺服器收到 token 時重新計算簽章比對，就知道內容沒被改過、確實是自己發的，不用查資料庫。

```text
Authorization: Bearer eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiIxMjMiLCJleHAiOjE3OTk5OTk5OTl9.xxxx
```

## 憑證放在哪裡：兩種攻擊 {#1-12-4-2}

| 存放位置 | XSS（注入惡意腳本） | CSRF（別的網站讓瀏覽器帶著你的憑證發請求） |
| --- | --- | --- |
| `localStorage`／`sessionStorage`，請求時手動加在 `Authorization` 標頭 | **怕**：任何腳本都讀得到，token 被偷就能在任何地方冒用 | 不怕：瀏覽器不會自動帶 |
| 記憶體（JS 變數），重新整理就沒了 | 較不怕：沒有固定位置可讀，但攻擊腳本仍能在頁面上代為發請求 | 不怕 |
| **HttpOnly Cookie** | 讀不到 token；但攻擊腳本在你的頁面上發的請求仍會帶 Cookie | **怕**：瀏覽器會自動帶，要用 SameSite 等方式防 |

**Cookie 的安全屬性**：

| 屬性 | 作用 |
| --- | --- |
| `HttpOnly` | JS 讀不到 |
| `Secure` | 只在 HTTPS 傳送 |
| `SameSite=Lax`（預設） | 跨站時只有「點連結換頁」這種頂層 GET 會帶，跨站的表單 POST、`fetch`、圖片請求不帶 |
| `SameSite=Strict` | 跨站一律不帶（從別的網站點連結進來也要重新登入） |
| `__Host-` 前綴 | 強制 `Secure`、`Path=/`、不能設 `Domain`，避免被子網域覆寫 |

```http
Set-Cookie: __Host-session=abc123; Path=/; Secure; HttpOnly; SameSite=Lax
```

`SameSite` 擋住了大部分 CSRF，但「同站不同子網域」的攻擊、用 GET 做修改的 API 仍有風險。改資料的 API 一律不要用 GET，並檢查 `Origin` 標頭或加上 CSRF token。

## 常見的組合做法 {#1-12-4-3}

| 做法 | 說明 | 取捨 |
| --- | --- | --- |
| Session Cookie（傳統） | Cookie 只放一個隨機 session ID，狀態存在伺服器 | 最簡單可靠，可以隨時讓 session 失效；要有共用的 session 儲存（例如 Redis） |
| Access token 放記憶體 + Refresh token 放 HttpOnly Cookie | access token 短效（幾分鐘），過期用 refresh token 換新；refresh token 每次使用就換一張（rotation），偵測到舊的被重複使用就全部撤銷 | SPA 呼叫跨網域 API 時常用 |
| 把 JWT 拆開放 | 舊書提出的折衷：header 與 payload 放 JS 可讀的 Cookie（前端可以顯示使用者資訊），簽章放 HttpOnly Cookie | 實作複雜，現在較少用 |
| **BFF（Backend for Frontend）** | 瀏覽器只拿到 HttpOnly 的 session Cookie；真正的 access／refresh token 留在同網域的後端，由後端代為呼叫 API | 目前對瀏覽器應用最推薦的做法，token 完全不會出現在瀏覽器 |

**敏感操作要重新驗證**：改密碼、改 Email、轉帳時，即使已經登入也要再輸入一次密碼或 OTP。這樣即使 session 被盜用或遭受 CSRF，也無法完成最關鍵的操作。

**JWT 的「無狀態」有代價**：簽發後在過期前都有效，伺服器無法單獨撤銷某一張。要做到強制登出、停用帳號立即生效，還是得維護黑名單或 refresh token 表，這時它就不再是完全無狀態了。
