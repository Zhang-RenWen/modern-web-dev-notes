## REST API {#1-22-6-1}

> REST 是資源導向的 HTTP API 風格：URI 表示資源、Method 表示操作、Status Code 表示結果。GET 讀取、POST 新增或觸發動作、PUT 整筆替換、PATCH 局部更新、DELETE 刪除。Path Parameter 定位資源；Query Parameter 篩選、排序、分頁；Body 放主要資料；Header 放 Authorization、Content-Type、Accept 等 metadata。

- 必記：**401 = 你是誰？（未登入）／ 403 = 知道你是誰但沒權限**；409 衝突、422 驗證失敗；502 / 503 / 504 閘道與服務可用性。更多狀態碼見 [1-18-18](./1-18-18.md#1-18-18-2)。
- 下一層要補：資源命名、**Idempotency 冪等性**、cursor pagination、OpenAPI、API versioning、統一 Error Response 格式。
- REST vs GraphQL：REST 由 server 定義回應形狀、好 cache；GraphQL 由 client 指定欄位、適合聚合多資料的頁面，但要處理 query complexity、cache、N+1、權限。不是誰取代誰。

### 設計有效且安全的 API（以購物車為例）

| 原則 | 不好 | 較好 |
| --- | --- | --- |
| 資源用名詞 | `GET /querycarts/123` | `GET /carts/123` |
| 用複數 | `GET /cart/123` | `GET /carts/123` |
| 冪等 | `POST /carts` | `POST /carts`，body 帶 `requestId` |
| 版本 | `GET /carts/v1/123` | `GET /v1/carts/123` |
| 軟刪除後查詢 | `GET /carts` | `GET /carts?includeDeleted=true` |
| 分頁 | `GET /carts` | `GET /carts?pageSize=xx&pageToken=xx` |
| 排序 | `GET /items` | `GET /items?sort_by=time` |
| 篩選 | `GET /items` | `GET /items?filter=color:red` |
| 安全存取 | 只帶 `X-API-KEY` | `X-API-KEY` + `X-EXPIRY` + `X-REQUEST-SIGNATURE`（HMAC(URL + QueryString + Expiry + Body)） |
| 跨資源參照 | `GET /carts/123?item=321` | `GET /carts/123/items/321` |
| 自訂動作 | `POST /carts/123?addItem=321` | `POST /carts/123/items:add`，body 帶 itemId |
| 限流 | 沒有限流（易被 DDoS） | 依 IP、user、action group 設計 rate limit |

來源：[ByteByteGo](https://blog.bytebytego.com/)

## API 效能基本功 {#1-22-6-2}

不是先加機器，而是：**Pagination（大資料用 cursor）、Async Logging（buffer / queue 批次寫）、Caching（TTL、invalidation，Browser / CDN / App / Redis 多層）、Payload Compression（gzip / brotli，已壓縮的圖片影片不要再壓）、Connection Pool（pool size、timeout、backpressure）、Load Balancer（health check）、Async Processing（queue、worker、retry、DLQ、idempotency）**。

- Middleware 三層防護：請求 → **超時控制**（例：慢查詢 10 秒直接回 504）→ **統一異常處理**（標準錯誤格式）→ **日誌記錄** → 業務邏輯。⚠️ 原貼文宣稱可用性 99.5%→99.95%、維護成本 -60%，屬未驗證的社群貼文數字。

## BFF（Backend For Frontend） {#1-22-6-3}

- 前端專用的後端層：聚合多個服務 API、轉成前端要的 DTO、過濾欄位、隔離核心服務變動；可分 Web / Mobile / Admin 各一個。
- **BFF ≠ API Gateway**：Gateway 管入口治理（routing、rate limit、TLS、認證），BFF 管「這個前端需要什麼形狀的資料」，兩者可並存。
- 只有「多前端 + 多後端服務 + 大量資料組裝」才值得；Vue → 單一 Backend → DB 硬塞 BFF 只是多一層部署與延遲。

## 認證與身份 {#1-22-6-4}

- **Cookie 是 client 端傳輸容器，Session 是 server 端狀態；Session ID 通常就放在 Cookie 裡**，兩者不是互斥方案。Cookie 屬性：HttpOnly、Secure、SameSite、Max-Age。
- **JWT 不是加密**（只是 Base64Url），保證未被竄改與有效期，不保證保密、不易即時撤銷；不要放敏感個資。
- Session 適合需要強控制與即時撤銷；JWT 適合多服務共用身份，要搭配短效 access token + refresh token rotation + 撤銷機制。
- 新系統現代做法：OAuth 2.0 是授權不是登入，**OIDC** 才是身份層；Authorization Code + **PKCE** 為主，不用 Implicit / Password Grant；token 不要隨手放 localStorage；搭配 MFA / OTP / Trusted Device。
- 更多見 [1-19-4](./1-19-4.md)、[1-19-5](./1-19-5.md)。

## 併發模型 {#1-22-6-5}

- **CPU-bound → 多執行緒 / worker pool；I/O-bound → async / event loop / non-blocking I/O**。
- Thread Pool：控制同時執行數、避免頻繁建立 thread；風險是被塞滿。Async：等 I/O 時釋放 thread；風險是錯誤處理與流程複雜。
- 語言執行模型：C / C++ / Go / Rust 編成 machine code；Java / C# 編成 bytecode / IL 再由 VM + JIT 執行；Python（CPython 也先編 bytecode）、JS（V8 有 JIT）由 runtime 執行。

## 框架與語言選擇 {#1-22-6-6}

- Express：只給 HTTP 工具；**Fastify**：HTTP + Plugin + Schema，架構自己決定（適合學後端架構）；**NestJS**：連應用程式怎麼組織都定規則（DI、Module、Decorator）。差別是**你願意把多少架構決策交給框架**。
- 後端概念跨語言可遷移；換語言主要是學新生態（Java：JVM、Spring DI、JPA、Transaction；Go：explicit error、goroutine、channel、context）。
- 語言能做的事高度重疊，選擇看**總成本與總風險**：開發速度、runtime、併發模型、型別、生態、人才、團隊既有能力、長期維護。
- 典型傾向（非限制）：BFF / Web API → Node / Java / Go；核心交易 → Java；Infra → Go；AI / Data → Python。
- **Polyglot 本身是成本**：每多一種語言就多一套 build、依賴、資安修補、CI/CD、監控、招募與 on-call 知識；公司裡多語言常常只是歷史包袱。新創用 Java 也完全合理。
- **後端真正難的是：資料、狀態、邊界、一致性、演進**——Domain Boundary、Data Model、Transaction / Idempotency / Race Condition / Eventual Consistency、API versioning 與 schema migration、認證授權日誌等橫切關注點。
- Legacy 核心（AS/400、IBM i、mainframe）不換，是因為 **Replacement Risk 大於 Legacy Cost**；現代化走 Legacy Core → API / Integration Layer → New Services，用 **Strangler Pattern** 逐步替換，不是全部重寫。
