# 1-5-3 渲染管線 Critical Rendering Path {#1-5-3}

::: info 新增（2026-11）
整理自 Notion「2026 全新瀏覽器原理」03，並併入原本 1-5-1「瀏覽器渲染流程與除錯」的實測與面試版回答。以 WHATWG HTML 標準、W3C CSS 規範與各大引擎共通的流程為主；Blink、Gecko、WebKit 內部的名稱和切法不同，但階段大致一樣。
:::

瀏覽器收到 HTML 之後，把文字變成螢幕上像素的整段過程，叫**關鍵渲染路徑 Critical Rendering Path**。

::: tip 一句話版本
**HTML → DOM、CSS → CSSOM，合起來算出每個元素的樣式 → 組成 Render Tree → Layout 算位置大小 → Paint 產生繪製指令 → 分層、點陣化 → Composite 把圖層疊成畫面**。改動越前面的階段，後面全部要重做，成本越高。
:::

## 總覽 {#1-5-3-1}

```txt
HTML bytes ─▶ Tokenize ─▶ DOM Tree ─┐
                                     ├─▶ Style（計算樣式）─▶ Layout（排版）─▶ Paint（繪製指令）
CSS bytes ──▶ Parse ───▶ CSSOM ─────┘                                            │
            ▲                                                                    ▼
JavaScript ─┘（可讀寫 DOM 與 CSSOM）  螢幕 ◀─ Composite（合成）◀─ Raster（點陣化）◀─ Layerize（分層）
                                             └──────── 在 Compositor／GPU 執行 ───────┘
```

| 階段 | 輸入 | 輸出 | 在做什麼 |
| --- | --- | --- | --- |
| 1. 解析 HTML | HTML 位元組 | DOM | 位元組 → 字元 → Token → 節點 → 樹 |
| 2. 解析 CSS | 外部、`<style>`、inline 的 CSS | CSSOM | 把所有樣式規則整理成樹狀結構 |
| 3. 樣式計算 Style | DOM + CSSOM | 每個元素的 Computed Style | 選擇器比對、層疊（Cascade）、繼承，算出最終值 |
| 4. Render Tree | DOM + Computed Style | Render Tree（現代引擎多稱 Layout Tree） | 只留下要畫出來的節點 |
| 5. Layout | Render Tree + 視窗大小 | 每個盒子的位置與尺寸 | 盒模型計算，把 %、em、vw 換成實際像素 |
| 6. Paint | Layout 結果 | 繪製指令清單（Display List） | 依堆疊順序決定先畫背景、邊框、文字… |
| 7. Layerize → Raster → Composite | 多個圖層 | 最終畫面 | 分層、切磚塊點陣化，合成執行緒把圖層依序疊起來交給 GPU |

## 1. 解析 HTML → DOM {#1-5-3-2}

- **流程**：位元組依編碼（通常 UTF-8）轉成字元 → Tokenizer 切成開始標籤、結束標籤、文字等 Token → 建成節點 → 依巢狀關係組成 DOM 樹。
- **邊下載邊解析**：不用等整份 HTML 下載完，所以畫面可以逐步出現。
- **容錯**：HTML 標準用狀態機規定了錯誤標籤要怎麼修正，所以少寫結束標籤也不會整頁壞掉，而且每個瀏覽器的結果一致。
- **Preload Scanner**：主解析器被卡住時，另一個輕量掃描器會先往後看，提早下載後面的 CSS、JS、圖片。
- **巢狀深度也有成本**：同樣 10,000 個 `div`，全部平鋪成兄弟節點時解析約 50 毫秒；改成一層包一層的深層巢狀，解析時間可能多兩個數量級。元件化時要避免無意義的包裝層。

**`<script>` 會卡住 HTML 解析**：JS 可能用 `document.write` 或改 DOM，所以解析器遇到一般的 `<script>` 必須停下來，下載並執行完才繼續。

| 寫法 | 下載時 | 執行時機 | 執行順序 | 適合 |
| --- | --- | --- | --- | --- |
| `<script>` | 停止解析 | 下載完立刻執行 | 依出現順序 | 幾乎不用；必要時放 `<body>` 底部 |
| `<script async>` | 不停止解析 | 下載完立刻執行（會中斷解析） | 不保證 | 獨立腳本，如追蹤、廣告 |
| `<script defer>` | 不停止解析 | HTML 解析完、`DOMContentLoaded` 之前 | 依出現順序 | 一般網站的主程式 |
| `<script type="module">` | 不停止解析 | 預設等同 defer | 依相依關係 | Vite 等現代打包工具的輸出 |

## 2. 解析 CSS → CSSOM {#1-5-3-3}

- **CSS 會阻塞渲染（render-blocking）**：CSSOM 建好前瀏覽器不會畫出第一幀，否則會先閃一次沒樣式的內容（FOUC）。
- **CSS 也會阻塞 JS 執行**：JS 可能讀取樣式（如 `getComputedStyle`），所以樣式表還沒載完，排在它後面的 script 要等。
- **CSS 不會阻塞 HTML 解析**：DOM 可以繼續建，只是不會畫出來。
- `media` 不符合的樣式表（如 `<link rel="stylesheet" media="print">`）仍會下載，但不阻塞渲染。

## 3. 樣式計算 Style（Recalculate Style） {#1-5-3-4}

- 對每個 DOM 節點找出所有符合的選擇器，依**層疊規則**決定誰贏：來源與 `!important` → `@layer` → 權重（Specificity：inline > id > class／屬性／偽類 > 標籤）→ 出現順序。
- 再加上**繼承**（如 `color`、`font-size` 會往下傳，`margin`、`border` 不會），得出每個屬性的最終值（Computed Style）。
- 選擇器**由右往左**比對：先找最右邊的關鍵選擇器，不符合就立刻排除，避免大量回溯。所以最右邊要夠具體（class），不要是 `span`、`div`、`*` 這類會命中大量元素的選擇器；`.a .b .c div span` 這種深層巢狀會讓這一步變慢。現代引擎已經很快，選擇器通常不是瓶頸，但在大量 DOM 與頻繁樣式重算時仍有差。
- Firefox 的樣式系統 Stylo 用 Rust 寫成，可以多執行緒平行計算樣式。

## 4. Render Tree {#1-5-3-5}

DOM + Computed Style 組成，**只包含要顯示的東西**：

| 情況 | 在 Render Tree 嗎 | 佔版面嗎 | 會觸發什麼 |
| --- | --- | --- | --- |
| `display: none` | ❌ 連子孫一起排除 | ❌ | 切換會 Reflow |
| `visibility: hidden` | ✅ | ✅ 位置保留 | 切換只 Repaint |
| `opacity: 0` | ✅ | ✅，還能被點擊 | 有獨立圖層時只 Composite |
| `<head>`、`<script>`、`<meta>` | ❌ | ❌ | — |
| `::before`／`::after` | ✅（不在 DOM 裡，卻在 Render Tree 裡） | ✅ | — |

## 5. Layout（Firefox 稱為 Reflow） {#1-5-3-6}

- 從根節點開始，依盒模型（content、padding、border、margin）、`display`、`position`、Flex／Grid 規則、文字斷行、字型度量，算出每個盒子的**確切位置與尺寸**。相對單位（%、em、rem、vw）在這裡換成像素，所以視窗大小一變，就要重新 Layout。
- 第一次算叫 Layout，之後因變動重算叫 **Reflow**（兩個詞常混用）。
- 排版是**最昂貴**的階段之一，而且會連鎖：一個元素的尺寸變了，可能牽動父元素、兄弟、子孫。
- Chromium 的新一代排版引擎叫 LayoutNG；Container Queries、`content-visibility` 等新特性都建立在它上面。

## 6. Paint {#1-5-3-7}

- 不是真的畫出像素，而是產生**繪製指令清單（Display List）**：「在 (x, y) 畫一個圓角矩形、填這個顏色、寫這段文字」。
- 順序依堆疊上下文（Stacking Context）與 `z-index`：大致是背景 → 邊框 → 內容 → 外框。

## 7. 分層、點陣化、合成（Layerize → Raster → Composite） {#1-5-3-8}

- 頁面被切成多個**圖層（Layer）**，每層切成**磚塊（Tile）**，在 GPU 或背景執行緒點陣化成像素；**合成執行緒 Compositor Thread** 依位置、透明度、變形把圖層疊成最終畫面。
- 會被提升成獨立圖層的常見情況：`transform`／`opacity` 動畫中、`will-change: transform`、3D transform、`<video>`、`<canvas>`、`position: fixed`（依引擎而定）。
- **好處**：只動 `transform`、`opacity` 時，可以跳過 Layout 和 Paint，直接在合成執行緒處理，就算主執行緒在忙 JS，動畫與捲動也不會卡。
- **代價**：每個圖層都吃記憶體（尤其手機），`will-change` 亂加反而變慢。
- 三家引擎的合成架構：Chromium 的 cc（Chrome Compositor）+ Skia 繪圖、Firefox 的 **WebRender**（Rust，把整個頁面當成 GPU 場景來畫）、WebKit 在 Apple 平台上大量使用 Core Animation 圖層。

## Reflow vs Repaint vs 只 Composite {#1-5-3-9}

**Reflow 一定會接著 Repaint，Repaint 不一定需要 Reflow。**

|  | Reflow（重排／回流） | Repaint（重繪） | 只 Composite |
| --- | --- | --- | --- |
| 什麼變了 | **幾何**：位置、尺寸、版面結構 | **外觀**：顏色、陰影，位置大小不變 | 圖層的位移、縮放、透明度 |
| 要重做的階段 | Style → Layout → Paint → Composite | Style → Paint → Composite | Composite |
| 成本 | 最高 | 中 | 最低 |
| 常見觸發 | `width`、`height`、`margin`、`padding`、`border-width`、`top`／`left`、`font-size`、文字內容變動、增刪 DOM、改 `display`、視窗 resize | `color`、`background-color`、`visibility`、`box-shadow`、`outline`、`border-color` | `transform`、`opacity`（元素在獨立圖層上時） |

實測（10,000 個 `p` 的頁面）：改 `margin` 會重新 layout 再 paint，耗時明顯增加；只改 `color` 幾乎只花在 paint；改 `font-size` 看似只是外觀，卻會改變文字尺寸而觸發 layout。

::: tip 效能黃金規則
只改 `transform` 和 `opacity` 的動畫可以只走「合成」這一步，不需要重新 Layout／Paint，而且不佔主執行緒。改 `width`、`top`、`margin` 則會一路觸發 Layout → Paint → Composite。
:::

### 讀取版面資訊也會強制 Reflow

瀏覽器平常會把多次修改排在一起，等下一個 frame 才算一次。但只要 JS 讀取下列屬性，瀏覽器為了回傳正確數字，必須**當下立刻**重算版面（強制同步佈局 Forced Synchronous Layout）：

`offsetTop／Left／Width／Height`、`clientTop／Width／Height`、`scrollTop／Height`、`getBoundingClientRect()`、`getComputedStyle()`、`innerText`、`focus()`

### Layout Thrashing（版面抖動）

在迴圈裡「讀 → 寫 → 讀 → 寫」，每一次讀都觸發一次強制 Reflow：

```js
// ❌ 每次迴圈：寫入讓版面失效 → 下一圈讀取又強制重算
for (const el of items) {
  el.style.width = box.offsetWidth + 'px'
}

// ✅ 先一次讀完，再一次寫完
const width = box.offsetWidth
for (const el of items) {
  el.style.width = width + 'px'
}
```

## 一個 frame 裡發生的事（幀預算） {#1-5-3-10}

60 Hz 螢幕每個 frame 約 **16.7 ms**，120 Hz 約 **8.3 ms**；扣掉瀏覽器自己的工作，留給 JS 的通常只有一半左右。

```txt
JS（事件、計時器）→ requestAnimationFrame 回呼 → Style → Layout → Paint → Composite
```

- 超過就會掉幀（卡頓）。`requestAnimationFrame` 的回呼會在下一次 Style／Layout 之前執行，是放視覺更新的正確位置；`setTimeout` 不保證對齊 frame。
- 主執行緒上一個超過 50ms 的任務叫 **Long Task**，會讓點擊沒反應，反映在 Core Web Vitals 的 **INP**。Event Loop 與切碎長任務見下一頁。

## 優化清單 {#1-5-3-11}

| 目標 | 做法 |
| --- | --- |
| 首屏更快出現 | CSS 放 `<head>`；JS 用 `defer` 或 `type="module"`；關鍵 CSS 內嵌、其餘延後載入；善用 `preconnect` 與 HTTP 快取標頭 |
| 減少 Reflow | 用切換 class 一次改多個樣式，不要逐條改 `style`；先讀後寫、批次處理 |
| 大量插入 DOM | 用 `DocumentFragment` 或先組好字串再一次插入；框架（Vue／React）的 Virtual DOM 也是在批次化 |
| 動畫順暢 | 用 `transform`／`opacity`，不要動 `top`／`left`／`width`；用 `requestAnimationFrame` |
| 縮小影響範圍 | 動畫元素用 `position: absolute／fixed` 脫離文件流；CSS `contain: layout paint` |
| 長頁面 | `content-visibility: auto` 讓畫面外的區塊跳過渲染；長列表用虛擬捲動 |
| 避免版面跳動（CLS） | 圖片、影片、廣告位先給寬高或 `aspect-ratio` |

## 實戰筆記 {#1-5-3-12}

- `backdrop-filter` 和大面積陰影的點陣化成本很高；元素用 `visibility: hidden` 藏起來再顯示，會重新點陣化（約 200ms）。
- 在 60Hz 螢幕上把 rAF 限速到 30fps，畫格間隔會不均勻，看起來比穩定的低幀率還頓。改成每次刷新都畫，動畫改用依時間計算的 easing。捲動時每一幀都 `setState` 會讓 React 重新比對整頁，改用 ref 直接寫 CSS 變數。
- 量效能前先排除環境因素：硬體加速有沒有開（看 `chrome://gpu`）、GPU 是不是被 SwiftShader 軟體模擬、headless 沒有 vsync、有沒有殘留的 Chrome 程序。指標看 p95 和超過 25ms 的幀數，不是平均 fps；在同一台機器用 `git stash` 量基準，逐一關掉效果做對照實驗找瓶頸。
- Core Web Vitals 標準：LCP ≤ 2.5s、INP ≤ 200ms、CLS ≤ 0.1。Lighthouse 是實驗室數據，要跑多次取中位數；Google 排名看的是真實使用者數據（RUM／CrUX）。
- 用 DevTools 驗證：Performance 面板錄一段，看 Parse HTML、Recalculate Style、Layout、Paint 各花多少時間（紫色是 Style／Layout，綠色是 Paint／Composite）；Rendering 面板開 Paint flashing 看重繪範圍、Layout Shift Regions 看版面位移；Layers 面板看哪些元素被提升為合成圖層。

## 面試常見問法 {#1-5-3-13}

- **從輸入網址到畫面出現發生了什麼？** → 導航流程 + 本頁的七個階段。
- **為什麼 CSS 放 head、JS 放 body 底部（或用 defer）？** → CSS 阻塞渲染，越早下載越好；一般 JS 阻塞 HTML 解析。
- **`display: none`、`visibility: hidden`、`opacity: 0` 差在哪？** → 看 Render Tree 那張表。
- **Reflow 和 Repaint 差在哪、怎麼避免？** → 幾何 vs 外觀；批次讀寫、用 transform／opacity。
- **為什麼 transform 動畫比 left 順？** → 跳過 Layout 和 Paint，只在合成執行緒處理。

::: tip 面試版回答
使用者輸入 URL 後，瀏覽器先解析 URL、檢查快取與可重用連線，再做 DNS 查詢取得 IP。HTTP/1.1、HTTP/2 通常建立 TCP 連線，HTTPS 再做 TLS handshake；HTTP/3 則走 QUIC over UDP。連線後送出 HTTP request、收到 response。瀏覽器解析 HTML 建 DOM、解析 CSS 建 CSSOM，兩者合成 render tree，接著計算 style、layout、paint，最後 composite 顯示。JS 由 JS 引擎執行，可能修改 DOM 或 CSSOM，造成重新 layout、repaint 或 composite。
:::

## 名詞剖析 {#1-5-3-14}

| 名詞 | 意思 |
| --- | --- |
| Critical Rendering Path | 瀏覽器把 HTML／CSS／JS 變成第一個畫面的必經步驟 |
| DOM／CSSOM | HTML／CSS 解析後的樹狀物件模型，JS 可以讀寫 |
| Token／Tokenizer | 解析的最小單位（開始標籤、文字…）／切出 Token 的程式 |
| Preload Scanner | 主解析器被卡住時先往後找資源下載的輕量掃描器 |
| render-blocking | 在它載完之前不會畫出畫面的資源（CSS、同步 script） |
| FOUC | Flash of Unstyled Content，先閃一次沒有樣式的頁面 |
| Computed Style | 層疊與繼承後，每個屬性的最終值 |
| Specificity／`@layer` | 選擇器權重／CSS 層級，後宣告的層優先權較高 |
| Render Tree／Layout Tree | 只包含要顯示的節點、用來排版的樹 |
| Reflow／Repaint | 重算位置尺寸／只重畫外觀 |
| Display List | Paint 階段產生的繪製指令清單 |
| Raster／Tile | 點陣化：把指令變成像素／圖層切成的小塊 |
| Compositor Thread | 主執行緒之外、負責疊圖層的執行緒 |
| Stacking Context | 堆疊上下文：z-index 只在同一個上下文內比較 |
| `will-change` | 提示瀏覽器某屬性即將變化，可能提前提升成圖層 |
| Forced Synchronous Layout | JS 讀取幾何屬性時，瀏覽器被迫當場重算版面 |
| Layout Thrashing | 迴圈中讀寫交錯，反覆觸發強制重排 |
| `requestAnimationFrame` | 在下一次重繪前執行的回呼，對齊螢幕刷新 |
| `contain`／`content-visibility` | 限制元素影響範圍／讓畫面外區塊跳過渲染 |
| `DocumentFragment` | 不在頁面上的輕量 DOM 容器，組好再一次插入 |
| CLS／INP／LCP／FCP | 版面位移／互動回應／最大內容出現／首次內容出現 |
| SwiftShader／vsync | Chrome 的軟體 GPU 模擬／跟螢幕刷新同步 |
