### Q1. Webpack 和 Vite 差在哪？ <Badge type="tip" text="高頻" /> {#21-11-1}

::: details 標準答案與過程
| | Webpack | Vite |
| --- | --- | --- |
| 開發伺服器 | 先打包整個應用再啟動，專案大時啟動慢 | 不打包，用瀏覽器原生 ESM 按需載入；依賴用 esbuild 預先打包 |
| HMR | 重新打包受影響的模組鏈 | 只讓改動的模組失效，速度幾乎不受專案大小影響 |
| 正式建置 | Webpack 本身 | Rollup（新版 Vite 正逐步改用 Rust 寫的 Rolldown） |
| 設定 | 彈性大但複雜（loader + plugin） | 開箱即用，相容 Rollup plugin |
| 生態 | 最成熟，Module Federation 原生支援 | 新專案主流 |

選擇：新專案 Vite；舊專案的 Webpack 設定複雜、或依賴 Module Federation 時評估遷移成本，也可以先換成相容 Webpack 設定的 Rspack。
:::

### Q2. Tree Shaking 的條件是什麼？為什麼有時候沒效？ <Badge type="tip" text="高頻" /> {#21-11-2}

::: details 標準答案與過程
Tree Shaking 是靠 ESM 的**靜態結構**在建置時找出沒被使用的匯出並刪除。

生效條件：
1. 使用 ESM（`import`／`export`），CommonJS 的 `require` 在執行期才決定，難以分析。
2. 正式建置模式（壓縮器做最後刪除）。
3. 模組沒有副作用，或在 `package.json` 宣告 `"sideEffects": false`（CSS 檔案要列為例外）。

沒效的常見原因：套件只提供 CJS 版本；`import * as _ from 'lodash'` 後動態存取；模組頂層有副作用（修改全域、註冊 polyfill）；Babel 把 ESM 轉成 CJS（`modules: false` 沒設）。
:::

**相關筆記**：[1-6-8 webpack 和 Rollup](./1-6-8.md)、[21-3 Q13 ESM 與 CommonJS](./21-3.md#21-3-13)

### Q3. Webpack 的 Loader 和 Plugin 差在哪？ <Badge type="tip" text="基礎" /> {#21-11-3}

::: details 標準答案與過程
- **Loader**：轉換「單一檔案」的內容，讓 Webpack 能理解非 JS 檔。由右到左（由下到上）串接執行。例：`ts-loader`、`css-loader`、`vue-loader`。
- **Plugin**：掛在 compiler／compilation 的生命週期 hook 上，處理整個建置流程。例：`HtmlWebpackPlugin` 產生 HTML、`MiniCssExtractPlugin` 抽出 CSS、`DefinePlugin` 注入環境變數。

```js
// 最簡單的 loader：把檔案內容轉成大寫字串匯出
module.exports = function (source) {
  return `export default ${JSON.stringify(source.toUpperCase())}`
}
```
:::

### Q4. Monorepo 的優缺點？怎麼管？ <Badge type="tip" text="高頻" /> {#21-11-4}

::: details 標準答案與過程
優點：共用元件與型別直接引用、跨套件修改一次提交、統一工具鏈與規範、重構容易。

缺點：倉庫變大、CI 時間變長、權限難細分、需要工具支援。

工具：pnpm workspace 管理依賴；Turborepo／Nx 做任務快取與「只建置受影響的套件」；Changesets 管版本與 changelog。

```txt
apps/
  admin/          # 後台
  portal/         # 客戶入口
packages/
  ui/             # 共用元件庫（Storybook）
  api-client/     # 由 OpenAPI 產生的型別與請求函式
  eslint-config/  # 共用規範
```
:::

### Q5. Git Flow 和 Trunk-based 怎麼選？merge 和 rebase 差在哪？ <Badge type="tip" text="高頻" /> {#21-11-5}

::: details 標準答案與過程
**分支策略**

- **Git Flow**（main／develop／feature／release／hotfix）：適合固定發版週期、需要維護多個版本（App、套裝軟體、金融業定期上版）。
- **Trunk-based／GitHub Flow**：短生命 feature branch + PR + CI，main 隨時可部署；搭配 feature flag。適合持續部署的 SaaS。

**hotfix**：從 main（正式版）切出修正，完成後同時合回 main 與 develop，並打版本 tag。

**merge vs rebase**

- `merge`：保留真實歷史，產生 merge commit，安全。
- `rebase`：把自己的 commit 重放到最新基底上，歷史線性好讀，但會改寫 commit。**已推到共用分支的 commit 不要 rebase。**
- 已上線的錯誤 commit 用 `git revert`（新增反向 commit），不要 `reset` 後強推。
:::

**相關筆記**：[1-7-2 Git 心智模型與團隊實務](./1-7-2.md)、[1-7-3 Git 情境速查](./1-7-3.md)

### Q6. 前端測試怎麼規劃？什麼該測？ <Badge type="tip" text="高頻" /> {#21-11-6}

::: details 標準答案與過程
| 層級 | 工具 | 測什麼 | 比例 |
| --- | --- | --- | --- |
| 單元 | Vitest／Jest | 純函式、商業規則、composable／hook、格式化 | 多 |
| 元件 | Vue Test Utils、Testing Library | 元件依使用者操作的行為（不是實作細節） | 中 |
| 整合 | Testing Library + MSW 模擬 API | 多元件 + API 的流程 | 中 |
| E2E | Playwright／Cypress | 關鍵使用者路徑：登入、下單、付款 | 少 |
| 視覺回歸 | Storybook + Chromatic／Playwright 截圖 | 元件庫外觀 | 視需要 |

原則：測「行為」不測「實作」（用 role、label 找元素，不用 class）；優先覆蓋最貴的錯誤（金額計算、權限、表單驗證）；E2E 要穩定，避免固定等待時間，用可重試的斷言。

```ts
import { render, screen } from '@testing-library/vue'
import userEvent from '@testing-library/user-event'

test('金額欄位輸入負數時顯示錯誤', async () => {
  render(PremiumForm)
  await userEvent.type(screen.getByLabelText('保費'), '-100')
  await userEvent.click(screen.getByRole('button', { name: '送出' }))
  expect(screen.getByText('保費必須大於 0')).toBeInTheDocument()
})
```
:::

### Q7. 前端的 CI/CD pipeline 會包含哪些步驟？ <Badge type="tip" text="高頻" /> {#21-11-7}

::: details 標準答案與過程
```txt
PR 階段：install（npm ci）→ lint / type-check → unit test → build → bundle size 檢查
        → E2E（預覽環境）→ 安全掃描（dependency、secret）→ Code Review
合併後：build 一次產出 artifact（Docker image 或靜態檔）→ 部署 Dev → QA → UAT
上線：  同一個 artifact 部署 Production（canary／blue-green）→ smoke test → 監控 → 出事 rollback
```

重點：
1. **Build once, deploy many**：各環境用同一個 artifact，差異用執行期設定注入，不要每個環境重新 build。
2. 快取 `node_modules`／pnpm store 加速。
3. 環境變數與密鑰放 CI secrets，不寫進程式碼；前端打包進去的變數都是公開的。
4. 版本號與 commit SHA 寫進產物，錯誤監控能對應版本。
:::

### Q8. 前端 SPA 怎麼用 Docker 部署？ <Badge type="tip" text="高頻" /> {#21-11-8}

::: details 標準答案與過程
用 multi-stage build：第一階段 build，第二階段只放靜態檔與 Nginx，映像檔小且不含原始碼與 node_modules。

```dockerfile
# Stage 1: build
FROM node:22-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

# Stage 2: serve
FROM nginx:1.27-alpine
COPY nginx.conf /etc/nginx/conf.d/default.conf
COPY --from=build /app/dist /usr/share/nginx/html
EXPOSE 80
```

```nginx
server {
  listen 80;
  root /usr/share/nginx/html;

  location / {
    try_files $uri $uri/ /index.html;   # SPA 路由回退，否則重新整理子路徑會 404
    add_header Cache-Control "no-cache";
  }

  location /assets/ {
    add_header Cache-Control "public, max-age=31536000, immutable";
  }
}
```

除錯指令：`docker build -t web .`、`docker run -p 8080:80 web`、`docker logs <id>`、`docker exec -it <id> sh`。
:::

### Q9. Kubernetes 你需要知道哪些？ <Badge type="tip" text="基礎" /> {#21-11-9}

**考點**：台達電「basic Kubernetes (reading yaml, running kubectl)」。

::: details 標準答案與過程
一個前端服務通常是 **Deployment + Service + Ingress**：

- **Pod**：最小執行單位，跑一個或多個容器。
- **Deployment**：宣告要幾個 Pod、用哪個映像，負責滾動更新與回滾。
- **Service**：給一組 Pod 穩定的內部網址與負載平衡。
- **Ingress**：對外的 HTTP 路由與 TLS。
- **ConfigMap／Secret**：設定與密鑰。
- **Probe**：`readinessProbe`（準備好才接流量）、`livenessProbe`（卡死就重啟）。

常用指令：

```bash
kubectl get pods -n web
kubectl describe pod web-7d9f -n web       # 看事件：拉不到映像、OOMKilled、Probe 失敗
kubectl logs -f web-7d9f -n web
kubectl rollout status deployment/web -n web
kubectl rollout undo deployment/web -n web # 回滾
kubectl port-forward svc/web 8080:80 -n web
```

常見狀態：`ImagePullBackOff`（映像名稱或權限錯）、`CrashLoopBackOff`（程式啟動就掛，看 logs）、`OOMKilled`（記憶體限制太小）。
:::

**相關筆記**：[1-7-5 Container：Docker 與 Kubernetes](./1-7-5.md)

### Q10. Micro-Frontends 有哪些做法？什麼時候該用？ <Badge type="warning" text="進階" /> {#21-11-10}

::: details 標準答案與過程
Micro-Frontends 是把大型前端依業務拆成可**獨立開發、獨立部署**的子應用，由一個 shell 組合起來。

| 做法 | 隔離性 | 優點 | 缺點 |
| --- | --- | --- | --- |
| iframe | 最強 | 簡單、技術棧完全獨立 | 溝通麻煩、SEO 差、彈窗與路由同步困難 |
| Module Federation | 弱 | 執行期共享依賴、體驗一致 | 依賴版本需協調、綁定建置工具 |
| single-spa／qiankun | 中 | 可混用框架、生命週期管理 | 樣式與全域狀態要自己隔離 |
| Web Components | 中 | 標準技術、框架無關 | 與框架整合、SSR 較麻煩 |
| 建置期整合（npm 套件） | — | 最簡單 | 不能獨立部署，不算真正的微前端 |

該用的情況：多個團隊各自負責業務、需要獨立發版、有新舊技術棧並存要漸進遷移（Strangler Pattern）。

不該用：單一團隊、產品規模不大。它解決的是**組織問題**，代價是共享依賴、樣式衝突、跨應用通訊、整體效能、端對端測試都變複雜。
:::

**相關筆記**：[1-1-4 未來趨勢：Web components](./1-1-4.md)、[1-22-6 Strangler Pattern](./1-22-6.md#1-22-6-6)

### Q11. 怎麼建立共用元件庫和 Design System？ <Badge type="tip" text="高頻" /> {#21-11-11}

::: details 標準答案與過程
1. **Design Tokens**：顏色、間距、字級、圓角定義成變數（CSS variables），和設計師在 Figma 同步。
2. **分層**：Primitive（Button、Input）→ 通用 Composite（DatePicker、Table）→ Domain Component（PolicyPeriodPicker）。元件庫只放前兩層。
3. **API 設計**：props 命名一致、受控／非受控都支援、可擴充（slots／children）、無障礙（鍵盤、ARIA）內建。
4. **包裝第三方**：底層用成熟套件，外面包一層自己的 API，未來可替換。
5. **文件**：Storybook 寫各狀態的 story，同時當視覺回歸測試。
6. **發布**：Monorepo 內獨立套件、語意化版本、changelog、破壞性變更有遷移指南。
7. **治理**：貢獻流程、審查標準、使用率追蹤；不要讓業務邏輯滲進元件庫。
:::

**相關筆記**：[1-6-11 去框架化的前端架構](./1-6-11.md)、[1-6-12 高難度通用元件](./1-6-12.md#1-6-12-2)、[1-6-10 標準化工具管理團隊](./1-6-10.md)

### Q12. i18n 要注意什麼？ <Badge type="tip" text="高頻" /> {#21-11-12}

::: details 標準答案與過程
1. **Key 管理**：用有語意的階層 key（`policy.detail.premium`），不要用中文原文當 key；缺字時 fallback 到預設語系並回報。
2. **插值與複數**：用 ICU MessageFormat，不要字串相加（語序不同）：`{count, plural, one {# item} other {# items}}`。
3. **格式化**：日期、數字、貨幣、相對時間都用 `Intl`。

```js
new Intl.NumberFormat('ja-JP', { style: 'currency', currency: 'JPY' }).format(12345)
new Intl.DateTimeFormat('en-US', { dateStyle: 'medium', timeZone: 'Asia/Taipei' }).format(date)
new Intl.RelativeTimeFormat('zh-TW', { numeric: 'auto' }).format(-1, 'day') // 昨天
```

4. **時區**：儲存 UTC，顯示時轉使用者時區；契約日期、生日存日期本身，不要轉成 UTC 零時。
5. **版面**：文字長度可能差 30% 以上；RTL 語系用 CSS 邏輯屬性（`margin-inline-start`）。
6. **載入**：依語系懶載入字典，不要把所有語系打包在一起。
7. **SEO**：每個語系獨立 URL、`hreflang`、`html lang`。
8. **流程**：翻譯檔與 CMS／翻譯平台同步，CI 檢查缺漏的 key。
:::

### Q13. 線上出問題，你怎麼跨前後端排查？ <Badge type="tip" text="高頻" /> {#21-11-13}

**考點**：台達電「production incident response — read logs, triage issues across frontend, backend, and infrastructure」。

::: details 標準答案與過程
1. **止血優先**：影響範圍多大？能否 rollback 或關閉 feature flag？先恢復服務再找根因。
2. **定位層級**：
   - 前端：錯誤監控（Sentry）有沒有新錯誤？是否只發生在特定版本、瀏覽器？
   - 網路：DevTools 看請求狀態碼、耗時、回應內容；CORS 或 4xx／5xx？
   - 後端：用 traceId 對應後端 log；502／504 看閘道與上游服務。
   - 基礎設施：`kubectl get pods`、`describe`、`logs`；最近有沒有部署或設定變更？
3. **常用指令**：

```bash
kubectl logs deploy/api -n prod --since=30m | grep -i error | sort | uniq -c | sort -nr | head
curl -sv https://api.example.com/health
```

4. **事後**：寫 postmortem（時間線、根因、為什麼沒被測到、預防措施），把預防措施變成測試、告警或 CI 檢查。
:::

### Q14. 你怎麼使用 AI 工具開發？怎麼確保品質？ <Badge type="tip" text="基礎" /> {#21-11-14}

**考點**：台達電明列「AI Fluency」。

::: details 標準答案與過程
用途：
- 讀陌生程式碼庫（請 AI 先畫出模組關係與資料流，再自己驗證）。
- 用不熟的語言開發（例如前端工程師讀 Java／Spring 後端程式）。
- 產生測試、樣板程式碼、文件初稿、重構建議。

把關：
1. **我負責判斷，AI 負責加速**：需求、架構決策、取捨由人決定。
2. 產出一律經過型別檢查、測試、Code Review，不直接合併。
3. 安全與授權：不貼機密與個資到外部工具，遵守公司規範；注意套件授權與幻覺出來的不存在 API。
4. 先寫清楚規格與驗收條件再交給 AI，小步提交便於回退。

回答時舉一個具體例子：用 AI 做了什麼、你發現了它哪裡錯、怎麼修正。
:::
