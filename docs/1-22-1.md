## 總綱：一條推理鏈 {#1-22-1-1}

> **Problem → Model → Constraint → Trade-off → Solution**
>
> Solution 永遠最後才出現。AI 很會回答「有哪些 Solution」，人要負責的是「在這個條件下選哪個、為什麼、何時改」。

| 能力層級 | 內容 | AI 可替代程度 |
| --- | --- | --- |
| L1 | 知道 Redis / Kafka / CDN / Sharding 是什麼 | 極高 |
| L2 | 知道 Pattern 怎麼實作 | 高 |
| L3 | 知道什麼問題適合什麼 Pattern | 中 |
| L4 | 能從 Requirement / Constraint 推導架構 | 低 |
| L5 | 能預測 Trade-off、Failure Mode、成本與演進路徑 | 最低 |

**七條架構原則**

1. **Context before Architecture**：沒有需求、限制、NFR，就沒有正確架構。
2. **Measure before Optimize**：沒有 Metrics 就沒有效能優化，不能靠感覺調。
3. **Isolation before Scaling**：先做資源與故障隔離（例如 DB 與 App 分機），再談堆機器。
4. **Query before Hardware**：SQL、Index、Schema、Transaction 優先於升級硬體。
5. **Simple before Distributed**：單機能解就不要分散式。
6. **Evolution over Prediction**：不預測五年後，而是定義「什麼指標到什麼程度才演進」。
7. **AI analyzes; architect decides.**

## 標準決策流程 {#1-22-1-2}

```txt
Business Problem → Requirement → NFR / Constraints → Domain / Data Flow
→ Options → Trade-off → Decision → ADR → Implement / Deploy
→ Metrics → Production Feedback → Evolution
```

## 先建立 Architecture Context（不要直接叫 AI「幫我設計」） {#1-22-1-3}

- 業務：Business Goal、Actors、Core Workflows
- 流量：Traffic、Peak Concurrency、Read/Write Ratio、Data Volume、成長率
- 品質：Availability、Latency、RPO / RTO、Security、Compliance
- 現實：External Integrations、Legacy、團隊人數與技能、維運能力、預算、Time to Market

## ADR / 決策輸出模板 {#1-22-1-4}

```txt
Problem / Current Context / Constraints / Bottleneck or Risk
Options A / B / C
Trade-offs: Performance, Complexity, Cost, Maintainability,
            Availability, Scalability, Security, Reversibility
Recommendation / Why not the alternatives
Trigger for future migration   ← 最重要：例如「read QPS 或 query latency 到 X 才導入 Replica」
Metrics to monitor / Failure modes
```

## 架構師的判斷習慣 {#1-22-1-5}

- 每個技術都要能回答：**現在為什麼需要？不加會怎樣？加了多什麼複雜度？哪個 metric 到多少才值得導入？**
- **新技術沉澱三年**：三年內進入主流、形成穩定生態才上手，順便避開早期顛覆性改版（例：React class → function component → Hooks）。
- **三種常見錯誤**：盲追熱門（十年前把 MongoDB 當所有新專案首選，接手者痛苦）；盲追高併發（人家要直升機你造火箭）；堆技術棧（技術棧與技術債成正比）。
- 例外：一項新技術能**同時取代多項舊技術**才是真價值（例：導入 Kubernetes 劃掉好幾個 DevOps 工具）。
- **設計只是開始**：系統上線到退役前都要負責，運維是最常被架構師忽略的技能。
- 框架選擇：Express.js 本身商業價值低（只是 HTTP 工具），值錢的是框架之上的後端能力。

## 對不同人說話 {#1-22-1-6}

專案負責人、公司技術 VP/CTO、客戶負責人、實際使用者——層級越高時間越少，內容要越濃縮；把技術語言翻成對方關心的利弊。客戶描述的是表層問題（Ford：他們只會要更快的馬），要挖根因再說服他們接受方案。
