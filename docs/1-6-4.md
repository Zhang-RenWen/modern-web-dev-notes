# 1-6-4 網頁效能入門 {#1-6-4}

::: info 改寫（2026-11）
原內容整理自《High Performance Browser Networking》（Ilya Grigorik，2013）第 10 章。已刪掉網站演進史、2013 年的 HTTP Archive 數據與 Yahoo! 瀑布圖截圖，只留到現在仍成立的觀念。更新的部分：`performance.timing` → Navigation Timing Level 2；`rel="subresource"`、`rel="prerender"` → `preload` 與 Speculation Rules；頁面載入時間 → Core Web Vitals。

> 一句話：**大多數網頁慢，是卡在網路往返次數（延遲），不是頻寬**；瀏覽器已經做了很多最佳化，開發者的工作是別擋住它，並給它正確的提示。

## 從「頁面」到「應用程式」，指標也變了 {#1-6-4-1}

早期的網頁是一份文件加上幾張圖，量「`onload` 觸發時間」就夠了。現在的網頁是應用程式：HTML 解析出 DOM、CSS 解析出 CSSOM，JavaScript 又會改動兩者，三者互相阻塞（見 [1-5-3 渲染管線](./1-5-3.md)）；`onload` 之後還在載入資料、還在互動。

所以要量的是**使用者感受到的時間點**：主要內容何時出現（LCP）、點擊多久有反應（INP）、版面穩不穩（CLS），以及對自己業務重要的時間點（例如「第一排商品圖出現」）。指標細節見 [1-6-1](./1-6-1.md)。

**人對時間的感受**（Nielsen 的經驗法則，至今仍常用）：

| 延遲 | 使用者感受 |
| --- | --- |
| 0～100ms | 即時 |
| 100～300ms | 感覺得到一點延遲 |
| 300ms～1 秒 | 「機器在處理」 |
| 超過 1 秒 | 注意力開始轉移，需要進度提示 |
| 超過 10 秒 | 放棄 |

光是 DNS、TCP、TLS 加上一次請求，就可能用掉幾百毫秒，所以「1 秒內出現有意義的內容」非常緊。

## 看懂資源瀑布圖 {#1-6-4-2}

DevTools 的 Network 面板或 [WebPageTest](https://www.webpagetest.org/) 都能看瀑布圖。每個請求分成這幾段：

| 階段 | 慢的話通常是 |
| --- | --- |
| Queueing／Stalled | 同一網域連線數用完（HTTP/1.1 每個網域約 6 條）、優先權較低 |
| DNS | 第三方網域太多 → `dns-prefetch`／`preconnect` |
| Initial connection、SSL | 沒有重用連線、沒用 TLS 1.3 → 合併網域、啟用 HTTP/2、HTTP/3 |
| Waiting（TTFB） | 伺服器處理慢、沒有 CDN 快取 |
| Content Download | 檔案太大 → 壓縮、切分、換格式 |

讀瀑布圖的重點：

- **找「串在一起」的請求**：HTML → CSS → CSS 裡的字型，每多一層就多一次往返。用 `preload` 讓瀏覽器提早發現。
- **看開始渲染的時間點**：不需要等所有資源下載完，畫面就可以開始出現。
- **看頻寬利用率**：多數時間頻寬都閒著，等待的是往返延遲。

## 延遲比頻寬重要 {#1-6-4-3}

Google 的 Mike Belshe 在 2010 年做過實驗（也是 SPDY → HTTP/2 的起點）：

- **頻寬**從 1 Mbps 增加到 5 Mbps，頁面載入時間明顯下降；超過 5 Mbps 後幾乎沒有改善。
- **延遲**每降低 20ms，頁面載入時間就穩定地跟著下降。

原因是網頁由大量小檔案組成，每個都要經過 DNS、TCP 握手、TLS、TCP 慢啟動，這些都以「往返次數」計算，頻寬再大也省不掉。影片串流這種大檔案傳輸才真的受頻寬限制。

所以提升速度的方向是：**減少往返次數**（重用連線、HTTP/2 多工、TLS 1.3、HTTP/3 的 0-RTT）、**縮短每次往返的距離**（CDN 把內容放到離使用者近的地方）。傳輸層細節（TCP、TLS、HTTP/2、HTTP/3）屬於網路協定，不在本站範圍。

## 實驗室測試與真實使用者資料 {#1-6-4-4}

| | 實驗室（Synthetic） | 真實使用者（RUM） |
| --- | --- | --- |
| 工具 | Lighthouse、WebPageTest、CI 裡的效能測試 | `web-vitals`、Navigation／Resource／User Timing API、CrUX |
| 優點 | 可重複、能在上線前抓到退步 | 反映真實的裝置、網路、快取狀態、地區 |
| 缺點 | 測不出真實使用者的多樣性 | 資料雜、要先上線才有 |

- 兩者都要。實驗室測試搭配**效能預算**（例如「JS 不超過 300KB」「LCP 不超過 2.5 秒」），超過就讓 CI 失敗。
- 分析 RUM 資料**不要看平均值**：分布通常是長尾，要看中位數、第 75 百分位（Core Web Vitals 的標準）、第 95 百分位，並依裝置、網路、地區分開看。

```js
// Resource Timing：每個資源的各階段時間
for (const r of performance.getEntriesByType('resource')) {
  console.log(r.name, { dns: r.domainLookupEnd - r.domainLookupStart, ttfb: r.responseStart - r.requestStart })
}
// User Timing：自訂區段
performance.mark('task-start')
doWork()
performance.measure('task', 'task-start') // 從標記到現在
```

跨網域資源要回應 `Timing-Allow-Origin` 標頭，才拿得到詳細時間。

## 瀏覽器幫你做的最佳化，以及怎麼給提示 {#1-6-4-5}

瀏覽器會自動：用**預載掃描器**（preload scanner）在 HTML 還在解析時就先抓到後面的資源；依類型排**優先權**（CSS、同步 JS 高，畫面外的圖片低）；依瀏覽紀錄**預先解析 DNS、預先連線**。

開發者要做的是**別擋住它**：

- CSS 放在 `<head>` 盡早載入，它會阻塞渲染。
- 非必要的 JS 加 `defer` 或 `type="module"`，不要阻塞 HTML 解析。
- 關鍵資源要寫在 HTML 裡讓掃描器看得到；只在 JS 裡動態插入的資源，瀏覽器很晚才會發現。
- 伺服器**串流輸出 HTML**：先送出 `<head>`（CSS、預載提示），再慢慢查資料產生內容，瀏覽器可以提早開始下載。

以及**給正確的提示**：

| 提示 | 用途 |
| --- | --- |
| `<link rel="preconnect" href="https://cdn.example.com">` | 提早完成 DNS + TCP + TLS（只對確定會用到的 1～3 個網域） |
| `<link rel="dns-prefetch">` | 只預先解析 DNS，成本更低 |
| `<link rel="preload" as="font" crossorigin>` | 本頁一定會用到、但瀏覽器很晚才會發現的資源（字型、LCP 圖片） |
| `fetchpriority="high"`／`"low"` | 調整單一資源的優先權 |
| `<link rel="prefetch">` | 下一頁可能用到的資源，閒置時下載 |
| Speculation Rules（`<script type="speculationrules">`） | 預先載入或預先渲染整個下一頁，點了立刻顯示（Chromium 支援，取代舊的 `rel="prerender"`） |
| `103 Early Hints` | 伺服器還在產生回應時，先告訴瀏覽器要預載什麼（取代已被移除的 HTTP/2 Server Push） |
