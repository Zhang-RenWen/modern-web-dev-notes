> **總原則：底層原理深學，架構能力重押，工具實作即可，語法交給 AI，面試八股另外建立快取。**
>
> 細節外部化，決策模型內部化。Don't memorize implementations. Build mental models.

## 技術有不同的折舊率 {#1-24-3-1}

| 層級 | 例子 | 策略 |
| --- | --- | --- |
| **底層原理** | OS、網路、資料庫、併發、資安、資料結構與演算法 | 深入理解，長期持有 |
| **架構能力** | 資料流、系統設計、一致性、快取、佇列、權限模型、Trade-off | 重點投資 |
| **工具／框架** | Vue、React、Fastify、NestJS、Docker、K8s | 理解用途並實際做過 |
| **短期細節** | API 語法、CLI 指令、設定參數 | 不硬背，查文件或問 AI |
| **過時知識** | 舊版 API、淘汰的工具、歷史 workaround | 知道存在即可 |

**腦袋與 AI 的分工**：原理、系統模型、關鍵字、Trade-off、問題拆解、架構判斷放在自己腦中；語法、樣板、CLI、API 細節、版本差異、實作範例交給 AI 與文件。危險不是用 AI，而是**自己沒有心智模型，只能判斷 AI 的答案「看起來像不像真的」**。目標是：知道問題是什麼，也知道 AI 有沒有在胡說。

職涯方向的參考：不一定要成為單一領域的極深專家，而是**工程實作 × 系統架構 × 商業理解 × 技術決策**。「打通後端」的定義是能獨立理解、設計、實作並部署一套完整後端服務；競爭力不是能講繼承、多型、API，而是能講為什麼選這個方案、成本收益、擴展性、維護成本、技術風險、商業限制與演進路徑。

## 筆記的新用途：建立認知地圖 {#1-24-3-2}

- 舊流程：蒐集 → 整理 → 背 → 怕忘 → 複習。
- 新流程：**篩選 → 建索引 → 理解核心 → 需要時由 AI／文件補齊**。

例：資料庫 → 交易 → ACID → 隔離等級 → Lock／MVCC → 索引 → 複寫 → 分片。不必立刻講出每個細節，但要知道「這個問題屬於哪一層、往哪裡挖」。

優先放進腦袋的順序：OS／記憶體 → 網路 → 資料庫／交易／索引 → 併發 → 資安／認證 → 快取／佇列 → 分散式系統 → 系統設計 → 資料建模 → 複雜度與 DSA；再往上是**抽象、問題拆解、Trade-off、系統邊界**。

## 實作仍然必須做 {#1-24-3-3}

架構經驗來自：**實作 → 出問題 → Debug → 發現限制 → 理解 Trade-off → 抽象成經驗**。AI 能把知識講清楚，但替代不了「在終端機裡真的遇過 permission denied」「看到延遲就直覺先查 DNS 與 TCP 握手」這種踩坑直覺。實作是為了長出心智模型，不是為了背框架。

- 讀到理論就做**小實驗驗證**：例如讀到檔案系統快取，就用 Node.js 讀 1GB 檔案，比較第一次與第二次的速度。
- 學新工具（例如 D3.js）不必先刷題或上完整課程：先跑範例，卡在哪裡再補背後的數學或原理（卡在 `scaleLog` 就補對數、卡在 `forceSimulation` 就補向量）。

## 實務案例庫：取代抄書 {#1-24-3-4}

按**主題**分類，不按書的章節：效能（debounce、throttle、虛擬捲動、懶載入）、非同步（重試、取消請求、並行與序列）、資安（XSS、CORS、token refresh）、工程化、TypeScript。

每個案例固定四欄：**情境 → 錯誤示範 → 最佳實踐（可直接用的程式碼）→ 延伸 Trade-off**。

例：多個 API 並行，任一失敗不能整組掛掉。
- 錯誤：`Promise.all([a(), b(), c()])`，一個 reject 全部失敗。
- 做法：

```ts
const results = await Promise.allSettled([a(), b(), c()])
results.forEach((r) => {
  if (r.status === 'fulfilled') console.log(r.value)
  else console.error(r.reason)
})
```

- Trade-off：金融交易能不能容忍部分成功？很可能反而需要全有全無。

**Side project 就是筆記**：關鍵程式碼寫「為什麼這樣寫」的註解；每個專案的 README 寫架構、用到的知識點、踩過的坑與解法，以及「面試被問到這段要怎麼解釋」。

## 讀別人的程式碼要問 Why，不只是學 How {#1-24-3-5}

- 軟體的起點是問題，不是程式碼。直接讀原始碼，就像空降到決策樹的中段，容易瞎子摸象。
- 品質標準（可靠、可擴展、可測試、可移植、可重用）只管非功能面，不保證做法本身正確。**案例：Log4j**——Apache 專案、品質控管到位，但根本錯誤在於把「依外部文字執行查詢」這種高權限行為暴露給外部輸入，照著學只會複製更多漏洞。
- 接手專案先補**業務背景**（市場、競品、使用情境），才看得懂技術決策；只有 know-how 沒有 know-why，團隊最後常選擇重寫，舊程式就變成 legacy。
- 自己做決策時，留下「為什麼」的紀錄（ADR、會議紀錄）。

## 把演算法與 Schema 用在實務 {#1-24-3-6}

- **Big-O 的實務理解**：不是背公式，而是判斷「資料量放大後，成本怎麼成長、哪裡先成為瓶頸」。成本不只 CPU 與記憶體，還有 DB I/O、DOM 與渲染、網路、GC。
- **後端**：List 線性搜尋改 Map／Set 查找；避免 O(n²) 巢狀迴圈與 N+1 查詢；善用索引、批次與快取。
- **前端**：注意渲染中重複的 `find`／`filter`／`map`、大型列表、重複的事件監聽、整棵子樹更新；用正規化狀態、虛擬化、分頁、記憶化、事件委派控制成本。
- **CSS 與瀏覽器**：真正重要的是 layout／paint／composite 與大量 DOM 操作；批次更新、用 `transform`／`opacity`、控制 DOM 規模，比糾結選擇器更實際。
- **Schema 設計不是在畫表，而是在設計未來的查詢路徑**：判斷 entity、關係、WHERE／JOIN／ORDER BY、資料量成長、索引、正規化與反正規化。多對多用中介表；核心查詢欄位不要隨便塞 JSON；寫入的核心資料偏正規化，Dashboard、搜尋、報表可以另建 read model、彙總表、materialized view。
- 真正的後端能力是把理論壓成可運作的生產系統：migration、transaction、認證與 RBAC、連線池、重試、冪等、競態與鎖、佇列、快取、日誌與監控、Docker、Nginx／TLS、環境變數與密鑰、CI/CD、部署。完成標準不是功能很多，而是「真實資料自己進來 → 處理 → 儲存 → 聚合 → API → Dashboard → 告警 → 部署 → 出問題可以追」。

## CS 基礎怎麼讀 {#1-24-3-7}

- 投入程度參考：DSA 練到 NeetCode 150、以 Medium 為主即可，不追 Hard 或競賽題；線性代數除非走 AI／資料方向，否則優先度較低。
- 讀法（取自跨考資工所的心得，方法仍適用）：
  - **資料結構**：每看完一個結構就自己用程式實作一次（例如 heapsort），一定會卡住，卡住的地方就是原本以為懂、其實沒懂的地方。重點是樹、排序、時間複雜度。
  - **演算法（CLRS）**：只讀「問題是什麼 + 怎麼解」，跳過幾十頁的正確性證明；累積「看到 DAG → 拓樸排序 → DFS」這類聯想反射。
  - **計算機組織**：大部分不用背，每個設計都有原因，想通就順，可以和 OS 一起讀。
  - **作業系統**：內容多且雜、容易忘，先拿基本分，遇到沒看過的再查恐龍書。
  - 該心得作者的 CP 值排序：線代＝計組 ＞ 離散＝資結 ＞ OS＝演算法；考古題要寫，會出現重複題。
  - 來源：[第一次跨考資工所就上手](https://home.gamer.com.tw/creationDetail.php?sn=2398590)

## 技術案例速記 {#1-24-3-8}

- **RAG 基本流程**：切 chunk 時保留 overlap（讓檢索到的片段語意連貫）→ Embedding 成向量 → 存 Vector DB → 查詢時把問題也 embedding，找距離最近的向量。GraphRAG 在此之上再建圖描述文本關係，能理解大範圍內容，但建圖與維護成本高，不適合輕量任務（見 [1-22-9](./1-22-9.md#1-22-9-2)）。
- **模擬器不等於真實硬體**：自寫的 OS 在 QEMU 正常、上 RISC-V 開發板卻沒有輸出 → QEMU 預設會把 `.bss`（未初始化的全域變數）清零，實機不會。教訓：環境差異是排錯第一個要懷疑的方向。
