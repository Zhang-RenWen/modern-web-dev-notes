# 1-7-6 同構應用 {#1-7-6}

::: info 改寫（2026-11）
原內容整理自 2019 年前的書籍，示範用 Koa + webpack + React Router 手動搭建 SSR。現在多半直接用 Next.js、Nuxt、React Router（原 Remix）這類框架，所以已改成「每個問題的原理 + 框架怎麼解決」。過時的工具（react-apollo 的做法、`isomorphic-style-loader`、`componentWillMount`）只留一句說明。
:::

> 一句話：**同一份元件程式碼，在伺服器產生 HTML（首屏快、搜尋引擎看得到），到了瀏覽器再「接手」變成可互動的應用（hydration）。**

## 渲染模式怎麼選 {#1-7-6-2}

| 模式 | HTML 在哪裡產生 | 適合 |
| --- | --- | --- |
| CSR（純前端渲染） | 瀏覽器執行 JS 後 | 後台、登入後才看得到的應用 |
| SSG（靜態生成） | 建置時一次產生 | 文件、部落格、行銷頁（本站就是） |
| ISR／快取 SSR | 第一次請求時產生，之後快取一段時間 | 商品頁這類「會變但不用即時」的內容 |
| SSR | 每次請求都在伺服器產生 | 個人化、需要即時資料又要 SEO 的頁面 |
| 串流 SSR | 先送出外框，資料好了再分段送出 | 頁面有慢的區塊時，不讓整頁一起等 |
| Server Components | 元件只在伺服器執行，不送 JS 到瀏覽器 | 大量靜態內容、直接讀資料庫的頁面 |
| Islands（Astro） | 頁面大部分是靜態 HTML，只有互動的「島」載入 JS | 內容網站 |

多數網站並沒有即時 SEO 的需求，全站 SSR 會大幅增加維運複雜度（要有 Node 伺服器、要處理快取與記憶體），先考慮 SSG 或預渲染。各模式在應用架構上的取捨見 [1-8-1](./1-8-1.md#1-8-1-8)。

## 同構要處理的問題 {#1-7-6-3}

| 問題 | 原因 | 框架的解法 |
| --- | --- | --- |
| 路由 | 伺服器沒有 `window.location`，要依請求網址找頁面 | 伺服器用請求網址渲染（以前是 `StaticRouter`），框架用檔案路由自動處理 |
| 伺服器端資料 | 渲染前要先拿到所有資料 | 路由層級的 `loader`／`getServerSideProps`，或 Server Component 直接 `await`。以前的做法是在元件上掛靜態方法 `loadData`，伺服器先找出所有符合的路由再一起請求 |
| 注水與脫水 | 伺服器拿到的資料要交給瀏覽器，不然瀏覽器會重新請求一次 | 框架自動把資料序列化進 HTML，瀏覽器端直接使用 |
| 只有瀏覽器才有的 API | 伺服器沒有 `window`、`document`、`localStorage` | 放進 `useEffect`／`onMounted`（只在瀏覽器執行），或標成只在用戶端渲染 |
| hydration 不一致 | 伺服器和瀏覽器渲染結果不同（日期時區、隨機數、`typeof window` 分支） | 讓兩邊輸入一致；只能在瀏覽器決定的內容延後到掛載後再顯示 |
| 樣式 | 伺服器只回 HTML，CSS 晚到會閃一下 | 建置時把 CSS 抽成檔案放進 `<head>`；CSS-in-JS 要額外收集樣式（以前用 `isomorphic-style-loader`），零執行期的方案（CSS Modules、Tailwind、vanilla-extract）最省事 |
| `<title>`、`<meta>` | 每頁不同，而且要在伺服器就輸出 | React 19 可以直接在元件裡寫 `<title>`；Next.js 用 metadata API；Vue 用 `useHead`。以前用 react-helmet |
| 404 狀態碼 | 找不到頁面時只渲染了 NotFound 元件，HTTP 狀態仍是 200 | 框架的 `notFound()`；自己做要把「找不到」從渲染結果傳回伺服器設定狀態碼 |

## SSR（Hydration）的登入 {#1-7-6-1}

- 伺服器拿不到 `localStorage`，所以登入狀態要放在 **HttpOnly Cookie**。瀏覽器請求頁面時會帶上 Cookie，伺服器用它換取或驗證 token，再於渲染 HTML 前呼叫後端 API。
- 伺服器代替使用者呼叫 API 時，要**轉送**原請求的 Cookie 或授權資訊；不同使用者的資料不能被快取共用（回應標 `private`，或依使用者區分快取 key）。
- 多數網站沒有即時 SEO 需求，全 SSR 會大幅提高複雜度；優先考慮 **Prerender**。

## 安全：序列化資料造成的 XSS {#1-7-6-4}

把伺服器資料塞進 HTML 時，常見寫法是：

```js
html += `<script>window.__DATA__ = ${JSON.stringify(data)}</script>`
```

如果資料裡有使用者輸入的 `</script><script>alert(1)</script>`，`JSON.stringify` 不會跳脫，就會提早結束 `<script>` 並執行攻擊者的程式碼。要用會跳脫 `<`、`>`、`/`、` ` 的序列化函式（`serialize-javascript`、`devalue`），或改成 `<script type="application/json">` 再用 `textContent` 讀取。框架內建的序列化都處理好了，自己手寫時才要注意。`dangerouslySetInnerHTML`、`v-html` 也有同樣的風險。

## 效能 {#1-7-6-5}

- **快取**是 SSR 最重要的最佳化：整頁快取在 CDN（依使用者區分的頁面不行）、資料層快取、元件級快取。
- **串流**：先送出 `<head>` 和外框，讓瀏覽器開始下載 CSS、JS，慢的區塊用 `Suspense` 包起來晚點送。
- **只 hydrate 需要互動的部分**：Server Components、Islands 都是在減少瀏覽器要下載與執行的 JS。
- 伺服器端渲染是同步的 CPU 工作，元件樹太大會拖慢 TTFB；監控伺服器的渲染時間。
