## 初始設定 {#1-7-3-1}

```bash
git config --global user.name "Name"
git config --global user.email "me@example.com"
git config --local user.email "other@example.com"   # 只對這個專案生效
git config --global core.editor "code --wait"        # 不想被 Vim 卡住
git config --global alias.st status
git config --global alias.l "log --oneline --graph"
```

- `.git` 目錄就是全部的版控：專案裡其他東西刪了都救得回來，`.git` 刪了就沒了。

## add / commit 的坑 {#1-7-3-2}

- `add` 之後又改了檔案，要再 `add` 一次；commit 只會收進暫存區裡的版本。
- `commit -a` 只對已追蹤的檔案有效，新檔案還是要先 `add`。
- 空目錄無法 commit（Git 只看內容），慣例放一個 `.gitkeep`。
- Git 2.x 起 `git add .` 與 `git add -A` 對新增、修改、刪除的處理已相同（差別只剩範圍：前者是目前目錄以下）。
- 只想 commit 檔案的一部分：`git add -p`（y 加入、n 跳過、s 切更細、e 手動編輯）；反向丟棄部分修改：`git restore -p`。
- 訊息原則：清楚、別帶情緒、別寫「bug fixed」這種模糊字，有 issue 就附編號（`fix: #34 …`）。

## 查歷史 {#1-7-3-3}

```bash
git log --oneline --graph --all --decorate
git log --author="Sherly\|Eddie"     # 指定作者
git log --grep="login"              # 搜 commit 訊息
git log -S "Ruby"                   # 搜檔案內容的增刪
git log --since="9am" --until="12pm"
git log -p welcome.html             # 單一檔案每次改了什麼
git blame -L 5,10 index.html        # 某幾行最後是誰改的
```

## 刪檔、改名、停止追蹤 {#1-7-3-4}

- `git rm file`（刪檔並放進暫存區）、`git mv a b`（改名）。Git 依內容算 SHA，改名不產生新 blob，只產生新 tree。
- `git rm --cached file`：檔案留在硬碟，但不再被 Git 追蹤。

## .gitignore {#1-7-3-5}

- 規則只對「之後才加入」的檔案有效；已被追蹤的檔案要先 `git rm --cached` 才會開始被忽略。
- 強制加入被忽略的檔案：`git add -f file`；清掉所有被忽略的檔案：`git clean -fX`。
- 各語言範本：[github/gitignore](https://github.com/github/gitignore)

## 修改最後一次 commit {#1-7-3-6}

- 改訊息：`git commit --amend -m "新訊息"`
- 補漏掉的檔案：`git add 漏的檔案 && git commit --amend --no-edit`
- amend 會產生新 SHA，已經 push 的不要改。更早的 commit 要用 `rebase -i`。

## reset 是「前往」不是「刪除」 {#1-7-3-7}

| 模式 | 拆出來的變更去哪 | 工作目錄 | 暫存區 |
| --- | --- | --- | --- |
| `--mixed`（預設） | 丟回工作目錄 | 不變 | 清掉 |
| `--soft` | 丟回暫存區 | 不變 | 不變 |
| `--hard` | 直接丟掉 | 清掉 | 清掉 |

- `HEAD^` 前一個、`HEAD~3` 前三個。commit 本身沒消失，只是暫時沒有指標指向它。
- **後悔藥**：`git reflog`（本機 HEAD 移動紀錄，預設保留約 90 天）→ `git reset --hard HEAD@{n}`；剛做完 reset / merge / rebase 也可直接 `git reset --hard ORIG_HEAD`（只記最後一次）。

## HEAD 與 detached HEAD {#1-7-3-8}

- `.git/HEAD` 內容是 `ref: refs/heads/main`；分支本身只是一個存著 commit SHA 的 40 字元檔案。
- 進入 detached HEAD：`checkout <sha>`、`checkout origin/dev`、`checkout <tag>`。此時可以看、可以 commit，但切走前沒建分支就會變孤兒。
- 離開：`git switch main`，或要保留就 `git switch -c rescue`。
- 要追蹤遠端分支應該用 `git switch dev`（自動追蹤 origin/dev）或 `git switch -c dev origin/dev`，不要直接 checkout `origin/dev`。

## 分支操作 {#1-7-3-9}

- 改名 `git branch -m old new`；刪除 `-d`（未合併會被擋）、`-D`（強制）。目前所在的分支不能刪。
- 從舊 commit 開分支：`git switch -c hotfix-legacy <sha>`（或 tag）。
- 誤刪未合併分支：`git reflog` 找最後的 SHA → `git branch 名稱 <sha>`。
- 改到一半切分支：不衝突會把修改帶過去；會覆蓋到就被擋 → `git stash`（含新檔案用 `stash -u`）。

## merge 與 rebase {#1-7-3-10}

- merge 是三方合併（共同祖先 + 兩邊），產生有兩個 parent 的 merge commit；「合併」只是新增一個交會點，兩條歷史都還在。
- 可以 fast-forward 時預設直接快轉；`--no-ff` 強制留下 merge commit，保留「曾有個功能分支」的痕跡。
- A 合併 B 和 B 合併 A 內容可能相同，但 parent 順序不同，SHA 也不同。
- rebase 是把 commit「重放」到新基底上，產生新的 D'、E'；舊 commit 變孤兒，之後被 gc 清掉。rebase 前可先 `git branch backup-before-rebase`。
- 取消 rebase：進行中 `git rebase --abort`；已完成 `git reset --hard ORIG_HEAD` 或 reflog。
- **`rebase -i HEAD~N`**：`reword` 改訊息、`squash` 合併、`edit` 停下來拆 commit（`reset HEAD~1` 後用 `add -p` 分批 commit 再 `rebase --continue`）、刪掉一行就是刪 commit、調換行序就是調順序。
- 二進位檔衝突無法手改：`git checkout --ours file` 或 `--theirs file` 選一邊，再 `add`。

## revert / reset / rebase 怎麼選 {#1-7-3-11}

| 指令 | 改寫歷史 | 適用 |
| --- | --- | --- |
| revert | 否，新增一個反向 commit | 已 push、團隊共用的歷史 |
| reset | 是，移動 HEAD | 本機還沒 push 的 commit |
| rebase | 是，重寫 commit | 整理自己的 feature 分支、跟上 main |

一句話：**公開歷史用 revert，本地實驗用 reset，自己的分支整理用 rebase。**

## Tag {#1-7-3-12}

- 輕量標籤 `git tag v1.0.0` 只是指標；附註標籤 `git tag -a v1.0.0 <sha> -m "msg"` 是獨立物件，有 tagger、時間、訊息、可簽名，**發版用附註標籤**。
- 推送：`git push origin v1.0.0` 或 `--tags`；刪除遠端標籤：`git push origin --delete v1.0.0`。一個 commit 可以有多個 tag。

## Stash {#1-7-3-13}

- `stash` / `stash -u` / `stash list` / `stash show -p` / `stash apply`（保留）/ `stash pop`（套用並刪除）/ `stash drop` / `stash clear` / `stash branch 新分支`。
- stash 本質是一組特殊 commit（工作目錄、暫存區、未追蹤檔各一個），存在 `refs/stash`；clear 之後就沒了。

## cherry-pick {#1-7-3-14}

- `git cherry-pick <sha>`、多個 `<a> <b> <c>`、連續範圍 `A^..C`（含 A）、`-n` 只套用不 commit；衝突處理同 rebase（`--continue` / `--abort`）。產生的是新 SHA，濫用會讓歷史混亂。

## 徹底移除誤上傳的機密檔 {#1-7-3-15}

```bash
cp -r repo repo-backup                          # 先備份
git filter-repo --path secret.txt --invert-paths  # 取代已不建議的 filter-branch
git push --force
```

- 補充：密碼或金鑰一旦推到遠端就應視為已外洩，**一定要同時作廢並更換**，改寫歷史只是清理。
- 舊的 filter-branch 會把原狀態備份在 `refs/original/refs/heads/<branch>`，可用 `git reset --hard refs/original/refs/heads/main` 還原。

## 物件底層 {#1-7-3-16}

- Blob 的 SHA-1 = hash(`"blob " + 長度 + "\0" + 內容`)，與時間、檔名無關；可用 `git hash-object` 驗證。存在 `.git/objects/前2碼/後38碼`（分目錄是為了避免單一目錄檔案過多）。
- Commit → Tree → Blob 是有向無環圖（DAG），不是真的目錄階層；checkout 就是沿著這串把快照「拎」回工作目錄。
- 物件起初完整存放，`git gc`（物件過多或 push 時自動觸發）會打包成 packfile 並做差異壓縮。
- dangling：沒有其他物件或分支直接指向；unreachable：連 reflog 都走不到。`git fsck --unreachable` 可撈出來，`git show <sha>` 看內容，`git branch 名稱 <sha>` 救回。所有 unreachable 都是 dangling，反之不一定。

## 遠端協作 {#1-7-3-17}

- clone：HTTPS（要 Personal Access Token）或 SSH（`git@github.com:user/repo.git`，設好金鑰免輸入）。clone 是第一次取得整個專案，pull 是更新已有的專案。
- `git push -u origin feature/x`：第一次推送並設定上游，之後直接 `git push / pull`；`git branch -vv` 看追蹤關係。
- `git push origin master:main` 會把本地 master 推到遠端 main，小心覆蓋。
- 刪遠端分支 `git push origin --delete feature/x`；清掉本機的遠端殘影 `git fetch -p`。
- 必須強推時用 `git push --force-with-lease`（遠端若有別人的新 commit 就拒絕），不要用 `-f`。共用分支、審查中的 PR、受保護分支都不要強推。

## 推不上去的常見原因 {#1-7-3-18}

| 錯誤訊息關鍵字 | 原因 | 解法 |
| --- | --- | --- |
| `fetch first` / `rejected` | 遠端有你沒有的 commit | `git pull --rebase` 再 push |
| `protected branch` / `GH006` | 受保護分支 | 推到 feature 分支並開 PR |
| `Authentication failed` | 密碼已不支援、Token 失效 | 用 PAT 或 SSH key |
| `non-fast-forward` | 你改寫過歷史 | 確認無人受影響後 `--force-with-lease` |
| `src refspec … does not match any` | 分支名打錯或還沒建立 | `git branch` 確認後再推 |

## Fork 開源專案的工作流 {#1-7-3-19}

```bash
git clone git@github.com:me/project.git
git remote add upstream https://github.com/author/project.git
git fetch upstream && git rebase upstream/main   # 跟上原專案
git switch -c fix-typo                           # 不要直接改 main
git push origin fix-typo                         # 再到 GitHub 對 upstream 開 PR
```

## Git Flow 五種分支的規則 {#1-7-3-20}

- master：只放可上線版本，只接受合併，並在上面打版本 tag。
- develop：開發基礎，feature 從這裡切、做完合回來。
- hotfix：從 master 切出修緊急問題，修完**同時**合回 master 和 develop（不合回 develop，下次發版問題會再出現；不從 develop 切，是因為 develop 上可能有未完成功能）。
- release：develop 夠成熟時切出做上線前測試，完成後同時合回 master 和 develop。
