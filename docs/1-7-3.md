# 1-7-3 React: 資料狀態管理 {#1-7-3}

::: info 改寫（2026-11）
原內容整理自 2019 年前的書籍，當時的主流是 Redux + `connect` 與 MobX。已更新為現在的分工：伺服器資料交給 TanStack Query、SWR 這類資料請求函式庫；全域的用戶端狀態用 Redux Toolkit 或 Zustand；Vue 用 Pinia（取代 Vuex）。「`connect` 的位置」與「狀態扁平化」這兩個仍然重要的原則保留。
:::

> 一句話：**先分清楚是哪一種狀態，再決定放哪裡**。大部分狀態根本不需要全域狀態管理。

## 為什麼需要狀態管理 {#1-7-3-1}

例：頁面上有好幾個「訂閱」按鈕，點了其中一個，其他的也要變成「已訂閱」。用 jQuery 的寫法是在每個按鈕的事件裡手動改其他按鈕，按鈕一多就亂掉。

元件化的解法是：讓所有按鈕都依同一個狀態 `isSubscribed` 渲染，改狀態，畫面自己跟著變。問題就變成「這個狀態放在哪裡、誰可以改」。需要狀態管理的訊號：

- 好幾個沒有上下層關係的元件要讀同一份資料（例如購物車數量出現在頁首、購物車頁、結帳頁）。
- 一個元件要改另一個遠方元件的狀態。
- 要做復原／重做、時間旅行除錯這類需要記錄每次變化的功能。

## 先分類，再決定放哪裡 {#1-7-3-2}

| 狀態種類 | 例子 | 放哪裡 |
| --- | --- | --- |
| 元件內的 UI 狀態 | 輸入框內容、彈窗開關、hover | `useState`；只有一兩層要用就往上提到共同父元件 |
| **伺服器資料**（遠端資料的快取） | 商品清單、使用者資料 | **TanStack Query、SWR、RTK Query**：處理快取、重新整理、重試、競態，這部分以前常被硬塞進 Redux |
| 網址狀態 | 目前分頁、篩選條件、搜尋關鍵字 | URL query string（可分享、重新整理不會遺失） |
| 表單狀態 | 欄位值、驗證錯誤 | React Hook Form 或元件內狀態 |
| 全域用戶端狀態 | 登入者、主題、購物車、跨頁的操作流程 | Context（變化少的）、Zustand、Redux Toolkit、Jotai；Vue 用 Pinia |

把伺服器資料移出去之後，真正需要全域 store 的狀態通常很少。

## Context 的限制 {#1-7-3-3}

`Context` 解決的是「層層傳 props」，不是效能問題：**Provider 的 value 一變，所有用到這個 Context 的元件都會重新渲染**，就算它只用到其中一個欄位。

- 適合變化少的資料：主題、語系、登入者。
- 高頻變化的資料（購物車、即時狀態）放 Context，要拆成多個 Context，或改用可以「只訂閱一部分」的 store。

## Redux：現在怎麼寫 {#1-7-3-4}

舊寫法要分開寫 action type、action creator、reducer，還要手動保持不可變，模板程式碼很多。現在官方推薦 **Redux Toolkit**：

```js
const cartSlice = createSlice({
  name: 'cart',
  initialState: { items: [] },
  reducers: {
    added(state, action) {
      state.items.push(action.payload) // 內建 Immer，可以直接「改」，實際產生新物件
    },
  },
})
export const { added } = cartSlice.actions

// 元件裡：只訂閱需要的那一部分，其他部分變了不會重新渲染
const count = useSelector((state) => state.cart.items.length)
const dispatch = useDispatch()
dispatch(added(product))
```

舊書提到的兩個原則，現在仍然成立：

**1. 在用到資料的地方訂閱，不要只在最頂層訂閱**

頁面有 Profile、Feeds、Images 三區，如果只在 Page 讀整個 store 再往下傳，任何一區的資料變了，整頁都會重新渲染。讓三個元件各自用 `useSelector` 選自己需要的部分（以前是各自 `connect` + `mapStateToProps`），變的是哪一區就只有哪一區重新渲染。

**2. 狀態要扁平化（正規化）**

```js
// 巢狀：改某個作者的名字，要一路複製 articles → comments → author
{ articles: [{ id: 1, comments: [{ id: 9, author: { id: 3, name: 'Ann' } }] }] }

// 扁平：像資料庫一樣用 id 互相參照，改作者只動 users 一處
{
  articles: { byId: { 1: { id: 1, commentIds: [9] } }, allIds: [1] },
  comments: { byId: { 9: { id: 9, authorId: 3 } } },
  users: { byId: { 3: { id: 3, name: 'Ann' } } },
}
```

Redux Toolkit 的 `createEntityAdapter` 會幫你產生這種結構和常用的增刪改函式。

## 各方案怎麼選 {#1-7-3-5}

| 方案 | 特色 | 適合 |
| --- | --- | --- |
| Redux Toolkit | 單一 store、action 可追蹤、DevTools 時間旅行、生態完整 | 大型團隊、狀態變化需要稽核或重播 |
| Zustand | 一個 hook 就是一個 store，幾乎沒有模板程式碼，可選擇只訂閱部分欄位 | 中小型專案的全域狀態 |
| Jotai、Recoil 風格 | 狀態拆成很多小 atom，元件訂閱需要的 atom | 狀態之間有很多衍生關係 |
| MobX | 響應式：直接改物件，用到的元件自動更新（類似 Vue） | 喜歡可變資料寫法、物件導向的領域模型 |
| Pinia（Vue） | Vue 官方，取代 Vuex，支援 TypeScript 與 Composition API | Vue 專案 |

React 元件設計原則見 [1-7-2](./1-7-2.md#1-7-2-5)。
