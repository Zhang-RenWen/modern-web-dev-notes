## 渲染流程 {#1-3-3-1}

```txt
HTML → DOM Tree
CSS  → CSSOM Tree
DOM + CSSOM → Render Tree → Style → Layout → Paint → Composite → 顯示
JavaScript 由 JS Engine 執行，可能改 DOM／CSSOM 而觸發重新 Layout／Paint
```

- `display: none` 不進 Render Tree；`visibility: hidden` 仍佔版面。

| 階段 | 什麼會觸發 | 成本 |
| --- | --- | --- |
| Layout（Reflow） | 改 width／height／margin／top／left／font-size／display、增刪 DOM、讀 offsetWidth 後又改樣式 | 最貴 |
| Paint（Repaint） | 改 color、background-color、box-shadow、border-color | 中 |
| Composite only | 只改 transform、opacity | 最便宜，動畫首選 |

- 動畫用 `transform: translateX()`、`opacity`，不要用 `left`、`width`。
- 修正：JS 是由 **JavaScript Engine** 執行（Chrome／Edge 的 V8、Firefox 的 SpiderMonkey、Safari 的 JavaScriptCore），包含 parser、interpreter、JIT、GC，不只是「Interpreter」。
- 瀏覽器模組圖（UI、Browser Engine、Rendering Engine、Networking、JS Engine、Data Persistence、UI Backend）只是概念圖；現代瀏覽器是多程序架構：Browser、Renderer、GPU、Network、Storage process，加上 main thread、compositor thread、worker。

::: tip 面試版回答
使用者輸入 URL 後，瀏覽器先解析 URL、檢查快取與可重用連線，再做 DNS 查詢取得 IP。HTTP/1.1／HTTP/2 通常建立 TCP 連線，HTTPS 再做 TLS handshake；HTTP/3 則走 QUIC over UDP。連線後送出 HTTP request、收到 response。瀏覽器解析 HTML 建 DOM、解析 CSS 建 CSSOM，兩者合成 render tree，接著計算 style、layout、paint，最後 composite 顯示。JS 由 JS Engine 執行，可能修改 DOM 或 CSSOM，造成重新 layout、repaint 或 composite。
:::

網路段的細節見 [1-18-18 從輸入網址到收到回應](./1-18-18.md)。

## 行動裝置除錯 {#1-3-3-2}

- iOS Safari 遠端除錯：Mac Safari → 設定 → 進階 → 勾「顯示開發」，接手機即可檢查全部內容。
- iOS Chrome：網址列輸入 `chrome://inspect` 只能看 console；其餘用 Mac Chrome 模擬。
- iPhone 上的瀏覽器在多數地區仍必須使用 **WebKit**（Apple 條款規定；EU 自 iOS 17.4、日本自 2025/12 起依法可用其他引擎）；Android 與桌機多數是 Chromium，Firefox 用 Gecko。

## 瀏覽器的組成與渲染引擎 {#1-3-3-5}

::: info 新增（2026-11）
本節以下整理自 Notion「Node.js 了不起」子頁〈瀏覽器原理〉（書籍摘錄 + AI 校正），已更新為現況。
:::

瀏覽器本質上是一個客戶端，但它的內容要先從伺服器取得再解析渲染，彈性換來的就是效能問題。組成中，使用者介面、UI 後端、網路、瀏覽器引擎是開發者改變不了的；要重點理解的是**渲染引擎**與 **JavaScript 引擎**。

| 瀏覽器 | 渲染引擎 | JS 引擎 |
| --- | --- | --- |
| Chrome、Edge、Opera | Blink（從 WebKit 分支） | V8 |
| Firefox | Gecko | SpiderMonkey |
| Safari | WebKit | JavaScriptCore |

舊引擎 Trident（IE）、EdgeHTML、Presto，以及 Chakra 等舊 JS 引擎都已淘汰。各家仍有差異，但都在往標準靠攏。

**User-Agent** 範例：`Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/130.0.0.0 Safari/537.36`

- `Mozilla/5.0` 是歷史相容標記，幾乎所有瀏覽器都以此開頭；括號內是平台。
- `AppleWebKit/537.36` 是渲染引擎標記（Blink 仍保留這段）；最後的 `Safari/...` 是給無法辨識 Chrome 的伺服器用的備選。
- UA 容易偽造，而且瀏覽器正在凍結 UA 字串、改用 **User-Agent Client Hints**（`Sec-CH-UA` 等標頭）。功能判斷應該用特性偵測，不要靠 UA。

## 影響渲染效能的細節 {#1-3-3-6}

**1. DOM 的巢狀深度**

同樣 10,000 個 `div`，全部平鋪成兄弟節點時解析約 50 毫秒；改成一層包一層的深層巢狀，解析時間可能多兩個數量級。標籤數量與**層級深度**都會影響建立 DOM 樹的時間，元件化時也要避免無意義的包裝層。

**2. CSS 選擇器由右往左比對**

瀏覽器拿每個元素去找符合的規則時，是從選擇器**最右邊**開始比對，不符合就立刻排除，避免從左往右時大量回溯。所以：

- 最右邊的「關鍵選擇器」要夠具體（class），不要是 `span`、`div`、`*` 這類會命中大量元素的選擇器。
- 例如 `div p.last span` 會先找出所有 `span` 再逐一往上檢查；`.list-item-title` 這類扁平的 class 選擇器最快。
- 實務上現代引擎已經很快，選擇器效能通常不是瓶頸，但在大量 DOM 與頻繁樣式重算時仍有差。

**3. Layout 一定帶來 Paint，Paint 不一定帶來 Layout**

在 10,000 個 `p` 的頁面上實測：改 `margin` 會重新 layout 再重新 paint，耗時明顯增加；只改 `color` 幾乎只花在 paint；改 `font-size` 雖然看似只是外觀，卻會改變文字尺寸而觸發 layout。修改樣式時要知道每個屬性會走到哪一階段（見上方 [渲染流程](#1-3-3-1) 的表格）。

現代渲染管線還多了 **Style 計算**、**Layer Tree** 與 **Composite**：被提升為獨立圖層的元素（`transform`、`opacity` 動畫）由合成執行緒處理，不佔主執行緒。

**4. 用 DevTools 驗證**

- Performance 面板：錄製後看 Parse HTML、Recalculate Style、Layout、Paint 各花多少時間，Insights 側欄會標出問題（舊的 Performance Insights 面板已併入）。
- Rendering 面板：開啟 Paint flashing 看重繪範圍、Layout Shift Regions 看版面位移。
- Layers 面板：看哪些元素被提升為合成圖層。

## JavaScript 引擎與 script 載入 {#1-3-3-7}

JS 引擎可以透過 DOM、BOM 操作頁面。為了避免兩邊同時改 DOM 產生衝突，**渲染與 JS 執行在同一條主執行緒上互相阻塞**：同步的 `script` 下載或執行太久，頁面就一直白畫面。

| 寫法 | 下載 | 執行時機 | 順序 |
| --- | --- | --- | --- |
| `script` | 阻塞解析 | 下載完立刻執行 | 依出現順序 |
| `script defer` | 與解析並行 | HTML 解析完成後、`DOMContentLoaded` 前 | 依出現順序 |
| `script async` | 與解析並行 | 下載完立刻執行（仍會打斷解析） | 不保證 |
| `script type="module"` | 與解析並行 | 預設同 `defer` | 依相依關係 |

把 `script` 放在 `body` 最後是舊做法；現在直接用 `defer` 或 module。

要在背景執行大量計算用 **Web Worker**（不能碰 DOM）；**Service Worker** 則是攔截網路請求、做離線快取與推播的代理層，不是拿來做一般計算的。

## 瀏覽器端的資料儲存 {#1-3-3-8}

瀏覽器不能直接讀寫磁碟，只能透過以下 API，而且依來源（origin）隔離：

| 方式 | 特性 | 注意 |
| --- | --- | --- |
| Cookie | 每次請求自動帶上，伺服器可透過標頭讀寫 | 約 4KB；設 `HttpOnly` 後 JS 讀不到；`Secure`、`SameSite` |
| localStorage | 鍵值字串，永久保存 | 同步 API 會阻塞主執行緒；JS 可讀，不放 token |
| sessionStorage | 同上，分頁關閉就清除 | 每個分頁獨立 |
| IndexedDB | 非同步的 NoSQL 資料庫，可存大量結構化資料與檔案 | API 較複雜，常用 idb、Dexie 包裝 |
| Cache Storage | 搭配 Service Worker 快取請求與回應 | 離線應用 |

WebSQL 已從 Chrome 移除，不要再用。

## 格式化上下文：BFC 與 IFC {#1-3-3-9}

格式化上下文是頁面中一塊獨立的渲染區域，類似程式語言的「獨立作用域」。BFC 的觸發條件與用途見 [1-1-2](./1-1-2.md) 與 [模擬面試 2 Q2](./interview-2.md#interview-2-2)。

**IFC（Inline Formatting Context）**：多個行內（或行內區塊）元素排在一起時形成；中間插入區塊元素就會被切成多個 IFC。

- IFC 內的元素水平排列，放不下就換行成多個行框（line box）。
- 水平方向的 margin、border、padding 有效；垂直方向的 margin 對行內元素無效。
- 垂直對齊用 `vertical-align` 調整，常見問題是圖片下方多出的空隙（基線對齊造成），可用 `display: block` 或 `vertical-align: middle` 解決。
