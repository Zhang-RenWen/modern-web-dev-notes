## 案例庫 {#1-22-2-1}

| 案例 | 發生什麼 | 教訓 |
| --- | --- | --- |
| i18n 預先國際化 | 只做中國市場的產品，一開始就做全套多語詞典、版本對應、CDN 快取處理，至今沒有任何外語使用者 | 不要解決想像出來的問題 |
| Hadoop 處理 10GB | 每小時 1000 萬行、總量不到 10GB，卻上 Hadoop 全家桶與共用叢集 | 資料塞得進記憶體就直接在記憶體算，省下數月工時 |
| Pinterest 拆庫 | 3 個工程師維護 7 種資料庫叢集；後來砍到 3 種，改成「大表單獨一庫、按邏輯拆庫」，MySQL 拆到 88 個仍撐住千萬級月活 | 最樸素的拆分常是最好的擴容 |
| Excel 取代 CMS | 用 Excel 當前端取代子公司 Java Web CMS，使用者反而更滿意 | 使用者在乎問題被解決，不在乎技術 |
| Postgres 一庫多用 | JSON、圖、KV 很多場景都能用 PostgreSQL 處理 | 熟一個成熟工具，可直接縮小技術棧 |

- **別造輪子**：通用輪子會變成有完整生命週期的產品，大多數在普及前就被棄坑。
- **規範交給 CI**：格式、命名等「沒有對錯」的爭論，在專案開始前定規則並放進 formatter / CI，不要在 code review 裡吵。

## 何時才需要 Design Pattern {#1-22-2-2}

先解問題，再用 Pattern 命名；不要為了用而用。出現以下訊號才引入：

| 訊號 | 可考慮 |
| --- | --- |
| 需求常變，一改就崩 | Strategy、State |
| 大量相似 if-else、重複邏輯 | Factory、Template Method |
| A 一動 B/C/D 都要改 | Observer、Mediator |
| 需要插件式擴充（支付、報表格式、第三方登入） | Decorator、Command、Factory + Interface |

## Clean Code：當工具，不當教條 {#1-22-2-3}

⚠️ 兩派衝突：Uncle Bob 派（函式要短、單一職責）vs 原子能派（KISS、反對沒必要的抽象與審美式規則）。調和方式：**唯一的裁判是「讓人更容易讀、改、合作」**；為了美觀而定的規則（如「函式不能超過 10 行」）就不要執行。

原則衝突時的優先序：**可讀性與意圖清晰 → SRP → 避免副作用 → 不過早抽象（YAGNI/KISS）→ 錯誤處理清晰 → OCP → DRY**

- 案例 1：Controller 驗證抽成 `validateFeedback()` → 抽（SRP 優先，用命名補可讀性）。
- 案例 2：只有一種 feedback 就先做 `FeedbackHandler` 介面 → 不抽（YAGNI，等出現第二種再重構）。
- 案例 3：重複的 `if empty throw` 想包成 `ValidationUtils` → 保留重複（語意比省行數重要）。

值得長期保留的 Clean Coder 守則：分清「承諾」和「嘗試」、敢說不、估時要誠實（別低估測試與除錯）、技術債要記錄、對團隊負責而非盲從命令。

## 可讀性與巢狀 {#1-22-2-4}

- 註解會過時甚至誤導；可讀性靠**清楚命名 + 單層流程（early return、抽函式）**。
- 巢狀控制在 **2–3 層**；超過就抽函式、拆模組、或改平坦資料結構。
- **合理的深層**：權限（Org→Team→Project→Resource→Action）、UI 樹、多環境設定、多租戶、文件樹、工作流、AST、i18n、PKI。控痛方式都一樣：
  - 對外給**扁平視圖或高階 API**（例：`can(user, action, resourcePath)`、`getConfig(key, ctx)`）
  - 用**路徑**定位（`org/123/team/7`），不要 `.a.b.c.d.e` 直穿
  - 讀寫分離：深層結構負責寫入一致性，讀取給扁平快照
  - 定義與執行分離、Schema 驗證、可觀測性
- 程式分兩層：**模組碼**（通用、獨立可測、統一介面）+ **業務碼**（按順序編排模組）。⚠️ 原影片進一步主張用 JSON 編排 + 程式碼生成取代業務碼，這屬於該團隊自家框架的做法，一般專案導入要非常謹慎。
- 前端：業務邏輯與模板分開；資料不要寫死在元件裡，大型系統用狀態管理。
