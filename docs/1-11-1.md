# 1-11-1 瀏覽器網路通訊入門 {#1-11-1}

::: info 改寫（2026-11）
原內容整理自《High Performance Browser Networking》（Ilya Grigorik，2013）第 14 章。已濃縮成「瀏覽器替你做了什麼」與「各種網路 API 怎麼選」兩部分，比較表改成文字並加入 `fetch`、WebTransport 等 2013 年之後的 API。
:::

> 一句話：**網頁的 JS 碰不到 socket**，只能透過瀏覽器提供的 API 發請求；瀏覽器在底下管連線、快取、安全限制，所以同樣的程式在不同情境下效能差很多。

## 瀏覽器替你做的事 {#1-11-1-1}

| 層面 | 瀏覽器做了什麼 | 對開發者的影響 |
| --- | --- | --- |
| 連線管理 | 依「來源（scheme + 網域 + port）」維護連線池，重用連線、依優先權排隊。HTTP/1.1 每個來源最多約 6 條連線；HTTP/2、HTTP/3 一條連線就能多工 | 不用自己管 socket；但 HTTP/1.1 下請求太多會排隊 |
| 預先連線 | 依瀏覽紀錄或提示預先做 DNS、TCP、TLS | 可以用 `preconnect` 提示（見 [1-6-4](./1-6-4.md#1-6-4-5)） |
| 安全沙盒 | 同源政策、CORS、禁止 JS 設定某些標頭（`Host`、`Cookie`、`Origin`…）、混合內容封鎖、TLS 驗證 | 跨網域請求要後端配合 CORS，見 [1-5-6](./1-5-6.md) |
| 快取與狀態 | HTTP 快取自動處理驗證與重新使用；Cookie 自動附加到符合的請求 | 快取策略由回應標頭決定，見 [1-6-3](./1-6-3.md) |
| 資源限制 | 背景分頁的計時器與網路節流、行動裝置省電 | 長連線在背景可能被暫停或中斷，要能重連 |

## 網路 API 怎麼選 {#1-11-1-2}

沒有萬用的協定，要依「誰主動發資料、多常發、要多即時」挑選：

| API | 方向 | 適合 | 備註 |
| --- | --- | --- | --- |
| `fetch`（XHR 的後繼者） | 用戶端請求 → 伺服器回應 | 一般 API 呼叫、上傳下載 | 支援串流讀取回應、`AbortController` 取消；需要上傳進度時仍要用 XHR。見 [1-11-2](./1-11-2.md) |
| Server-Sent Events（`EventSource`） | 伺服器 → 用戶端，單向 | 通知、即時動態、LLM 逐字輸出 | 走一般 HTTP、自動重連、只能傳文字。見 [1-11-3](./1-11-3.md) |
| WebSocket | 雙向 | 聊天、協作編輯、遊戲、行情報價 | 一條長連線雙向傳送文字或二進位；要自己處理重連、心跳、訊息格式。見 [1-11-4](./1-11-4.md) |
| WebRTC | 點對點 | 視訊通話、螢幕分享、P2P 傳檔 | 需要信令伺服器交換連線資訊，NAT 穿越靠 STUN／TURN。見 [1-11-5](./1-11-5.md) |
| WebTransport | 雙向，基於 HTTP/3 | 低延遲的遊戲、串流，可選擇不保證順序或不重傳 | Chromium、Firefox 支援，Safari 尚未全面支援，要準備備援 |
| Web Push（Push API） | 伺服器 → 裝置，頁面關閉也收得到 | 推播通知 | 透過 Service Worker 與瀏覽器廠商的推播服務 |

**判斷流程**：

1. 用戶端問一次、伺服器答一次 → `fetch`。
2. 伺服器要主動推、用戶端很少回傳 → SSE（比 WebSocket 簡單，能重用 HTTP 的認證、快取、負載平衡）。
3. 雙方都會頻繁發送 → WebSocket。
4. 要傳影音、或想讓資料不經過伺服器 → WebRTC。
5. 頁面沒開也要收到 → Web Push。

以前用來模擬推送的「輪詢」（每幾秒問一次）和「長輪詢」（伺服器有資料才回應），現在只在環境不允許長連線時當備援。
