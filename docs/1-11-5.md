# 1-11-5 WebRTC {#1-11-5}

::: info 改寫（2026-11）
原內容整理自《High Performance Browser Networking》（Ilya Grigorik，2013）第 18 章，當時 WebRTC 還是草案，API 要加瀏覽器前綴。原文約 1,300 行，逐層解說 DTLS、SRTP、SCTP 封包並附 Wireshark 截圖；已濃縮成「建立連線的流程」與「實務上怎麼部署」。WebRTC 在 2021 年成為 W3C 正式標準，所有瀏覽器都支援，不需要前綴或相容層。
:::

> 一句話：**讓兩個瀏覽器直接互傳影音或資料，不經過伺服器轉送**；但要先透過你自己的伺服器交換「怎麼找到對方」的資訊（信令），而且有些網路環境還是得靠中繼伺服器。

## 三個 API {#1-11-5-1}

| API | 用途 |
| --- | --- |
| `navigator.mediaDevices.getUserMedia({ video, audio })` | 取得攝影機、麥克風（要 HTTPS 和使用者授權）；螢幕分享用 `getDisplayMedia()` |
| `RTCPeerConnection` | 建立並管理點對點連線：協商、NAT 穿越、加密、頻寬調整 |
| `RTCDataChannel` | 在同一條連線上傳任意資料，可以選擇要不要保證順序與送達 |

## 建立連線的流程 {#1-11-5-2}

雙方要先交換兩種資訊，WebRTC **沒有規定**怎麼交換，通常用 WebSocket 寫一個簡單的信令伺服器：

1. **SDP（Session Description）**：我支援哪些編碼、要傳哪些媒體、加密的指紋。
2. **ICE candidate**：我可能可以被連到的位址（區網 IP、公網 IP、中繼位址）。

```js
const pc = new RTCPeerConnection({
  iceServers: [
    { urls: 'stun:stun.example.com' },
    { urls: 'turn:turn.example.com', username: 'u', credential: 'p' },
  ],
})

// 把本地的攝影機加進連線
const stream = await navigator.mediaDevices.getUserMedia({ video: true, audio: true })
stream.getTracks().forEach((t) => pc.addTrack(t, stream))

// 找到一個候選位址就立刻傳給對方（trickle ICE，不必等全部找完）
pc.onicecandidate = (e) => e.candidate && signaling.send({ candidate: e.candidate })
// 收到對方的影音
pc.ontrack = (e) => (remoteVideo.srcObject = e.streams[0])

// 發起方
const offer = await pc.createOffer()
await pc.setLocalDescription(offer)
signaling.send({ sdp: pc.localDescription })

// 接收方收到 offer 後
await pc.setRemoteDescription(offer)
await pc.setLocalDescription(await pc.createAnswer())
signaling.send({ sdp: pc.localDescription })

// 雙方收到對方的 candidate
await pc.addIceCandidate(candidate)
```

雙方可能同時發起協商（例如同時加入新的影音軌），MDN 的「perfect negotiation」模式示範了怎麼處理這種衝突。

## NAT 穿越：STUN 與 TURN {#1-11-5-3}

大多數裝置在路由器（NAT）後面，只有私有 IP，對方無法直接連進來。ICE 會依序嘗試：

| 方式 | 做法 | 成本 |
| --- | --- | --- |
| 區網直連 | 雙方在同一個網路 | 免費 |
| **STUN** | 問 STUN 伺服器「從外面看我的 IP 和 port 是多少」，再嘗試打洞直連 | STUN 伺服器很便宜，只回答一個問題 |
| **TURN** | 直連失敗（對稱型 NAT、公司防火牆）時，所有流量經過 TURN 伺服器中繼 | 貴：要負擔全部頻寬 |

正式服務**一定要準備 TURN**，否則一部分使用者會連不上；常見估計是一到兩成的連線需要中繼。TURN 也可以走 TCP 443 穿過嚴格的防火牆。

## 傳輸與加密 {#1-11-5-4}

- 一律加密，不能關閉：先用 **DTLS** 交換金鑰，影音用 **SRTP** 傳送，資料通道用 **SCTP over DTLS**。
- 底層用 UDP：即時影音寧可掉幾格畫面，也不要等重傳造成延遲。
- 瀏覽器會依網路狀況自動調整解析度與位元率；音訊用 Opus，影像用 VP8、VP9、H.264、AV1。

**DataChannel 的可靠性選項**：

```js
const reliable = pc.createDataChannel('chat')                                   // 預設：保證順序與送達，像 TCP
const fast = pc.createDataChannel('game-state', { ordered: false, maxRetransmits: 0 }) // 不保證：像 UDP，適合即時位置
```

遊戲裡的位置更新用不可靠通道並帶上序號，晚到的舊資料直接丟掉；道具使用、比賽結果這類重要事件用可靠通道。

## 多人通話怎麼架 {#1-11-5-5}

| 架構 | 做法 | 適合 |
| --- | --- | --- |
| Mesh（全連接） | 每個人和其他每個人直連 | 2～4 人；人數一多，每個人的上傳頻寬和 CPU 都撐不住 |
| **SFU**（選擇性轉發） | 每個人只上傳一份給伺服器，伺服器轉發給其他人，不解碼 | 現在的主流；搭配 simulcast（同時上傳高中低畫質，伺服器依收看者網路挑一種） |
| MCU（混流） | 伺服器把所有人的畫面合成一個再送出 | 用戶端很弱、或要錄影直播時；伺服器 CPU 成本高 |

自建 SFU 可以用 mediasoup、Janus、LiveKit；也可以用雲端服務（Twilio、Agora、Cloudflare Calls、LiveKit Cloud）。直播推流與觀看現在有 WHIP／WHEP 這兩個標準化的 HTTP 信令協定。

## 效能與部署檢查清單 {#1-11-5-6}

- 準備 STUN 與 TURN（TURN 要有 UDP、TCP、TLS 443 三種）。
- 用 trickle ICE 縮短建立連線的時間。
- 監控 `pc.getStats()`：往返時間、封包遺失率、位元率、目前是不是走 TURN。
- 依用途選擇 DataChannel 的可靠性設定；大檔案自己切塊，避免塞住通道。
- 行動裝置：注意電量與頻寬，非必要時降低解析度或關閉視訊。
