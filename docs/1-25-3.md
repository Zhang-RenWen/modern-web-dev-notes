# 1-25-3 TypeScript 開發原則 {#1-25-3}

::: info 新增（2026-11）
自己寫 TS 時怎麼做決定。每條原則都附上反例與正例。
:::

## 1. 開 strict，不要和編譯器妥協 {#1-25-3-1}

`tsconfig.json` 一律 `"strict": true`，建議再加 `noUncheckedIndexedAccess`。舊專案逐步開啟：先開 strict、用 `// @ts-expect-error` 標記既有錯誤，CI 擋住新增的錯誤（見 [模擬面試 4 Q9](./interview-4.md#interview-4-9)）。

**`明確型別 > unknown > any`**。真的要用 `any`，寫註解說明原因與移除時機。

## 2. 用型別表達業務規則 {#1-25-3-2}

型別最大的價值是讓錯誤在編譯期就出現。

```ts
// ❌ 用 string 和一堆 boolean 表達狀態
interface Order { status: string; isPaid: boolean; isRefunded: boolean; refundedAt?: Date }

// ✅ 狀態用聯集，每種狀態只帶該有的資料
type Order =
  | { status: 'pending'; id: string }
  | { status: 'paid'; id: string; paidAt: Date }
  | { status: 'refunded'; id: string; paidAt: Date; refundedAt: Date }
```

其他常用手法：
- 固定選項用字面量聯集或 `as const` 物件，不用一般 `string`（見 [模擬面試 4 Q7](./interview-4.md#interview-4-7)）。
- 容易混用的 ID、金額用 branded type 區分（見 [模擬面試 4 Q8](./interview-4.md#interview-4-8)）。
- 不可變的資料加 `readonly`、`ReadonlyArray<T>`。

## 3. 在邊界驗證，內部信任型別 {#1-25-3-3}

TS 型別在執行期不存在，**外部進來的資料都要驗證**：API 回應、表單、URL 參數、localStorage、第三方 SDK。

```ts
import { z } from 'zod'

const UserSchema = z.object({ id: z.number(), name: z.string(), email: z.string().email() })
type User = z.infer<typeof UserSchema>        // 型別從 schema 推導，只維護一份

export async function fetchUser(id: number): Promise<User> {
  const res = await fetch(`/api/users/${id}`)
  return UserSchema.parse(await res.json())   // 不符合就在這裡丟錯，不會讓髒資料流進系統
}
```

驗證只在邊界做一次，系統內部就可以信任型別，不需要到處判斷 `if (user && user.name)`。

## 4. 型別放在對的地方 {#1-25-3-4}

- **由來源產生型別，不要手抄**：API 型別由 OpenAPI 產生、資料庫型別由 ORM 產生（Prisma）、schema 型別由 Zod 推導。手抄的型別一定會和實際資料脫節。
- **區分不同層的型別**：API 回傳的 DTO、前端畫面要的 View Model、表單的 Form Model 不一定一樣，轉換集中在一處做（見 [1-6-11 去框架化 7 原則](./1-6-11.md#1-6-11-1)）。
- **衍生型別**：用 `Pick`、`Omit`、`Partial` 從主型別衍生，主型別一改，衍生型別自動跟著改。

```ts
type User = { id: number; name: string; email: string; createdAt: string }
type CreateUserInput = Omit<User, 'id' | 'createdAt'>
type UpdateUserInput = Partial<CreateUserInput>
```

## 5. 少用斷言 {#1-25-3-5}

`as` 和 `!` 是在告訴編譯器「相信我」，等於關掉檢查：

```ts
// ❌
const el = document.querySelector('#app') as HTMLDivElement
el.innerHTML = '...'                       // 如果元素不存在，執行期才爆

// ✅ 讓 TS 幫你檢查
const el = document.querySelector<HTMLDivElement>('#app')
if (!el) throw new Error('#app not found')
el.innerHTML = '...'
```

能用縮小型別、`satisfies`、泛型參數解決的就不要用斷言（見 [模擬面試 4 Q6](./interview-4.md#interview-4-6)）。

## 6. 函式簽章是契約 {#1-25-3-6}

- 參數多於三個或有可選參數時，改用物件參數，呼叫端可讀性高、順序不會弄錯。
- 公開函式寫明回傳型別，避免實作改動時默默改變介面。
- 錯誤也是契約的一部分：可預期的失敗（驗證失敗、找不到資料）可以用回傳值表達，讓呼叫端被迫處理。

```ts
type Result<T, E = string> = { ok: true; value: T } | { ok: false; error: E }

function parseAmount(input: string): Result<number> {
  const n = Number(input)
  if (!Number.isFinite(n) || n <= 0) return { ok: false, error: '金額必須大於 0' }
  return { ok: true, value: Math.round(n * 100) }      // 以「分」為單位的整數
}

const r = parseAmount(form.amount)
if (!r.ok) showError(r.error)
else submit(r.value)
```

## 7. type 與 interface 統一一種 {#1-25-3-7}

物件形狀兩者都能用；需要聯集、tuple、mapped type 時只能用 `type`；要讓外部擴充（宣告合併）時用 `interface`。團隊約定一種主要寫法即可（見 [模擬面試 4 Q2](./interview-4.md#interview-4-2)）。

## 8. 不要過度設計型別 {#1-25-3-8}

型別是給人讀的。十層巢狀的條件型別也許很厲害，但下一個接手的人看不懂，就變成維護負擔。

- 業務程式碼的型別保持簡單直接；複雜的型別運算留在共用函式庫裡，並附上使用範例。
- 型別錯誤訊息看不懂時，先拆成幾個有名字的中間型別。

## 檢查清單 {#1-25-3-9}

- [ ] `strict` 開啟，沒有新增的 `any`
- [ ] 外部資料在邊界驗證
- [ ] 狀態用可辨識聯合，不用一堆 boolean
- [ ] 型別從單一來源產生或衍生
- [ ] 沒有不必要的 `as`、`!`
- [ ] 公開函式有明確的參數與回傳型別
