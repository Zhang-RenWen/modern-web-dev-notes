# 1-25-5 物件導向設計原則與常見模式 {#1-25-5}

::: info 新增（2026-11）
設計原則是「為什麼這樣切」的理由。看懂這些，Java 專案裡一層層的 interface、Service、Repository 就不再是莫名其妙的樣板。範例都用 TypeScript。
:::

## SOLID {#1-25-5-1}

| 原則 | 一句話 | 違反時的症狀 |
| --- | --- | --- |
| **S** 單一職責 | 一個類別只有一個「會讓它改變的理由」 | 改報表格式卻要動到寄信的程式 |
| **O** 開放封閉 | 新增功能靠擴充，不靠修改既有程式 | 每加一種付款方式就改一次 `switch` |
| **L** 里氏替換 | 子類別要能完全替代父類別 | 子類別覆寫方法後直接丟「不支援」 |
| **I** 介面隔離 | 介面要小，不強迫實作用不到的方法 | 實作類別裡一堆空方法 |
| **D** 依賴反轉 | 高層邏輯依賴抽象，不依賴具體實作 | 業務邏輯直接 `new MySqlRepository()`，換資料庫要改業務程式、也沒辦法測試 |

**O 與 D 的例子**：

```ts
// ❌ 每加一種付款方式都要改這個函式，而且業務邏輯綁死在具體實作上
async function checkout(order: Order, method: 'card' | 'linepay') {
  if (method === 'card') await new CardClient().charge(order.total)
  else if (method === 'linepay') await new LinePayClient().pay(order.total)
}

// ✅ 業務邏輯只依賴介面；新增付款方式 = 新增一個實作，不動 CheckoutService
interface PaymentGateway {
  charge(amount: number): Promise<string>
}

class CheckoutService {
  constructor(private readonly gateways: Record<string, PaymentGateway>) {}

  async checkout(order: Order, method: string) {
    const gateway = this.gateways[method]
    if (!gateway) throw new Error(`不支援的付款方式：${method}`)
    return gateway.charge(order.total)
  }
}
```

原則是工具不是教條：只有一種實作、短期也不會有第二種時，不必為了 O 和 D 先做介面（見 [1-22-2 何時才需要 Design Pattern](./1-22-2.md#1-22-2-2)）。

## 組合優於繼承 {#1-25-5-2}

繼承的問題：父類別一改，所有子類別都受影響；層數一深，很難知道某個方法到底在哪一層定義；而且只能繼承一個父類別。

```ts
// ❌ 用繼承組合能力：會飛又會游的怎麼辦？
class Animal {}
class FlyingAnimal extends Animal { fly() {} }
class SwimmingAnimal extends Animal { swim() {} }
class Duck extends ???

// ✅ 用組合：把能力當成零件裝進去
interface CanFly { fly(): void }
interface CanSwim { swim(): void }

class Duck implements CanFly, CanSwim {
  constructor(private wings: Wings, private feet: WebbedFeet) {}
  fly() { this.wings.flap() }
  swim() { this.feet.paddle() }
}
```

現代 Java 與 TS 的主流寫法都是：**interface + 組合 + 依賴注入**，繼承只用在框架要求或明確的 is-a 關係。

## 依賴注入（DI） {#1-25-5-3}

物件不自己 `new` 它的依賴，而是由外部（通常是框架的容器）傳進來：

```ts
// 自己 new：綁死實作、無法替換、無法測試
class OrderService {
  private repo = new PostgresOrderRepository()
}

// 依賴注入：只宣告需要什麼
class OrderService {
  constructor(private readonly repo: OrderRepository) {}
}

// 正式環境
const service = new OrderService(new PostgresOrderRepository(db))
// 測試
const service = new OrderService(new InMemoryOrderRepository())
```

Angular、NestJS、Spring 都有 DI 容器：你只要在建構子宣告需要的型別，框架會自動建立並傳入。看到 Java 的 `@Autowired` 或建構子注入、NestJS 的 `@Injectable()`，就是這件事（見 [模擬面試 7 Q2](./interview-7.md#interview-7-2)）。

## 分層架構：Controller → Service → Repository {#1-25-5-4}

這是後端（Spring、NestJS）最常見的結構，每層只做自己的事：

```txt
Controller   接收請求、驗證輸入、轉成 DTO、呼叫 Service、回傳回應（不放業務規則）
    ↓
Service      業務邏輯與交易邊界（例如：檢查庫存 → 建立訂單 → 扣款，要嘛全成功、要嘛全失敗）
    ↓
Repository   存取資料庫（查詢、儲存），不知道業務規則
    ↓
Entity       對應資料表的物件
```

```ts
// DTO：API 進出的資料形狀，和資料庫 Entity 分開
class CreateOrderDto { productId!: string; quantity!: number }

class OrderController {
  constructor(private readonly orders: OrderService) {}
  create(dto: CreateOrderDto, userId: string) {
    return this.orders.create(userId, dto)
  }
}

class OrderService {
  constructor(private readonly orders: OrderRepository, private readonly stock: StockService) {}
  async create(userId: string, dto: CreateOrderDto) {
    await this.stock.reserve(dto.productId, dto.quantity)   // 業務規則在這一層
    return this.orders.save(Order.create(userId, dto))
  }
}
```

看懂這個分層，就能在任何 Spring 專案裡快速找到東西：API 從 Controller 進來，邏輯在 Service，SQL 在 Repository（見 [1-25-6 Spring 專案結構](./1-25-6.md#1-25-6-6)）。

## 常見設計模式 {#1-25-5-5}

| 模式 | 解決什麼 | 你會在哪裡看到 |
| --- | --- | --- |
| **Strategy** | 同一件事有多種做法，執行期選一種 | 付款方式、計價規則、排序方式（上面的 PaymentGateway） |
| **Factory** | 依條件建立不同的物件，呼叫端不用知道細節 | `NotifierFactory.create(type)`、Spring 的 Bean 建立 |
| **Repository** | 把資料存取包成像集合一樣的介面 | Spring Data JPA 的 `JpaRepository`、TypeORM |
| **Singleton** | 全系統只有一個實例 | DI 容器預設的 Service、設定物件 |
| **Observer** | 狀態改變時通知訂閱者 | 事件系統、EventEmitter、RxJS、Spring 的 ApplicationEvent |
| **Decorator** | 不改原物件，包一層加功能 | 快取、記錄日誌、重試的包裝；Spring AOP |
| **Adapter** | 把不相容的介面轉成需要的介面 | 包裝第三方 SDK、各家銀行介接 |
| **Template Method** | 父類別定流程，子類別填細節 | 上一頁的 `BaseNotifier`、Spring 的 `JdbcTemplate` |
| **Builder** | 參數很多的物件一步步建立 | Java 的 `User.builder().name(...).build()`（Lombok） |

```ts
// Decorator 模式：不改原本的 Repository，加上快取
class CachedUserRepository implements UserRepository {
  private cache = new Map<string, User>()
  constructor(private readonly inner: UserRepository) {}

  async findById(id: string) {
    const hit = this.cache.get(id)
    if (hit) return hit
    const user = await this.inner.findById(id)
    if (user) this.cache.set(id, user)
    return user
  }
}
```

更多模式與 JS 實作見 [1-5 設計模式](./1-5.md)。

## 什麼時候不需要這些 {#1-25-5-6}

- 只有一種實作，短期內也不會有第二種 → 先不要抽介面。
- 一個函式就能解決 → 不需要 class。
- 小專案、原型、一次性腳本 → 簡單直接最重要。

先寫出能動的程式，**出現重複、變化、難以測試的訊號時再重構成模式**，而不是一開始就套（見 [1-22-2 大道至簡](./1-22-2.md)）。
