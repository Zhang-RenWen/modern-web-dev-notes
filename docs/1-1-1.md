# 1-1-1 HTML 語意化 {#1-1-1}

::: info 改寫（2026-11）
原內容整理自 2019 年前的書籍，已精簡並更新：標籤分類表刪掉已廢除的 `command`、`param`，「微格式（Microformats）」改成現在搜尋引擎實際採用的 JSON-LD 結構化資料。
:::

> 一句話：**依內容的意思選標籤，而不是依長相。** 長相交給 CSS。

## 為什麼要語意化 {#1-1-1-1}

| 好處 | 說明 |
| --- | --- |
| 無障礙 | 螢幕閱讀器靠標籤判斷「這是導覽列、這是主內容、這是按鈕」，使用者可以直接跳到 `<main>` 或列出所有標題 |
| 內建行為 | `<button>` 天生可以用 Tab 聚焦、按 Enter／空白鍵觸發；`<div onclick>` 這些都要自己補 |
| SEO | 搜尋引擎用標題層級和 `<article>` 判斷頁面重點 |
| 維護 | 讀程式碼的人一眼看出結構，CSS 選擇器也不用靠一堆 class |

## 怎麼選標籤 {#1-1-1-2}

| 內容 | 用 | 備註 |
| --- | --- | --- |
| 網站或區塊的頁首、頁尾 | `<header>`、`<footer>` | 可以出現在 `<article>` 裡，代表那篇文章的頁首頁尾 |
| 主要導覽連結 | `<nav>` | 不是每組連結都要包 `<nav>`，只包主要的 |
| 頁面主內容 | `<main>` | 一頁只有一個（可見的） |
| 可以單獨拿出去用的內容：文章、留言、商品卡 | `<article>` | 判斷方式：放到 RSS 或別的頁面還看得懂 |
| 有標題的主題區塊 | `<section>` | 沒有標題就用 `<div>` |
| 和主內容相關但可以拿掉的：側欄、廣告、延伸閱讀 | `<aside>` | |
| 搜尋表單 | `<search>` | 2023 年起各大瀏覽器支援 |
| 圖片、圖表、程式碼範例加說明 | `<figure>` + `<figcaption>` | |
| 標題 | `<h1>`～`<h6>` | 不要跳級（`h2` 下面直接 `h4`），也不要為了字大而用標題 |
| 會觸發動作的元素 | `<button>` | 換頁用 `<a href>`，執行動作用 `<button>` |
| 強調、重要 | `<em>`、`<strong>` | `<i>`、`<b>` 只是樣式上的區分，沒有強調語意 |
| 純排版容器 | `<div>`、`<span>` | 沒有語意，前面都不合適時才用 |

常見錯誤：

- 用 `<div class="btn" onclick>` 做按鈕：鍵盤無法操作，螢幕閱讀器也不知道它能按。
- 圖片沒有 `alt`，或裝飾性圖片寫了一長串 `alt`（裝飾圖要寫 `alt=""`）。
- 表單欄位沒有 `<label for>`，點文字不會聚焦輸入框，閱讀器也念不出欄位名稱。

無障礙的檢測方式與 ARIA 用法見 [1-1-3 無障礙設計](./1-1-3.md)。

## 結構化資料：讓搜尋引擎讀懂實體 {#1-1-1-3}

語意標籤只說明「這是一篇文章」，說不出「這是一個食譜，烹調時間 30 分鐘」。要讓搜尋結果顯示星等、價格、活動日期這類資訊，要加上 [schema.org](https://schema.org/) 的結構化資料。

早期做法是微格式（Microformats，例如用 `class="vcard"` 標記聯絡資訊），現在 Google 建議用 **JSON-LD**：和 HTML 結構分開，比較好維護。

```html
<script type="application/ld+json">
{
  "@context": "https://schema.org",
  "@type": "Article",
  "headline": "HTML 語意化",
  "datePublished": "2026-11-14",
  "author": { "@type": "Person", "name": "Author" }
}
</script>
```

寫完用 Google 的 [Rich Results Test](https://search.google.com/test/rich-results) 檢查。
