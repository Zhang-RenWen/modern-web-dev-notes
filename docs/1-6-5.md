# 1-6-5 應用程式傳輸最佳化 {#1-6-5}

::: info 改寫（2026-11）
原內容整理自《High Performance Browser Networking》（Ilya Grigorik，2013）第 13 章。當時 HTTP/2 還是草案，一半篇幅在討論 HTTP/1.x 與 2.0 並存的部署策略；現在 HTTP/2 已是主流、HTTP/3 也普及，已刪掉雙協定部署與 SPDY 的內容。更新：Server Push 已被瀏覽器移除；網域分片、檔案合併、雪碧圖在 HTTP/2 下反而有害。TCP、TLS 參數調校屬於伺服器端，移到個人筆記，不在本站範圍。
:::

> 一句話：**光速和距離改不了，能做的是減少往返次數、減少傳輸的位元組、讓瀏覽器盡早知道要抓什麼。**

## 不受協定版本影響的原則 {#1-6-5-1}

| 原則 | 為什麼 | 做法 |
| --- | --- | --- |
| 減少 DNS 查詢 | 每個新網域都要一次查詢 | 合併第三方網域；必要的用 `dns-prefetch`／`preconnect` |
| 重用連線 | 新連線要 TCP + TLS 握手，還要經過慢啟動 | HTTP/2、HTTP/3 一個網域一條連線就夠；不要每個請求都關閉連線 |
| 減少重新導向 | 每次導向都是一次完整往返，可能還要連到新網域 | 連結直接寫最終網址；`http → https` 交給 HSTS |
| 用 CDN | 往返時間取決於距離 | 靜態資源、可快取的頁面放邊緣節點 |
| 刪掉不需要的資源 | 最快的請求是不發的請求 | 定期檢查第三方腳本、沒用到的 CSS／JS |
| 快取 | 不必重新下載 | 見 [1-6-3](./1-6-3.md) |
| 壓縮 | 文字檔壓縮後通常剩 20～30% | 文字用 Brotli（舊用戶端退回 gzip）；**已壓縮的圖片、影片不要再壓** |
| 圖片最佳化 | 圖片通常是頁面最大的部分 | AVIF／WebP、依螢幕給適當尺寸、移除 EXIF 等中繼資料 |
| 減少請求標頭 | Cookie 每個請求都會帶 | 靜態資源放在不帶 Cookie 的網域；Cookie 只放必要的 |

## HTTP/1.1 時代的技巧，現在要拆掉 {#1-6-5-2}

HTTP/1.1 一條連線同時只能處理一個請求（管線化有隊頭阻塞問題，瀏覽器實際上沒啟用），每個網域只能開約 6 條連線。所以當年發展出這些技巧：

| HTTP/1.1 技巧 | 原本的目的 | HTTP/2、HTTP/3 之下 |
| --- | --- | --- |
| 網域分片（`img1.`、`img2.` 多個網域） | 突破每網域 6 條連線的限制 | **有害**：多了 DNS 和握手，還破壞單一連線的優先權排序。HTTP/2 一條連線就能多工 |
| 合併成一支大 JS／CSS | 減少請求數 | **不划算**：改一行就整包快取失效。改成依路由、依功能切成適當大小的 chunk |
| 雪碧圖 | 減少圖片請求數 | 不需要：用 SVG 圖示 |
| 內嵌資源（base64 圖片、內嵌 CSS） | 省掉一次往返 | 只對**極小**且首屏必要的內容有意義（例如關鍵 CSS）；內嵌的東西無法單獨快取 |

HTTP/2 的多工不代表檔案越碎越好：每個請求仍有標頭與處理成本，壓縮率也會變差。實務上打包工具預設的 chunk 切法（共用套件一包、每個路由一包）就是不錯的平衡。

## Server Push 已經走入歷史 {#1-6-5-3}

HTTP/2 Server Push 讓伺服器在瀏覽器要求之前就推送資源。實際上很難用對：推送的資源瀏覽器可能早就快取了，反而浪費頻寬。Chrome 106（2022）起移除支援，HTTP/3 的瀏覽器也沒有實作。

替代方案：

- **`103 Early Hints`**：伺服器還在產生 HTML 時，先回一個 103 告訴瀏覽器要 `preload`／`preconnect` 什麼，由瀏覽器自己決定要不要抓（它知道自己有沒有快取）。
- **`<link rel="preload">`**：寫在 HTML 或回應標頭裡。

## 瀏覽器端最容易犯的錯 {#1-6-5-4}

就算網路層都最佳化了，頁面還是可能被自己擋住：

- 同步的 `<script>` 放在 `<head>` 裡，阻塞 HTML 解析。
- 關鍵資源只在 JS 裡動態載入，瀏覽器的預載掃描器看不到，很晚才發出請求。
- CSS 用 `@import` 串接，或字型藏在 CSS 深處，形成好幾層「下載完才知道下一個」。

瀏覽器怎麼排優先權、怎麼給提示，見 [1-6-4](./1-6-4.md#1-6-4-5)。
