## 先決定要回答什麼問題 {#1-10-4-1}

| 想知道 | 先用 | 再用 |
| --- | --- | --- |
| 使用者說卡，是程式還是他的環境？ | `chrome://gpu` | Rendering 面板的 FPS 計數 |
| 現在幾 fps、有沒有掉幀？ | Rendering 面板 Frame Rendering Stats | Puppeteer 自動量測（可重複、可比對） |
| 慢在 JS、樣式計算、版面，還是 GPU？ | Performance 面板錄一段 | Tracing 加事件彙總 |
| 是哪個 CSS 或圖層造成的？ | Rendering 面板 Paint flashing、Layer borders | A／B 變體測試（逐一關掉可疑樣式） |
| 一幀到底畫了幾次、用了哪些 shader？ | `renderer.info` | Spector.js 擷取單一影格 |
| 有沒有記憶體或 WebGL 資源洩漏？ | Memory 面板 heap snapshot | `renderer.info.memory`、反覆掛載卸載 |
| 改動有沒有讓載入變慢？ | Lighthouse | 建置輸出的 chunk 大小 |
| 邏輯有沒有被改壞？（不是快慢） | Vitest 模擬 renderer | — |

## 環境檢查（每次量測前） {#1-10-4-2}

**`chrome://gpu`**：確認瀏覽器真的在用 GPU。

- Graphics Feature Status 裡的 WebGL、WebGL2 要是「Hardware accelerated」；顯示「Software only」代表 3D 全由 CPU 畫。
- `GL_RENDERER` 應是實際顯示晶片（Mac 上類似 ANGLE、Apple、Metal 字樣）；出現 SwiftShader 就是軟體模擬。
- 案例：改到 60 fps 之後使用者仍說卡，原因是 Chrome 設定裡的「使用圖形加速」被關掉（`chrome://settings/system`），程式再怎麼改都沒用。

**其他會讓數字失真的因素**

- 筆電用電池、過熱降頻：插電量。
- 螢幕更新率：120 Hz 螢幕的理想值是 120 fps，不是 60；判斷要用「幀間隔是否穩定」而不是只看 fps。
- 擴充功能、其他分頁：用無痕視窗或乾淨的設定檔。
- 殘留的瀏覽器程序：上一次自動化測試崩潰留下的 Chrome 會搶 GPU，量之前先關掉。
- 開發伺服器與正式建置不同：比較改動前後時兩邊用同一種模式即可；要報告絕對數字時用正式建置（`npm run build` 後 `npm run preview`）。

## Chrome DevTools {#1-10-4-3}

**Rendering 面板**（Cmd+Shift+P 輸入「Show Rendering」）

- Frame Rendering Stats：畫面左上角出現即時 fps 與 GPU 記憶體。
- Paint flashing：重繪的區域會閃綠色。捲動時如果整塊大面板一直閃，代表每幀都在重繪它。
- Layer borders：顯示合成圖層邊界。圖層太多或太大都會吃記憶體。
- Emulate CSS media feature `prefers-reduced-motion`：確認「減少動態」模式下動畫真的停了。

**Performance 面板**

- 錄製後實際操作 3～5 秒（捲動、移動滑鼠）。模擬手機可把 CPU 設成 4x slowdown。
- Frames：紅色、黃色的影格就是掉幀或只畫了一部分。
- Main：紅色三角形是超過 50 ms 的長任務；捲動時如果每幀都有 React 重繪，就是「捲動時 setState」的問題。
- GPU：長條持續很滿，代表瓶頸在繪製量（像素填充、draw call）。Bottom-Up 依自身耗時排序找最花時間的函式。
- DevTools 開著本身就有成本，數字會比實際略差；用來找原因，不要拿來報告最終數字。

**Performance monitor**（Cmd+Shift+P 輸入「Show Performance monitor」）：即時看 CPU、JS heap、DOM Nodes、Layouts／sec、Style recalcs／sec。捲動時 Layouts／sec 衝高就是改了會影響版面的屬性；JS heap 持續上升不回落，可能是每幀建立新物件或洩漏。

**Memory 面板**：先拍一張 heap snapshot，進出頁面 5 次，再拍一張，用 Comparison 看 Three.js 物件（BufferGeometry、Material、WebGLRenderer）有沒有只增不減。瀏覽器同時能開的 WebGL context 數量有限，沒釋放時 console 會出現「Too many active WebGL contexts」。

## Three.js 與 WebGL 專用工具 {#1-10-4-4}

```js
// renderer.info：Three.js 內建統計。開發時暫時掛到 window，合併前移除
window.__renderer = renderer
__renderer.info.render // calls（draw call 數）、triangles、points、lines
__renderer.info.memory // geometries、textures 數量
```

- draw call：同材質的線合併、重複形狀用 instancing 之後，這個數字應該很小（範例主視覺整個場景只有 11 個繪製物件）。
- memory：元件卸載後 geometries、textures 應歸零；沒有歸零就是 `dispose()` 漏了。
- **Spector.js**（瀏覽器擴充功能）：擷取單一影格的所有 WebGL 呼叫，逐一檢視每個 draw call 的 shader、uniform、混合模式、貼圖。適合懷疑「某個效果其實畫了很多次」或 shader 太重時。
- **stats.js、lil-gui**：頁面角落顯示 FPS、每幀毫秒數；即時調整透明度、粒子數等參數。只在開發分支用，合併前移除。

## 自動化量測：Puppeteer {#1-10-4-5}

手動量測每次結果都不一樣；自動化腳本在改動前後跑同一套動作，數字才能比較。

```js
// 一定要有視窗、用真的 GPU：headless 沒有垂直同步，fps 不準
const browser = await puppeteer.launch({
  headless: false,
  defaultViewport: null,
  args: ['--use-angle=metal', '--enable-gpu', '--ignore-gpu-blocklist', '--window-size=1440,960'],
})

// 頁面載入前注入計數器
await page.evaluateOnNewDocument(() => {
  // 場景實際畫了幾次：攔截 WebGL clear（每畫一格都會呼叫）
  window.__renders = []
  const clear = WebGL2RenderingContext.prototype.clear
  WebGL2RenderingContext.prototype.clear = function (...args) {
    window.__renders.push(performance.now())
    return clear.apply(this, args)
  }
  // 瀏覽器實際送出幾格
  window.__frames = []
  const loop = (t) => { window.__frames.push(t); requestAnimationFrame(loop) }
  requestAnimationFrame(loop)
  // 長任務總時間
  window.__long = 0
  new PerformanceObserver((list) => list.getEntries().forEach((e) => (window.__long += e.duration)))
    .observe({ type: 'longtask', buffered: true })
})

// 用 CDP 取得瀏覽器內部耗時，情境前後各取一次相減
const cdp = await page.createCDPSession()
await cdp.send('Performance.enable')
const metrics = async () =>
  Object.fromEntries((await cdp.send('Performance.getMetrics')).metrics.map((m) => [m.name, m.value]))
// ScriptDuration、RecalcStyleDuration、LayoutDuration、TaskDuration

// 固定的操作情境：滑鼠畫圓 360 次、滾輪 240 次，每次間隔 16 ms
for (let i = 0; i < 360; i++) {
  const a = i / 30
  await page.mouse.move(720 + Math.cos(a) * 300, 450 + Math.sin(a) * 180)
  await new Promise((r) => setTimeout(r, 16))
}
for (let i = 0; i < 240; i++) {
  await page.mouse.wheel({ deltaY: 12 })
  await new Promise((r) => setTimeout(r, 16))
}
```

- **兩個計數器一起看**：瀏覽器每秒 60 格、場景卻只畫 22 次，代表場景自己在跳幀。原本的 30 fps 限速就是這樣抓到的。
- **要報告的數字**：把時間戳換成相鄰間隔後排序，算出 fps、p50、p95、最大間隔、超過 25 ms 的影格數；每個情境輸出一行 JSON，方便改動前後並排比較。
- **需要登入的頁面**：建一個暫時的測試頁，直接渲染要量的元件，量完刪除、不提交。

## Tracing：找出「是誰」造成卡頓 {#1-10-4-6}

```js
await page.tracing.start({
  path: 'scroll-trace.json',
  categories: ['devtools.timeline', 'disabled-by-default-devtools.timeline.frame', 'gpu', 'viz', 'cc', 'blink'],
})
// ……執行捲動情境……
await page.tracing.stop()
```

讀取 traceEvents，依「執行緒＋事件名稱」加總、依單次最大耗時排序，前 20 名通常就看得出元兇；也可以把 JSON 拖進 [Perfetto UI](https://ui.perfetto.dev/) 或 DevTools Performance 面板。

| 關鍵事件 | 代表 |
| --- | --- |
| `GLContext::BackpressureFenceWait` | GPU 忙不過來，CPU 在等它：減少繪製量、降低解析度 |
| `RasterDecoderImpl::DoRasterCHROMIUM` | 點陣化成本高：大面積陰影、`backdrop-filter`、反覆顯示隱藏的大元素 |
| 樣式重算、版面配置 | 捲動時改了會影響版面的屬性，或每幀觸發 React 重繪 |

**A／B 變體**：同一個情境跑好幾次，每次用 `page.addStyleTag` 關掉一個可疑樣式，比較 fps 與點陣化時間。「關掉 canvas」這個變體可以分辨卡頓來自 3D 場景還是頁面其他部分。

```js
const variants = {
  current: '',
  'no-backdrop': '.panel{backdrop-filter:none!important}',
  'no-backdrop-no-shadow': '.panel{backdrop-filter:none!important;box-shadow:none!important}',
  'no-canvas': '.scene-canvas{display:none!important}',
}
```

## 其他工具 {#1-10-4-7}

- **macOS 活動監視器**：「視窗 → GPU 歷史記錄」看 GPU 使用率。滿載代表瓶頸在繪製；很低但仍然卡，代表瓶頸在 CPU 或主執行緒。
- **Lighthouse、Web Vitals**：量的是載入與互動（LCP、TBT、INP），不是動畫流暢度。用來確認 three.js 有被拆成獨立 chunk、沒有拖慢首次載入。
- **Vitest 模擬 renderer**：證明邏輯，不證明快。mock 掉 renderer，取出 `setAnimationLoop` 註冊的函式自己餵時間戳，斷言「60 格就畫 60 次」、「持續變慢才降解析度」、「離開畫面停止迴圈」。可以放進 CI，防止有人把限速或每幀 setState 改回來。

## 標準量測流程 {#1-10-4-8}

1. `chrome://gpu` 確認硬體加速；插電；關掉殘留的瀏覽器程序。
2. 決定情境（閒置、滑鼠移動、捲動），寫成 Puppeteer 腳本。
3. `git stash` 把改動收起來，跑一次當基準；`git stash pop` 後再跑一次。
4. 數字不對時，用 Performance 面板或 tracing 找原因；懷疑某個樣式就做 A／B 變體。
5. 桌機與手機尺寸都拍改動前後截圖並排比較。
6. 把數字寫進 commit 說明：情境、改動前、改動後、量測環境（機型、螢幕更新率、瀏覽器）。

## 判讀速查 {#1-10-4-9}

| 看到 | 可能原因 | 下一步 |
| --- | --- | --- |
| 瀏覽器 60 格、場景只畫一半以下 | 程式自己跳幀或限速 | 改成每個動畫影格都畫，緩動用時間計算 |
| 平均 fps 正常但 p95 很高 | 偶發長影格：記憶體回收、重設畫布、點陣化 | Performance 面板找長任務；檢查每幀是否建立新物件 |
| 捲動時 Script 與樣式重算暴增 | 捲動時 setState 或改了影響版面的屬性 | 改寫 CSS 變數或 transform／opacity |
| BackpressureFenceWait 很長 | GPU 瓶頸 | 降低 pixel ratio、關掉高 DPR 的 MSAA、合併 draw call |
| 點陣化時間長 | 大陰影、`backdrop-filter`、反覆顯示隱藏 | A／B 變體逐一關掉確認 |
| JS heap 持續上升不回落 | 洩漏或每幀配置 | Memory 面板比較快照；檢查 dispose |
| 只有某位使用者卡 | 硬體加速關閉、舊裝置、省電模式 | 先看 `chrome://gpu` |
