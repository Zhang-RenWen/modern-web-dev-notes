### Q1. D3、ECharts、自己畫 SVG 怎麼選？ <Badge type="tip" text="高頻" /> {#interview-14-1}

::: details 標準答案與過程
| | D3 | ECharts | 自製 SVG |
| --- | --- | --- | --- |
| 本質 | 用資料驅動 DOM 的工具組：比例尺、座標軸、線條產生器都是零件，圖要自己組 | 設定式圖表庫：給一份 option 就出圖 | 用框架的 template 或 JSX 自己畫 |
| 繪製 | 通常是 SVG | 預設 Canvas，也可以切成 SVG | SVG |
| 互動 | 自己做 | tooltip、圖例切換、dataZoom 都內建 | 自己做 |
| 適合 | 照產品需求高度客製的圖 | 標準的走勢、長條、圓餅圖 | 資料語意要細緻控制、資料量小 |

判斷三件事：

1. **客製化程度**：每個元素都要自己決定的圖用 D3；標準圖用 ECharts 最快。
2. **資料量**：SVG 每個點都是一個 DOM 節點，幾萬個點就會卡，大量資料選 Canvas 繪製的套件（見 [模擬面試 8 Q3](./interview-8.md#interview-8-3)）。
3. **誰來維護**：D3 程式碼多，接手的人要懂 D3；團隊不熟就選設定式的套件，比較好交接。

自己畫 SVG 的理由通常是金融語意：單位、缺值、資料修訂這些，套件的預設行為不一定對。代價是開發成本高，互動都要自己做；資料量變大（分 K、很多檔同時顯示）時，再回頭評估 Canvas 的圖表庫。
:::

### Q2. D3 的 data join 是什麼？跟 Vue／React 一起用時誰管 DOM？ <Badge type="warning" text="進階" /> {#interview-14-2}

::: details 標準答案與過程
**data join**：把資料陣列綁到一組元素上，分三種情況處理：

- **enter**：有資料、沒元素 → 新增元素。
- **update**：兩邊都有 → 更新屬性。
- **exit**：有元素、沒資料 → 移除元素。

```js
svg.selectAll('circle')
  .data(points, d => d.date) // 第二個參數是 key
  .join(
    enter => enter.append('circle').attr('r', 3),
    update => update,
    exit => exit.remove(),
  )
  .attr('cx', d => x(d.date))
  .attr('cy', d => y(d.value))
```

**key 很重要**：預設用索引對應，資料順序一變，更新和動畫就會對錯元素；時間序列用日期當 key。新版 D3 用 `join()` 一次處理三種情況。

**跟框架一起用**：同一塊 DOM 不能兩邊一起改，否則框架重新渲染時會把 D3 畫的東西蓋掉。兩種分工：

1. 框架只管容器，D3 在元件掛載後接手容器內部；資料變了在 watch／effect 裡更新，卸載時清掉事件監聽和 transition。
2. D3 只負責「算」（比例尺、路徑字串），SVG 交給框架的 template 或 JSX 渲染。資料量不大時，這種寫法比較好維護。
:::

### Q3. ECharts 放進框架裡要注意什麼？ <Badge type="tip" text="高頻" /> {#interview-14-3}

::: details 標準答案與過程
ECharts 是一個要自己管生命週期的實例：`init` → `setOption` → `resize` → `dispose`。常見的坑：

1. **在隱藏的容器裡 init**：`display: none` 的元素量不到尺寸，畫布寬度是 0。等容器真的顯示之後（例如頁籤切換事件加上 `nextTick`）再 `resize`；更通用的做法是用 `ResizeObserver` 監聽容器，側欄收合也能處理。
2. **卸載沒有 `dispose`**：實例和事件監聽留在記憶體裡，越用越多。
3. **每次資料更新都重新 init**：應該保留同一個實例，用 `setOption` 更新。
4. **把實例放進響應式資料**：框架會去代理整個實例，拖慢效能甚至出怪問題；放在一般變數、`shallowRef`，或用 `markRaw`。
5. **`setOption` 預設是合併**：series 變少時舊的可能還留著；圖的結構變了（例如換圖表類型）就加 `notMerge: true` 整份換掉。

```ts
// Vue 3
const el = ref<HTMLDivElement>()
let chart: echarts.ECharts | null = null // 不放進 ref／reactive
let ro: ResizeObserver | null = null

onMounted(() => {
  chart = echarts.init(el.value!)
  ro = new ResizeObserver(() => chart?.resize())
  ro.observe(el.value!)
})

watch(data, (d) => chart?.setOption(buildOption(d))) // 同一個實例更新

onBeforeUnmount(() => {
  ro?.disconnect()
  chart?.dispose()
  chart = null
})
```

**資料量大時**：用 `sampling` 降採樣、`large` 模式，搭配 `dataZoom` 只看一段；也先問使用者真的需要看多長，例如歷史資料預設只顯示兩年。
:::

### Q4. K 線圖要注意什麼？ <Badge type="tip" text="基礎" /> {#interview-14-4}

::: details 標準答案與過程
**資料**：一根 K 線是一段期間的開、高、低、收（OHLC）。實體是開盤到收盤，上下影線是最高和最低。台股習慣漲紅跌綠，美股相反，顏色要依市場設定。

**前端三件事**：

1. **x 軸用交易日**，不是日曆日，休市日才不會留空白（做法見 [1-10-3 金融圖表](./1-10-3.md#1-10-3-1)）。
2. **週期換算**：週 K 由日 K 聚合，開盤取該週第一個交易日、收盤取最後一個交易日、最高最低取極值、成交量相加。
3. **使用者預期的互動**：這些是業界標配，需求沒寫也要先問清楚，不然第一版常常只有一張靜態圖。可以列成驗收清單：
   - 看某一根：十字線、日期、OHLC 數值。
   - 看不同區段：拖曳平移、縮放時間範圍。
   - 回到現在：回到最新、重設視圖。
   - 比較週期：資料來源支援時，可以切換日 K、週 K。
   - 畫線工具、多種技術指標另外判斷要不要做。

**疊加成交量與訊號**：

- 指數不是個股，資料要分開存，混進個股日行情會污染統計和篩選。
- 量用成交金額、不用股數，因為股數會被低價股放大。
- 訊號規則放在前端算，好處是調門檻不用重新部署後端（資料量小時，瀏覽器算一次只要幾毫秒）；代價是要做推播通知時，得把規則整份搬到後端。同一條規則只能有一個地方在管。
- 改規則前先用真實資料回測：看起來對稱的規則不一定有效。
- 訊號只描述狀態，不給買賣建議，這是投資資訊的法規界線。
:::

### Q5. 圖表上的金額單位、手機版怎麼處理？ <Badge type="tip" text="基礎" /> {#interview-14-5}

::: details 標準答案與過程
**格式化之前先確認資料語意**：畫面顯示怪數字時，不一定是格式化的問題。例如資料源的單位是「十億美元」，程式卻標成「百萬美元」，差了 1,000 倍，只改 formatter 會錯得更多。先對照資料源的單位定義，再決定怎麼顯示。

**顯示**：軸標籤和卡片用 T／B／M／K 動態縮寫，tooltip 顯示完整金額；不要只靠 tooltip，因為手機沒有 hover（見 [1-10-3](./1-10-3.md#1-10-3-1)）。被極端值壓扁的長期圖，詳細頁預設顯示較短的期間；值可能接近 0 的序列不要用對數座標。

**手機版：等比縮小，還是另做一套？** 看縮小後還讀不讀得懂：

- **讀得懂就等比縮小**：保留桌機排版，依容器寬度縮進螢幕（見 [1-2-5](./1-2-5.md#1-2-5-2)），一套排版、一套測試。
- **讀不懂就另做一套**：例如教學用的插圖，每個標籤都要在手機上看得清楚，就桌面、手機各一套座標。
:::

::: details IE11 時代的 SVG 坑（IE11 已在 2022 年停止支援）
- SVG 不吃 CSS 的 `transform`：位移、縮放要寫在 SVG 元素的 `transform` 屬性。
- `foreignObject` 裡的 HTML（例如 tooltip）不會顯示：把 tooltip 移到 SVG 外面，用絕對定位的 div 疊在圖上。
- 元件銷毀時要 `dispose` 圖表實例，否則 IE 的記憶體會越用越多。
:::
