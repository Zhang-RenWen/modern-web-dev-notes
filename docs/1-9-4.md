# 1-9-4 標準化工具管理團隊 {#1-9-4}

::: info 改寫（2026-11）
原內容整理自 2019 年前的書籍，設定檔是 `.eslintrc`、husky 4 的 `package.json` 寫法，並逐行解讀 ESLint 原始碼。已更新為 ESLint 9 的 flat config（`eslint.config.js`）、husky 9，補上 Biome 這類一體化工具；原始碼解讀濃縮成「怎麼寫一條自訂規則」。
:::

> 一句話：**格式交給 Prettier，品質交給 ESLint，在 commit 前自動執行，讓 code review 只討論邏輯。**

## 各工具管什麼 {#1-9-4-1}

| 工具 | 管什麼 | 例子 |
| --- | --- | --- |
| Prettier | **格式**：縮排、引號、換行、分號，沒有選擇空間（只有少數選項） | 存檔自動排版 |
| ESLint | **程式碼品質**：可能的 bug、不好的寫法 | 未使用的變數、`==`、Hooks 依賴漏寫 |
| TypeScript（`tsc --noEmit`） | 型別錯誤 | |
| Stylelint | CSS 的品質與規範 | |
| EditorConfig | 編輯器基本設定（縮排、換行字元、檔尾空行） | 讓不同 IDE 一致 |
| Biome、Oxlint | 用 Rust 寫的格式化與 lint 工具，快很多倍 | Biome 可以同時取代 Prettier 和大部分 ESLint 規則 |

ESLint 和 Prettier 一起用時，要用 `eslint-config-prettier` 關掉 ESLint 裡和格式有關的規則，避免兩邊互相改。ESLint 官方也已經把格式類規則移出核心，交給 `@stylistic` 外掛。

## ESLint 9：flat config {#1-9-4-2}

```js
// eslint.config.js
import js from '@eslint/js'
import tseslint from 'typescript-eslint'
import reactHooks from 'eslint-plugin-react-hooks'
import prettier from 'eslint-config-prettier'

export default [
  { ignores: ['dist/'] },
  js.configs.recommended,
  ...tseslint.configs.recommended,
  {
    plugins: { 'react-hooks': reactHooks },
    rules: {
      ...reactHooks.configs.recommended.rules,
      'no-console': ['warn', { allow: ['warn', 'error'] }],
    },
  },
  prettier, // 放最後：關掉和 Prettier 衝突的規則
]
```

和舊的 `.eslintrc` 相比：設定就是一個 JS 陣列，後面的覆蓋前面的；外掛用 `import` 直接引入，不再靠字串名稱去找。ESLint 9 預設只讀 flat config。

## commit 前自動檢查 {#1-9-4-3}

```bash
npm i -D husky lint-staged
npx husky init               # 建立 .husky/pre-commit
echo "npx lint-staged" > .husky/pre-commit
```

```json
// package.json
{
  "lint-staged": {
    "*.{js,ts,tsx,vue}": ["eslint --fix", "prettier --write"],
    "*.{css,md,json}": "prettier --write"
  }
}
```

- **lint-staged** 只檢查這次要 commit 的檔案，不會每次掃整個專案。
- hook 可以被 `--no-verify` 跳過，所以 **CI 一定要再跑一次**完整的 lint、型別檢查和測試，那才是真正的守門員。

**commit 訊息規範**：用 commitlint 檢查是否符合 Conventional Commits（`feat:`、`fix:`、`docs:`…），之後可以自動產生 changelog、決定版本號。

```bash
npm i -D @commitlint/cli @commitlint/config-conventional
echo "export default { extends: ['@commitlint/config-conventional'] }" > commitlint.config.js
echo 'npx --no -- commitlint --edit "$1"' > .husky/commit-msg
```

## ESLint 的原理：寫一條自訂規則 {#1-9-4-4}

ESLint 把程式碼解析成 AST，每條規則訂閱自己關心的節點類型，走訪到時檢查並回報。

```js
// 禁止 console.log，但允許 console.error
export default {
  meta: {
    type: 'suggestion',
    docs: { description: '不要留下 console.log' },
    fixable: 'code',
    messages: { noLog: '請移除 console.log' },
  },
  create(context) {
    return {
      // 選擇器語法類似 CSS：成員運算式 console.log 的呼叫
      'CallExpression[callee.object.name="console"][callee.property.name="log"]'(node) {
        context.report({
          node,
          messageId: 'noLog',
          fix: (fixer) => fixer.remove(node.parent), // 提供 --fix 自動修正
        })
      },
    }
  },
}
```

規則由 `meta`（描述、能不能自動修正、訊息）和 `create`（回傳「節點選擇器 → 檢查函式」）組成。團隊特有的規範（例如禁止直接 import 某個內部模組）寫成自訂規則，比寫在文件裡有效。

## 元件文件 {#1-9-4-5}

元件越來越多時，要讓人找得到、知道怎麼用，避免每個人重做一次：

- **Storybook**：每個元件寫幾個 story（不同 props 的狀態），產生可互動的元件目錄，也能做視覺回歸測試。現在是業界標準。
- 從 TypeScript 型別自動產生 props 表格（Storybook 內建 `react-docgen-typescript`、Vue 的 `vue-component-meta`）。
- 規範寫進工具（lint 規則、範本、產生器），比寫進文件更容易被遵守。
